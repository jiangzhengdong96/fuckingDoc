### Java 枚举知识点清单

###### 内容概述

本文件记录 Java 枚举相关知识点，包括枚举基础、枚举字段和方法、构造方法、抽象方法和策略枚举、常用 API、`EnumSet` / `EnumMap`、枚举单例、序列化和 Android 使用场景，以及关联面试题。

###### 使用场景

- 枚举适合表示固定数量的状态、类型、模式、错误码、排序规则、页面来源等。
- 枚举可以替代散落的字符串或数字常量，提高可读性、类型安全和可维护性。
- 枚举可以把固定状态和对应行为放在一起，例如支付状态展示文案、接口错误码说明、策略分发。
- Android 高频性能敏感或对包体极端敏感的场景可能会使用 `@IntDef` / `@StringDef`，但普通业务优先考虑可读性和类型安全。

<a id="枚举基础"></a>
###### 枚举基础

- 枚举用于定义一组固定常量。相比 `public static final int` 或字符串常量，枚举有类型约束，调用方不能传入集合之外的值。

```java
public enum OrderStatus {
    CREATED,
    PAID,
    CANCELED
}
```

- 每个枚举常量都是该枚举类型的一个固定实例。枚举类本质上继承自 `java.lang.Enum`，所以枚举不能再继承其他类，但可以实现接口。
- 枚举常量通常写在枚举类最前面，多个常量用逗号分隔。如果后面还有字段或方法，常量列表后面要写分号。
- 枚举适合“有限集合”。如果值可能来自服务端动态配置、数据库动态扩展，或者业务需要频繁新增不固定类型，就不一定适合用枚举写死。
- `switch` 可以直接处理枚举，适合少量分支；如果每个枚举值都有各自行为，策略枚举可能比大量 `switch` 更集中。

<a id="枚举字段和方法"></a>
###### 枚举字段和方法

- 枚举可以有字段、方法和接口实现，用来给每个枚举常量绑定额外信息。

```java
public enum ErrorCode {
    NETWORK(1001, "网络异常"),
    UNAUTHORIZED(1002, "未登录");

    private final int code;
    private final String message;

    ErrorCode(int code, String message) {
        this.code = code;
        this.message = message;
    }

    public int getCode() {
        return code;
    }

    public String getMessage() {
        return message;
    }
}
```

- 枚举字段建议尽量设计为不可变，例如使用 `private final`。如果枚举持有可变状态，所有调用方共享同一个枚举实例，容易出现线程安全和状态污染问题。
- 用枚举表达业务码时，建议显式定义 `code` 字段，而不是依赖 `ordinal()`。显式 code 更稳定，也更适合持久化、网络传输和数据库存储。
- 可以给枚举增加静态查找方法，例如根据 code 找枚举，避免到处手写循环解析。

<a id="枚举构造方法"></a>
###### 枚举构造方法

- 枚举构造方法只能是 private 语义，不能写 public 或 protected。即使不显式写 `private`，外部也不能直接 `new` 枚举对象。
- 枚举常量创建时会调用构造方法，构造参数写在枚举常量后面的括号里。
- 枚举构造方法执行时要避免依赖还未初始化完成的复杂静态状态。一般只做字段赋值，不做复杂逻辑。
- 不能通过反射普通方式创建枚举实例，Java 对枚举构造有特殊限制。

<a id="抽象方法和策略枚举"></a>
###### 抽象方法和策略枚举

- 枚举可以定义抽象方法，由每个枚举常量分别实现，适合固定策略分发。

```java
public enum Operation {
    PLUS {
        @Override
        int apply(int a, int b) {
            return a + b;
        }
    },
    MINUS {
        @Override
        int apply(int a, int b) {
            return a - b;
        }
    };

    abstract int apply(int a, int b);
}
```

- 策略枚举适合每个枚举值行为差异明确、数量固定的场景。它能减少散落在各处的 `if` / `switch`。
- 如果策略会不断扩展、依赖复杂对象或需要运行时动态注册，普通接口 + 类实现可能比枚举更灵活。

<a id="常用-api"></a>
###### 常用 API

- `values()` 返回当前枚举类型的所有常量数组。每次调用通常会返回新数组，不要在高频路径反复调用后再修改。
- `valueOf(String name)` 根据枚举常量名解析枚举，传入不存在的名称会抛出 `IllegalArgumentException`，传入 `null` 会抛出 `NullPointerException`。
- `name()` 返回枚举常量声明时的名字，通常比 `toString()` 更稳定；`toString()` 可以被重写，适合展示，不适合做稳定协议。
- `ordinal()` 返回枚举常量声明顺序，从 0 开始。它适合 `EnumSet` / `EnumMap` 等内部实现，不适合业务持久化或网络传输。
- `compareTo()` 按 `ordinal()` 顺序比较枚举，排序结果依赖声明顺序。

<a id="enumset-和-enummap"></a>
###### EnumSet 和 EnumMap

- `EnumSet` 是专门给枚举设计的高效 Set，内部通常用位向量表达枚举集合，适合保存一组选项、权限、标记位。

```java
EnumSet<Permission> permissions = EnumSet.of(Permission.READ, Permission.WRITE);
```

- `EnumMap` 是 key 为枚举类型的高效 Map，内部按枚举 `ordinal` 建立数组索引，适合用枚举映射文案、策略、配置。

```java
EnumMap<OrderStatus, String> textMap = new EnumMap<>(OrderStatus.class);
textMap.put(OrderStatus.PAID, "已支付");
```

- 如果 key 是枚举，优先考虑 `EnumMap` 而不是普通 `HashMap`。它更紧凑，也避免了哈希计算。
- `EnumSet` / `EnumMap` 都要求枚举类型明确，不适合动态 key。

<a id="枚举单例"></a>
###### 枚举单例

- 枚举可以实现单例：

```java
public enum AppConfig {
    INSTANCE;

    public void init() {
    }
}
```

- 枚举单例由 JVM 保证唯一实例，天然支持序列化时保持单例语义，也能避免常规反射创建新实例的问题。
- 枚举单例适合简单、无继承需求、生命周期和类加载一致的单例。Android 中如果单例需要 `Context`、生命周期管理、依赖注入或测试替换，要谨慎使用。
- 不要在枚举单例里长期持有 Activity / View 等短生命周期对象，避免内存泄漏。

<a id="枚举和序列化"></a>
###### 枚举和序列化

- 枚举天然实现 `Serializable`。Java 序列化枚举时主要依赖枚举常量名称，而不是普通对象字段序列化逻辑。
- 枚举反序列化后仍然会回到同一个枚举常量实例，不会创建一个新的普通对象实例。
- 如果修改枚举常量名称，旧序列化数据可能无法反序列化；如果只是新增枚举常量，一般不会影响旧常量读取。
- 不要依赖 `ordinal()` 保存枚举。调整顺序、插入新枚举都会改变 ordinal，旧数据会被错误解释。
- 对外协议、数据库字段、本地持久化更推荐保存显式 `code` 或稳定字符串，再通过查找方法转换成枚举。

<a id="android-使用场景和注意点"></a>
###### Android 使用场景和注意点

- Android 业务层可以正常使用枚举表示状态和类型，尤其是可读性、类型安全优先的地方。
- 早期 Android 开发里常说“避免枚举”主要是出于方法数、内存和性能考虑。现代构建工具和运行时优化后，普通业务不必机械回避枚举，但高频、底层、极致性能路径仍要结合实际测量。
- `@IntDef` / `@StringDef` 可以在保留 int / String 运行时形式的同时提供编译期约束，适合 Android SDK 风格 API 或性能敏感常量。
- 和服务端交互时，不要直接依赖枚举 `name()` 或 `ordinal()`，除非协议明确约定。更稳妥的是使用显式 code，并处理未知 code。
- 服务端新增枚举值时，客户端旧版本可能不认识。解析时要准备 `UNKNOWN` 或兜底逻辑，避免崩溃。

<a id="常见坑"></a>
###### 常见坑

- 用 `ordinal()` 做数据库值、网络值或本地持久化值，后续调整枚举顺序会导致数据错乱。
- 用 `valueOf()` 直接解析外部输入，不处理异常，服务端下发未知值时容易崩溃。
- 在枚举里放可变字段，多个调用方共享同一个枚举实例，可能造成状态污染。
- 把枚举用于动态扩展的业务类型，导致每次服务端新增值都必须发版客户端。
- 以为 `toString()` 一定等于枚举名。`toString()` 可以重写，稳定标识应优先用 `name()` 或显式 code。
- Android 中在极高频路径滥用复杂枚举对象，没有结合性能测量。
