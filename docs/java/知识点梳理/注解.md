### Java 注解知识点清单

###### 内容概述

本文件记录 Java 注解相关知识点，包括注解基础、注解参数、元注解、内置注解、运行时注解和反射读取、编译期注解处理、Android 使用场景和注意点，以及关联面试题。

###### 使用场景

- Android 中 Retrofit、Room、Hilt、Glide、Lint 等框架大量使用注解。
- 运行时注解常配合反射读取元数据。
- 编译期注解常配合 APT/KSP 生成代码，减少手写模板代码。
- 注解适合表达元数据和约束，不适合直接承载复杂业务逻辑。

###### 注解基础

- 注解本质是代码里的元数据，用来描述类、方法、字段、参数、构造方法、包、类型使用位置等信息。注解本身不会自动改变代码行为，真正产生效果的是编译器、注解处理器、框架或运行时反射逻辑对注解的读取和处理。
- 注解类型本身也是一种特殊的接口类型，编译后会有对应的 class 元信息。所有注解类型都和 `java.lang.annotation.Annotation` 相关，因此运行期读取注解时会通过反射 API 获取注解对象和注解参数。
- 定义注解使用 `@interface`，例如：

```java
public @interface Route {
    String path();
}
```

- 使用注解时可以把参数写在括号里：

```java
@Route(path = "/home")
public class HomeActivity {
}
```

- 注解可以用于编译期检查，例如 `@Override` 让编译器检查是否真的重写了父类方法；也可以用于运行期框架逻辑，例如 Retrofit 读取接口方法上的 HTTP 注解；还可以用于编译期生成代码，例如 Room、Hilt、Glide 等框架通过处理注解生成辅助类。
- 注解和反射关系密切，但不是所有注解都能在运行期通过反射读取。是否能被反射读到，取决于 `@Retention` 的保留策略。

###### 注解参数

- 注解里定义的参数也叫注解元素，本质上是无参数方法。参数类型只能是有限几类：

| 可用类型 | 示例 |
|---|---|
| 基本类型 | `int count()` |
| `String` | `String value()` |
| `Class` | `Class<?> target()` |
| 枚举 | `Mode mode()` |
| 注解 | `Meta meta()` |
| 上面类型的数组 | `String[] names()` |

- 注解参数可以有默认值，使用 `default` 声明：

```java
public @interface Route {
    String path();
    boolean needLogin() default false;
}
```

- 如果注解只有一个参数，并且参数名叫 `value`，使用时可以省略参数名：

```java
public @interface Api {
    String value();
}

@Api("/user/list")
public void listUser() {
}
```

- 注解参数不能随意使用普通对象类型，例如不能直接写 `User user()`。如果需要表达复杂结构，通常拆成基础类型、枚举、`Class` 或数组，或者交给注解处理器根据这些元数据生成代码。
- 注解参数值必须是编译期常量，不能使用运行期变量作为注解参数。比如 `static final` 编译期常量可以，普通变量不可以。

###### 元注解

- 元注解是用来修饰注解的注解，用于描述“这个注解可以用在哪里、保留到什么时候、是否出现在文档、是否可重复、是否可被子类继承”等规则。

| 元注解 | 作用 |
|---|---|
| `@Target` | 指定注解可以标记的位置 |
| `@Retention` | 指定注解保留到哪个阶段 |
| `@Documented` | 指定注解是否出现在 Javadoc 文档中 |
| `@Inherited` | 指定类注解是否可以被子类继承 |
| `@Repeatable` | 指定注解是否可以在同一位置重复使用 |

- `@Target` 常见位置：

| ElementType | 含义 |
|---|---|
| `TYPE` | 类、接口、枚举、注解类型 |
| `FIELD` | 字段 |
| `METHOD` | 方法 |
| `PARAMETER` | 方法参数 |
| `CONSTRUCTOR` | 构造方法 |
| `LOCAL_VARIABLE` | 局部变量 |
| `ANNOTATION_TYPE` | 注解类型 |
| `PACKAGE` | 包 |
| `TYPE_PARAMETER` | 泛型类型参数 |
| `TYPE_USE` | 类型使用位置 |

- `@Retention` 常见策略：

| RetentionPolicy | 含义 | 常见场景 |
|---|---|---|
| `SOURCE` | 只保留在源码阶段，编译后丢弃 | `@Override`、`@SuppressWarnings`、部分 Lint 注解 |
| `CLASS` | 保留到 class 文件，运行期反射通常读不到 | 编译期/字节码处理、Android 编译期框架 |
| `RUNTIME` | 保留到运行期，可以通过反射读取 | 运行时框架、动态解析注解 |

- 如果没有显式写 `@Retention`，默认是 `RetentionPolicy.CLASS`。旧笔记里“自定义注解通常要求运行期读取，所以要加 `@Retention(RetentionPolicy.RUNTIME)`”这个说法要加条件：只有需要运行期反射读取时才设置为 `RUNTIME`；如果是编译期处理，`SOURCE` 或 `CLASS` 更常见。
- `@Inherited` 只对类上的注解继承有效，并且只作用于 class 的继承关系。它不作用于接口继承，也不作用于方法、字段、参数等位置。
- `@Repeatable` 让同一个注解可以在同一位置重复使用。使用它时需要定义一个容器注解，用来承载多个重复注解。
- `@Documented` 只影响 Javadoc，不影响注解是否能被编译器、反射或注解处理器读取。

###### 内置注解

- `@Override` 用于标记方法重写，编译器会检查这个方法是否真的重写了父类或接口方法。它主要是编译期检查，能避免方法名、参数列表写错后变成普通新方法。
- `@Deprecated` 表示 API 已过时，不推荐继续使用。它通常会让编译器或 IDE 给出警告；可以配合 `since`、`forRemoval` 等属性说明从哪个版本开始废弃、未来是否计划移除。
- `@SuppressWarnings` 用于抑制编译器警告，例如 `@SuppressWarnings("unchecked")` 常见于受控泛型强转。不要为了消除警告滥用，应先确认警告是否真的安全。
- `@SafeVarargs` 用于告诉编译器某个泛型可变参数方法是安全的，常见于 `final`、`static` 或 private 方法。它不是让不安全代码变安全，而是开发者承诺方法内部没有污染泛型数组。
- `@FunctionalInterface` 用于标记函数式接口，编译器会检查接口是否只有一个抽象方法，常用于 Lambda 相关 API。

###### 运行时注解和反射读取

- 运行时注解需要 `@Retention(RetentionPolicy.RUNTIME)`，否则反射通常读不到。读取注解常用 API：

| API | 作用 |
|---|---|
| `isAnnotationPresent()` | 判断是否存在某个注解 |
| `getAnnotation()` | 获取指定注解，不存在返回 `null` |
| `getAnnotations()` | 获取可见注解，类上的 `@Inherited` 可能影响结果 |
| `getDeclaredAnnotation()` | 获取当前元素直接声明的指定注解 |
| `getDeclaredAnnotations()` | 获取当前元素直接声明的所有注解 |

- 读取类、字段、方法、构造方法上的注解都比较直接：

```java
Route route = HomeActivity.class.getAnnotation(Route.class);

Method method = ApiService.class.getDeclaredMethod("listUser");
GET get = method.getAnnotation(GET.class);
```

- 读取方法参数注解时会更复杂，因为一个方法有多个参数，每个参数又可以有多个注解，所以通常返回二维数组：

```java
Annotation[][] annotations = method.getParameterAnnotations();
```

- 运行时注解常见于需要动态读取元数据的框架，比如 Retrofit 根据接口方法上的注解构建请求，某些路由或序列化框架根据类、字段、方法上的注解决定映射关系。
- 运行时注解 + 反射的缺点是启动或首次调用时有扫描和解析成本，也容易受混淆影响。如果注解里依赖类名、字段名、方法名字符串，需要考虑 R8/ProGuard 规则。

###### 编译期注解处理

- 编译期注解处理常见方式是 APT、KAPT、KSP 或 Java 标准注解处理器。它们在编译阶段扫描注解，读取源码或符号信息，然后生成新代码、索引文件或校验错误。
- 编译期注解处理的优势是：把运行期反射扫描提前到编译期，减少启动开销；生成代码后调用链更明确；很多错误能在编译期暴露。
- 编译期注解处理通常不能直接修改已有源码，而是生成新的源码、资源或中间文件。框架再通过这些生成物完成注册、依赖注入、路由表、数据库访问对象等能力。
- Android 常见场景：

| 场景 | 说明 |
|---|---|
| Room | 根据注解处理 Entity、Dao、Database，生成数据库访问实现 |
| Hilt / Dagger | 根据依赖注入注解生成依赖图和工厂代码 |
| Glide | 通过注解和生成代码扩展 API |
| Router 类框架 | 根据路由注解生成路由表，避免运行时全量扫描 |
| Lint / AndroidX 注解 | 用于静态检查、约束 API 使用方式 |

- 编译期注解处理和运行时注解的核心区别：编译期处理关注“编译时生成或检查”，运行时注解关注“程序运行时读取和执行”。选择哪一种取决于是否需要动态能力、是否关注启动性能、是否能接受生成代码。

###### Android 使用场景和注意点

- Android 中注解非常常见，但不同框架使用注解的方式不同。Retrofit 更偏运行期读取接口方法注解；Room、Hilt、Dagger、Glide 更偏编译期生成代码；Lint 和一些 AndroidX 注解更偏静态检查和约束。
- 注解会影响混淆策略。运行期反射读取类、字段、方法和注解时，混淆可能导致找不到目标或注解信息丢失，需要按框架要求配置 `-keep` 规则。编译期生成代码的框架通常对运行期反射依赖更少，但仍要遵守官方混淆配置。
- 注解不是越多越好。注解适合描述稳定的元数据和约束；如果注解参数过多、表达复杂业务逻辑，代码可读性和可维护性会下降。
- 自定义注解时先明确处理阶段：只给编译器或 Lint 看，用 `SOURCE`；需要 class 文件处理，用 `CLASS`；需要运行期反射读取，用 `RUNTIME`。不要无脑把所有注解都设成 `RUNTIME`。
- 自定义注解最好同时明确 `@Target` 和 `@Retention`。不写 `@Target` 时注解可用于很多位置，容易被误用；不写 `@Retention` 时默认是 `CLASS`，运行时反射读不到。
