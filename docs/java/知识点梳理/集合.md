### Java 集合知识点清单

###### 内容概述

本文件记录 Java 集合相关知识点，包括集合体系、底层数据结构、List、Set、Map、Queue、Iterator、Collections 工具类、排序和比较、Android 常见集合、时间复杂度和空间复杂度、选择建议、常见坑和关联面试题。

###### 使用场景

- Android 页面列表、接口列表数据、Adapter 数据源通常会用到 `List`，常见实现是 `ArrayList`。
- 缓存、参数组装、索引映射、按 id 查找对象时经常用 `Map`，常见实现是 `HashMap`、`LinkedHashMap`。
- 去重、状态集合、标签集合、权限集合等场景适合用 `Set`。
- 任务排队、生产者消费者、广度优先遍历等场景会用到 `Queue` 或 `Deque`。
- Android 小规模 int/long key 映射、内存缓存等场景还会遇到 `SparseArray`、`ArrayMap`、`LruCache`。

<a id="集合体系"></a>
###### 集合体系

- Java 集合大体分为 `Collection` 和 `Map` 两条体系。`Collection` 是单列集合，表示一组元素，常见子接口有 `List`、`Set`、`Queue`；`Map` 是双列集合，保存 key-value 映射关系，不继承 `Collection`。
- `List` 的核心特点是有序、可重复、可按索引访问，适合保存列表数据；`Set` 的核心特点是元素不重复，适合去重和集合判断；`Queue` 的核心特点是队列语义，适合按一定规则排队处理元素。
- `Map` 的核心特点是 key 唯一、value 可重复，适合通过 key 快速查找 value。常见实现有 `HashMap`、`LinkedHashMap`、`TreeMap`、`Hashtable`、`ConcurrentHashMap`。
- `Iterable` 表示对象可以被迭代，`Collection` 继承了 `Iterable`，所以大多数集合可以使用增强 for 遍历。`Iterator` 是具体的迭代器模型，隐藏了集合内部结构。
- `Collection` 是集合接口，`Collections` 是工具类。`Collections` 提供排序、洗牌、不可变包装、同步包装、空集合、单元素集合等静态工具方法。

<a id="底层数据结构"></a>
###### 底层数据结构

- 集合底层结构不要只背“数组快、链表增删快、HashMap 是 O(1)”。更准确的理解是：不同数据结构是在用不同方式解决“数据怎么放、怎么找、怎么改”的问题，所以才会影响访问速度、插入删除成本、空间占用、顺序性和适用场景。

- **数组**：数组的核心是“一段连续空间 + 下标寻址”。假设数组起始地址是 `base`，每个元素占用大小是 `size`，访问 `arr[i]` 时大概可以理解为：

```text
元素地址 = base + i * size
```

  所以按下标访问是 `O(1)`，因为不需要从头遍历，直接根据下标计算位置。`ArrayList` 底层就是动态数组，适合随机访问、尾部追加、作为列表数据源。数组的问题是中间插入和删除会破坏连续顺序，例如 `[A, B, C, D]` 中间插入 `X` 后变成 `[A, X, B, C, D]`，`B/C/D` 都要往后移动，所以中间插入是 `O(n)`；删除中间元素时，后面的元素也要往前补位。`ArrayList` 扩容也是类似思路：旧数组装不下时创建更大的新数组，再把旧元素复制过去。

- **链表**：链表的核心是“节点不连续，每个节点靠引用串起来”。双向链表节点可以理解成：

```text
prev <- [data] -> next
```

  `LinkedList` 底层是双向链表，并且同时实现了 `List` 和 `Deque`。链表的优势不是“随便删除都快”，而是“如果已经拿到了目标节点，修改引用就能插入或删除”。例如 `A <-> B <-> C` 删除 `B` 时，只需要让 `A.next = C`、`C.prev = A`，这一步是 `O(1)`。但实际使用时通常没有直接拿到节点，如果只是知道“删除第 1000 个元素”，链表仍然要从头或尾走过去找到它，这个查找过程是 `O(n)`。所以面试里说“LinkedList 删除一定比 ArrayList 快”是不严谨的，更准确是：已知节点位置时，链表插入删除成本低；按索引查找时，链表反而慢。

- **哈希表**：哈希表的核心是“用 hash 把 key 映射到数组桶位”。大概流程可以理解为：

```text
key -> hashCode() -> hash 扰动 -> 桶下标 -> 找到桶 -> 比较 key
```

  理想情况下，每个 key 比较均匀地分散到不同桶里，例如 `bucket[0] -> A`、`bucket[1] -> B`、`bucket[2] -> C`，这时 `get()`、`put()`、`remove()` 接近 `O(1)`。但桶里真正保存的不是单独的 value，而是一个完整节点，节点里通常包含 `hash`、`key`、`value`、`next` 等信息：

```text
bucket[index] -> Node(hash, key, value, next)
```

  如果多个 key 落到同一个桶，就会发生哈希冲突，例如：

```text
bucket[2] -> Node(hashA, keyA, valueA)
          -> Node(hashB, keyB, valueB)
          -> Node(hashC, keyC, valueC)
```

  这时不能只靠桶下标，也不能只返回桶里的第一个 value，而是要在桶内继续比较 key。比较逻辑通常是先看节点 hash 是否相同，再用 `==` 或 `equals()` 判断 key 是否真的相等，可以理解成 `node.hash == hash && (node.key == searchKey || searchKey.equals(node.key))`。所以作为 `HashMap` key 的对象要正确重写 `equals()` 和 `hashCode()`。

- **HashMap 容量和负载因子**：`HashMap` 里两个重要概念是 `capacity` 和 `loadFactor`。`capacity` 表示桶数组容量，`loadFactor` 表示负载因子，默认负载因子常见是 `0.75`。元素数量超过 `capacity * loadFactor` 后，会触发扩容和重新分布节点。负载因子是在时间和空间之间做权衡：负载因子高会相对省空间，但桶内冲突概率可能增加；负载因子低会减少冲突，但桶数组会占用更多空间。

- **二叉树**：二叉树的核心是“每个节点最多两个子节点”。普通二叉树只是结构，不一定有查找效率；和集合关系更密切的是二叉查找树，它满足“左子树 < 根节点 < 右子树”。如果树是平衡的，查找过程类似二分，每次能排除一部分数据，接近 `O(log n)`；但如果树退化成一条链，例如 `1 -> 2 -> 3 -> 4`，查找就会退化成 `O(n)`。所以实际集合里不会直接依赖普通二叉查找树，而是使用更稳定的平衡树结构。

- **红黑树**：红黑树是一种自平衡二叉查找树，核心是通过颜色和旋转让树大致保持平衡。它不是完全平衡树，但能保证高度不会太离谱，所以查找、插入、删除都能稳定在 `O(log n)` 级别。`TreeMap`、`TreeSet` 和 JDK 8 以后 `HashMap` 桶内链表树化都和红黑树有关。可以这样理解：`HashMap` 追求平均 `O(1)`，但不保证有序；`TreeMap` 牺牲一点平均速度，换来 key 有序和稳定 `O(log n)`。`TreeSet` 底层通常也是基于 `TreeMap` 思路，元素是否重复不是看 hash，而是看比较结果是否为 `0`。

- **堆**：堆通常用数组实现，但逻辑上可以看成一棵完全二叉树。小顶堆的特点是父节点小于等于子节点，所以堆顶永远是优先级最高或最小的元素。`PriorityQueue` 底层常见就是堆结构，它不是普通 FIFO 队列，而是按自然排序或比较器决定出队顺序。`offer()`、`poll()` 这类入队出队操作通常是 `O(log n)`，`peek()` 查看队头通常是 `O(1)`。

- 常见命名也能辅助判断底层：`ArrayXxx` 往往和数组相关，`LinkedXxx` 往往和链表相关，`HashXxx` 往往和哈希表相关，`TreeXxx` 往往和排序树相关。选择时可以简单记：`HashMap` 适合按 key 快速找，`TreeMap` 适合按 key 有序，`PriorityQueue` 适合每次取优先级最高或最低的元素，`ArrayList` 适合按下标快，`LinkedList` 更适合双端队列或已知节点附近改动。

<a id="list"></a>
###### List

- `List` 表示有序且可重复的元素集合，顺序通常是插入顺序。它支持按索引访问，`get(index)`、`set(index, value)` 是 List 的典型能力。`contains()`、`indexOf()` 等方法判断元素相等时使用 `equals()`，不是 `==`，所以自定义对象如果需要查找，通常要正确重写 `equals()`。
- `ArrayList` 底层是动态数组，适合按下标随机访问、尾部追加、作为 RecyclerView/Adapter 数据源。无参构造时通常先使用空数组，第一次添加元素时扩容到默认容量；后续容量不足时常见扩容约为原容量的 1.5 倍，扩容需要创建新数组并复制旧元素。已知数据量较大时，可以预估初始容量或调用 `ensureCapacity()` 减少扩容次数。
- `ArrayList` 的短板是中间插入和删除，因为元素需要移动。尾部追加通常比较快，但如果触发扩容，也会有数组复制成本。它不是线程安全集合，多线程共享写入时需要额外同步或选择并发集合。
- `LinkedList` 底层是双向链表，既实现 `List`，也实现 `Deque`。它按下标访问慢，因为需要从头或尾逐步移动；在已知节点附近插入删除更灵活，但日常开发中不应简单认为“增删多就一定选 LinkedList”，因为查找节点和对象分配也有成本。
- `Vector` 底层也是数组，但很多方法带 `synchronized`，属于较老的线程安全 List。它可以配置 `capacityIncrement` 增长因子；没有历史兼容要求时，通常优先使用 `ArrayList` 或并发集合，而不是 `Vector`。
- `Arrays.asList()` 返回的是固定长度 List，背后和原数组关联，可以 `set()` 修改元素，但不能 `add()` 或 `remove()`。传入基本类型数组时要特别小心，比如 `Arrays.asList(new int[]{1, 2, 3})` 得到的是一个只包含 `int[]` 的 List，而不是三个 `Integer`。
- `subList()` 返回的是原 List 的视图，不是独立新集合。修改 `subList()` 会影响原 List；原 List 发生结构性修改后继续使用旧 `subList()` 可能抛异常。需要独立集合时使用 `new ArrayList<>(list.subList(...))`。

<a id="set"></a>
###### Set

- `Set` 表示不允许重复元素的集合，不支持按下标访问，通常使用迭代器或增强 for 遍历。重复元素的判断规则取决于具体实现：哈希类 Set 依赖 `hashCode()` 和 `equals()`，排序类 Set 依赖比较结果。
- `HashSet` 底层通常基于 `HashMap`，元素作为 `HashMap` 的 key 保存，value 使用固定占位对象。它不保证遍历顺序，判断唯一性依赖元素的 `hashCode()` 和 `equals()`，所以自定义对象放入 `HashSet` 时必须正确重写这两个方法。
- `LinkedHashSet` 可以理解为 HashSet 加上插入顺序维护。它既通过哈希表保证唯一性，又通过链表维护迭代顺序。这里的有序指“按插入顺序遍历”，不是完整队列语义。
- `TreeSet` 底层常见是红黑树，元素唯一且有序。有序来自元素的自然排序 `Comparable` 或创建集合时传入的 `Comparator`。它判断重复的核心是比较结果是否为 `0`，所以比较器和 `equals()` 不一致时，去重行为可能和直觉不同。
- `HashSet`、`LinkedHashSet`、`TreeSet` 都不是线程安全的。需要线程安全 Set 时，可以考虑 `Collections.synchronizedSet()` 或使用并发集合方案。
- `HashSet`、`LinkedHashSet` 通常允许一个 `null`。`TreeSet` 使用自然排序时通常不允许放入 `null`；如果自定义比较器能处理 `null`，行为取决于比较器实现。

<a id="map"></a>
###### Map

- `Map` 保存 key-value 映射，key 唯一，value 可以重复。相同 key 再次 `put()` 会替换旧 value。Map 适合按 key 快速定位 value，例如按 id 查对象、按业务 key 做缓存、组装请求参数等。
- `HashMap` 是最常用 Map，JDK 8 以后常见说法是数组 + 链表 + 红黑树，更准确是“桶数组 + 节点；冲突少时桶内节点用链表串起来，冲突严重且满足条件时桶内链表可能树化为红黑树”。链表和红黑树里保存的都不是单独 value，而是包含 `hash`、`key`、`value`、`next` 等信息的节点；树节点还会额外保存 `parent`、`left`、`right`、颜色等树结构信息。put 时先计算 key 的 hash，再定位桶位；如果桶位为空直接放入节点，如果发生冲突，就在桶内继续比较 key，相同 key 替换 value，不同 key 追加到链表或树里。
- `HashMap` 允许一个 `null` key 和多个 `null` value，不是线程安全的。默认负载因子常见是 `0.75`，用于平衡空间占用和查询效率。容量通常保持为 2 的幂，这样可以用 `hash & (n - 1)` 快速定位桶位，也便于扩容后重新分布。
- `HashMap` 扩容发生在元素数量超过阈值时，阈值通常是容量乘以负载因子。扩容会创建更大的数组并重新分布节点，成本较高，所以已知数据量较大时应该合理设置初始容量。JDK 8 常见说法是桶内链表节点达到 `8` 且数组容量至少 `64` 时可能树化，否则可能优先扩容；节点减少到一定程度后可能退化为链表。
- `HashMap` 的 key 要求非常重要：如果两个对象 `equals()` 为 true，它们的 `hashCode()` 必须相同；hash 相同不代表对象一定相等，因为哈希冲突允许存在。自定义对象作为 key 时，`equals()` 用到的字段通常也应该参与 `hashCode()` 计算，而且这些字段放入 Map 后不应该再随意修改。
- `Hashtable` 是较老的同步 Map，底层也属于哈希表结构，通常可以理解为数组 + 链表；它没有 JDK 8 `HashMap` 那种桶内红黑树优化。`Hashtable` 很多方法使用 `synchronized`，不允许 `null` key 和 `null` value。它继承自 `Dictionary`，`HashMap` 继承自 `AbstractMap`。没有历史兼容要求时，通常不优先使用 `Hashtable`。
- `ConcurrentHashMap` 是并发场景常用 Map，支持多线程并发访问，但线程安全不代表多个业务操作自动原子。它不允许 `null` key 和 `null` value，一个重要原因是避免并发场景下无法区分“没有这个 key”和“这个 key 对应的 value 是 null”。
- `LinkedHashMap` 在 HashMap 能力基础上维护链表顺序，可以按插入顺序迭代，也可以使用访问顺序模式实现简单 LRU 缓存。Android 或 Java 中做小型内存缓存时，经常能看到它的思路。
- `TreeMap` 按 key 排序，底层常见是红黑树。key 必须可比较：要么 key 自身实现 `Comparable`，要么创建 `TreeMap` 时传入 `Comparator`。它适合需要按 key 自然顺序或自定义顺序遍历的场景，对 value 没有排序要求。
- `Properties` 是特殊的键值配置类，常用于读取 `.properties` 配置，常用方法有 `load()`、`getProperty()`、`setProperty()`。`WeakHashMap` 的 key 是弱引用，key 没有强引用时可能被 GC 回收；`IdentityHashMap` 使用 `==` 比较 key；`EnumMap` 的 key 必须是枚举类型，适合枚举到值的高效映射。

<a id="queue"></a>
###### Queue

- `Queue` 表示队列，常见语义是先进先出。`offer()` 用于添加元素，失败时通常返回 `false`；`poll()` 取出并删除队头元素，队列为空时返回 `null`；`peek()` 查看队头元素但不删除。
- `Deque` 是双端队列，可以从队头和队尾插入、删除。`ArrayDeque` 是常用双端队列实现，通常比 `LinkedList` 更适合作为栈或普通队列，因为它基于数组循环结构，局部性更好，节点对象开销更少。
- `PriorityQueue` 是优先级队列，不保证 FIFO，而是根据自然排序或比较器决定出队顺序。它适合按优先级取任务、取最小/最大元素等场景。
- `BlockingQueue` 属于并发包里的阻塞队列，适合生产者-消费者模型。它更偏并发专题，这里只作为集合使用场景入口。

<a id="iterator"></a>
###### Iterator

- `Iterator` 是统一遍历模型，调用方不需要知道集合底层是数组、链表、哈希表还是树。集合返回的 Iterator 负责按自己的结构遍历元素。
- 增强 for 底层通常也是迭代器模型。遍历集合时如果需要删除当前元素，应优先使用 `Iterator.remove()`，而不是直接调用集合自己的 `remove()`，否则可能触发 `ConcurrentModificationException`。
- `ConcurrentModificationException` 体现的是 fail-fast 机制：集合发现遍历期间结构被非预期修改，就尽早失败，帮助暴露问题。fail-fast 不是线程安全保证，也不保证所有并发修改都一定能被检测到。

<a id="collections-工具类"></a>
###### Collections 工具类

- `Collections.emptyList()`、`emptySet()`、`emptyMap()` 创建不可变空集合；`singletonList()`、`singleton()`、`singletonMap()` 创建不可变单元素集合。这些适合返回空结果或固定单值结果，避免不必要的可变集合创建。
- `Collections.unmodifiableList()`、`unmodifiableSet()`、`unmodifiableMap()` 会把已有集合包装成不可变视图。注意它不是深拷贝，原始集合如果被修改，不可变视图看到的数据也会变化。
- `Collections.synchronizedList()`、`synchronizedSet()`、`synchronizedMap()` 可以给普通集合加同步包装，但通常是粗粒度同步；迭代时往往还需要外部手动同步。并发高的 Map 场景优先考虑 `ConcurrentHashMap`。
- `Collections.sort(list)` 可以排序，要求元素可比较或传入比较器；`Collections.shuffle(list)` 可以打乱顺序，常用于随机展示、测试数据等场景。
- `List.of()`、`Set.of()`、`Map.of()` 是 Java 9+ 的不可变集合工厂方法，创建结果不可变，且不允许 `null` 元素或 key/value。Android 项目使用时要注意 Java 版本和脱糖支持情况。

<a id="排序和比较"></a>
###### 排序和比较

- `Comparable` 表示对象自身具备自然排序能力，实现 `compareTo()`；`Comparator` 表示外部比较器，可以在不修改类本身的情况下定义排序规则。
- `TreeSet`、`TreeMap` 默认依赖自然排序，也可以传入 `Comparator`。比较结果小于 0、等于 0、大于 0 分别表示小于、相等、大于。
- `TreeSet` / `TreeMap` 中比较结果为 `0` 会被认为是同一个元素或同一个 key。为了减少歧义，`compareTo()` / `Comparator` 的相等逻辑最好和 `equals()` 保持一致。
- 排序字段如果可能为 `null`，比较器里要显式处理空值，例如使用 `Comparator.nullsFirst()` 或 `Comparator.nullsLast()`。

<a id="android-常见集合"></a>
###### Android 常见集合

- `SparseArray` 是 Android 提供的 int 到对象映射结构，可以避免 `HashMap<Integer, T>` 中 Integer 装箱带来的额外对象开销，适合小规模 int key 映射。
- `LongSparseArray` 是 long 到对象的映射结构，适合用 long id 做 key 的小规模映射，例如本地对象索引、缓存映射。
- `ArrayMap` 是 Android 提供的轻量 Map，适合小数据量 key-value 映射。数据量很大或频繁修改时，不一定比 `HashMap` 更合适。
- `LruCache` 适合做内存缓存，例如图片、解析结果、临时对象缓存。它会按最近最少使用策略淘汰旧数据，避免缓存无限增长。
- `CopyOnWriteArrayList` 适合读多写少的并发列表场景。它写入时会复制数组，读操作无锁且稳定，但写入频繁时成本很高。

<a id="时间复杂度和空间复杂度"></a>
###### 时间复杂度和空间复杂度

- 时间复杂度描述的是数据量变大时操作成本的增长趋势，不是某一次运行的绝对耗时。集合复杂度通常要结合底层结构理解：数组适合按下标访问，链表适合已知节点附近插入删除，哈希表适合按 key 快速定位，红黑树适合有序查找，堆适合优先级出队。
- 空间复杂度通常都是 `O(n)`，因为集合要保存 `n` 个元素。实际内存开销还要看额外结构：数组有预留容量和扩容复制成本，链表节点有前后引用，哈希表有桶数组和节点，红黑树节点有父子引用和颜色信息，`LinkedHashMap` 还要额外维护链表顺序。
- “均摊 `O(1)`”表示大多数情况下是 `O(1)`，但偶尔会有更贵的操作。例如 `ArrayList` 尾部添加多数时候很快，但触发扩容时要复制旧数组；把扩容成本分摊到多次添加后，平均看仍接近 `O(1)`。
- 哈希类集合的 `O(1)`通常指平均情况，前提是 hash 分布比较均匀。发生大量哈希冲突时，桶内需要继续查找；JDK 8 以后 `HashMap` 在满足条件时会把长链表树化为红黑树，把桶内查找从链表的 `O(n)` 改善到接近 `O(log n)`。

| 集合 / 结构 | 查找 / 访问 | 添加 | 删除 | 空间特点 | 适合理解方式 |
|---|---:|---:|---:|---|---|
| `ArrayList` | 按索引 `O(1)`，按值查找 `O(n)` | 尾部均摊 `O(1)`，中间插入 `O(n)` | 中间删除 `O(n)` | 连续数组空间，可能有预留容量，扩容时需要新数组和复制 | 适合随机访问、尾部追加、页面列表数据源 |
| `LinkedList` | 按索引或按值查找 `O(n)` | 已知节点附近 `O(1)`，按索引插入通常 `O(n)` | 已知节点 `O(1)`，按值删除通常 `O(n)` | 每个节点额外保存前后引用，对象数量更多 | 不要简单认为“增删多就一定快”，关键看是否已经定位到节点 |
| `HashMap` | 平均 `O(1)`，冲突严重时链表 `O(n)`，树化后接近 `O(log n)` | 平均 `O(1)`，扩容时成本较高 | 平均 `O(1)` | 桶数组 + 节点，负载因子影响空间和冲突概率 | 适合按 key 快速查找 value |
| `HashSet` | 平均 `O(1)` | 平均 `O(1)` | 平均 `O(1)` | 通常基于 `HashMap`，元素作为 key 保存 | 适合去重和快速存在性判断 |
| `LinkedHashMap` / `LinkedHashSet` | 平均 `O(1)` | 平均 `O(1)` | 平均 `O(1)` | 比哈希表多维护链表顺序 | 适合既要哈希查找，又要稳定遍历顺序 |
| `TreeMap` / `TreeSet` | `O(log n)` | `O(log n)` | `O(log n)` | 红黑树节点有额外指针和颜色信息 | 适合按排序顺序遍历和范围查找 |
| `PriorityQueue` | 查看队头 `O(1)`，查找普通元素 `O(n)` | `O(log n)` | 删除队头 `O(log n)`，删除普通元素 `O(n)` | 底层通常是数组形式的堆 | 适合每次取优先级最高或最低的元素 |
| `ArrayDeque` | 查找普通元素 `O(n)` | 两端添加均摊 `O(1)` | 两端删除均摊 `O(1)` | 循环数组，扩容时需要复制 | 适合栈、队列、双端队列，通常比 `LinkedList` 更适合做队列 |
| `CopyOnWriteArrayList` | 按索引 `O(1)`，遍历 `O(n)` | `O(n)` | `O(n)` | 写入时复制整个数组 | 适合读多写少，不适合频繁写入 |

- 选择集合时不要只背复杂度，还要看访问模式。比如只看删除，`LinkedList` 好像更快，但如果每次删除前都要先查找目标元素，整体仍然可能是 `O(n)`；`ArrayList` 虽然中间删除要移动元素，但内存连续、局部性好，实际开发中经常更常用。
- 面试中回答复杂度时，最好带上前提条件。例如 `HashMap` 是平均 `O(1)`，不是任何情况下都绝对 `O(1)`；`ArrayList` 尾部添加是均摊 `O(1)`，不是每一次都一定 `O(1)`；`TreeMap` 的 `O(log n)`来自红黑树保持相对平衡。

<a id="选择建议"></a>
###### 选择建议

- 默认需要列表数据时优先考虑 `ArrayList`；需要唯一性时考虑 `HashSet`；需要 key-value 映射时考虑 `HashMap`。这是日常开发最常见的三类选择。
- 需要保留插入顺序时，Set 选 `LinkedHashSet`，Map 选 `LinkedHashMap`；需要按排序顺序遍历时，Set 选 `TreeSet`，Map 选 `TreeMap`。
- 需要队列或栈语义时优先考虑 `ArrayDeque`；需要优先级出队时考虑 `PriorityQueue`；生产者-消费者模型考虑 `BlockingQueue`。
- 多线程共享读写 Map 时优先考虑 `ConcurrentHashMap`，不要直接用 `HashMap`。读多写少并且需要线程安全 List 时可以考虑 `CopyOnWriteArrayList`，但写入频繁不适合。
- Android 小规模 int/long key 映射可以考虑 `SparseArray` / `LongSparseArray`，小规模 Map 可以考虑 `ArrayMap`，内存缓存可以考虑 `LruCache`。
- `Hashtable`、`Vector` 属于历史类，除非维护旧代码或兼容历史 API，一般不作为优先选择。

<a id="常见坑"></a>
###### 常见坑

- `Set` 的不重复不是“重复元素覆盖旧元素”，重复添加通常失败；`Map` 相同 key 才会替换旧 value。
- `HashSet` 不保证遍历顺序，即使某次输出看起来稳定，也不要依赖这个顺序；需要稳定插入顺序时使用 `LinkedHashSet`。
- `TreeSet` / `TreeMap` 的唯一性和排序都依赖比较规则，比较结果为 `0` 会被认为重复；如果比较器和 `equals()` 不一致，去重和查找结果可能不符合直觉。
- `HashMap` 的 key 如果参与 hash 的字段被修改，后续可能查不到这个 key，因为它还留在旧 hash 对应的桶位中。
- `Arrays.asList()` 得到的是固定长度 List，不能直接添加或删除；`subList()` 是视图，不是独立拷贝，使用时要小心原 List 的结构性修改。
- 遍历集合时直接删除元素可能触发 `ConcurrentModificationException`；fail-fast 只是尽早发现问题，不是线程安全保证。
- 不可变集合不能添加、删除、修改元素，调用修改方法会抛出异常；`Collections.unmodifiableList()` 是不可变视图，不是对原集合的隔离副本。
- `ConcurrentHashMap` 线程安全不代表多个操作组合起来一定原子，例如“先判断不存在再 put”仍需要使用 `putIfAbsent()` 这类原子方法。
