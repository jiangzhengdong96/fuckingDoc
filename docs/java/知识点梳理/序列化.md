### Java 序列化知识点清单

###### 内容概述

本文件记录 Java 序列化相关知识点，包括序列化基础、`Serializable`、`transient`、`serialVersionUID`、自定义序列化、反序列化兼容性、`Parcelable` 对比、Android 使用场景和常见坑，以及关联面试题。

###### 使用场景

- Java 原生序列化可用于把对象写入文件、缓存或通过对象流传输，但不适合直接作为跨语言网络协议。
- Android 页面跳转、进程间传递和保存状态经常遇到对象传递问题，`Parcelable` 比 `Serializable` 更常见。
- 本地持久化、网络传输、日志上传、缓存结构需要关注数据格式兼容、安全和版本演进。
- JSON、Protocol Buffers、Parcelable、Serializable 都属于“对象和数据之间转换”的相关能力，但适用场景不同。

<a id="序列化基础"></a>
###### 序列化基础

- 序列化是把对象状态转换成可保存或传输的数据形式，例如二进制字节、JSON 字符串、Protocol Buffers 数据等；反序列化是把这些数据重新还原成对象。
- Java 原生序列化通常指 `ObjectOutputStream` / `ObjectInputStream` 配合 `Serializable` 把对象写成二进制流，再从二进制流恢复对象。
- 序列化保存的是对象的实例状态，不是类定义本身。反序列化时仍然需要本地有对应的 class，否则可能抛出 `ClassNotFoundException`。
- Java 原生对象流可以处理对象图。对象字段里引用的其他对象也会被一起处理，前提是这些对象也能序列化；重复引用和循环引用由对象流内部句柄机制处理。
- 序列化不等于深拷贝工具。虽然可以通过“序列化再反序列化”得到新对象图，但性能、兼容性和安全成本都较高，日常不推荐这样做。
- 网络 JSON 转对象属于数据编解码场景，和 Java 原生序列化不是一回事。网络接口一般优先使用 JSON、Protocol Buffers 等明确协议格式，而不是直接传 Java 原生序列化字节。

<a id="serializable"></a>
###### Serializable

- `Serializable` 是一个标记接口，没有需要实现的方法。一个类实现它，表示这个类允许被 Java 原生序列化机制处理。

```java
public class User implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private int age;
}
```

- 如果对象的某个非 `transient` 字段引用了不可序列化对象，序列化时可能抛出 `NotSerializableException`。
- `static` 字段属于类，不属于单个对象实例状态，默认不会作为对象内容被序列化。
- `final` 字段可以被序列化，但反序列化和版本兼容时要更谨慎，尤其是字段类型变化、构造逻辑变化时。
- Java 原生序列化使用方便，但二进制格式不直观、性能一般、版本兼容复杂，也存在反序列化安全风险。

<a id="transient"></a>
###### transient

- `transient` 用于修饰字段，表示该字段不参与 Java 原生序列化。

```java
public class Session implements Serializable {
    private static final long serialVersionUID = 1L;

    private String token;
    private transient String password;
}
```

- 反序列化后，`transient` 字段会恢复为类型默认值，例如对象引用为 `null`、`int` 为 `0`、`boolean` 为 `false`。
- 常见适用场景：密码、临时缓存、运行期上下文、线程对象、文件句柄、数据库连接、Socket、不能或不应该持久化的敏感字段。
- `transient` 只影响 Java 原生序列化，不一定影响 JSON、Room、Parcelable 等其他序列化或映射框架。不同框架有自己的忽略字段方式，例如 `@Transient`、`@IgnoredOnParcel`、`transient` 支持情况也不完全一样。

<a id="serialversionuid"></a>
###### serialVersionUID

- `serialVersionUID` 是序列化版本号，用来判断序列化数据和当前类定义是否兼容。

```java
private static final long serialVersionUID = 2709425275741743919L;
```

- 如果没有显式声明，JVM 会根据类结构自动计算一个值。类名、字段、方法、修饰符等变化都可能影响计算结果，导致反序列化旧数据时抛出 `InvalidClassException`。
- 建议需要持久化或跨版本传输的 `Serializable` 类显式声明 `serialVersionUID`，避免普通代码改动导致版本号意外变化。
- `serialVersionUID` 相同不代表一定兼容。它只是允许反序列化继续尝试，真正能否正确还原还取决于字段新增、删除、类型变化、类层级变化等。
- 常见兼容情况：新增字段时旧数据没有该字段，反序列化后使用默认值；删除字段时旧数据里的多余字段通常被忽略；字段类型变化通常不兼容。

<a id="自定义序列化"></a>
###### 自定义序列化

- Java 原生序列化可以通过私有方法定制序列化过程：

```java
private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject();
}

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
}
```

- `writeObject()` 可以在写入对象时额外处理字段，例如加密敏感字段、压缩数据、写入派生状态。
- `readObject()` 可以在读取对象后恢复 `transient` 字段、校验数据合法性、重建缓存或运行期对象。
- `writeReplace()` 和 `readResolve()` 可以在序列化或反序列化过程中替换对象，常见于代理对象、单例对象兼容等场景。
- `Externalizable` 提供完全手写读写逻辑的方式，但要求 public 无参构造方法，使用复杂度更高。普通场景优先理解 `Serializable` 和自定义 `writeObject` / `readObject`。

<a id="反序列化和兼容性"></a>
###### 反序列化和兼容性

- 反序列化 `Serializable` 对象时，对象自身的普通构造方法不会像 `new` 一样执行。对于第一个不可序列化父类，反序列化过程会调用它的无参构造方法。
- 常见异常：

| 异常 | 常见原因 |
|---|---|
| `ClassNotFoundException` | 本地找不到序列化数据对应的类 |
| `InvalidClassException` | `serialVersionUID` 不匹配或类定义不兼容 |
| `NotSerializableException` | 某个对象或字段引用的对象没有实现 `Serializable` |
| `OptionalDataException` | 对象流中数据类型或顺序不符合预期 |
| `StreamCorruptedException` | 序列化流损坏或不是合法对象流 |

- 不要反序列化不可信来源的数据。Java 原生反序列化历史上存在很多安全风险，攻击者可能构造恶意对象流触发危险代码路径。
- 持久化到本地的对象流要考虑 App 升级后的兼容性。类名、包名、字段类型、继承层级变化都可能导致旧数据无法读取。
- 长期存储和跨端协议更推荐使用稳定数据格式，例如 JSON、Protocol Buffers、数据库表结构或手写版本迁移逻辑。

<a id="parcelable-对比"></a>
###### Parcelable 对比

- `Parcelable` 是 Android 提供的对象扁平化机制，主要用于进程内或跨进程的高效数据传递，例如 `Intent`、`Bundle`、Binder IPC。
- `Serializable` 使用简单，只要实现标记接口即可；`Parcelable` 需要明确写入和读取字段，代码量更多，但在 Android 组件传递中通常性能更好、控制更明确。
- Kotlin / Android 可以用 `@Parcelize` 减少 `Parcelable` 模板代码，但仍然要理解哪些字段会被写入、哪些字段需要忽略。
- `Parcel` 不是通用持久化格式，不适合长期保存到文件或作为网络协议。它主要服务 Android 运行时对象传递。
- `Parcelable` 字段读写顺序必须一致，否则反序列化出来的数据会错位或崩溃。

<a id="android-使用场景和注意点"></a>
###### Android 使用场景和注意点

- Activity / Fragment 参数传递时，小对象可以通过 `Parcelable` 或 `Serializable` 放进 `Bundle` / `Intent`，但大对象不建议直接传，容易增加内存和 Binder 传输压力。
- Binder 单次事务大小有限，大对象、图片、列表等不要直接塞进 Intent。更合适的方式是传 id、uri、文件路径或通过共享缓存/数据库读取。
- 页面状态恢复应保存最小必要状态，不要把复杂对象图直接序列化进 `savedInstanceState`。
- 如果对象只是网络数据模型，通常不需要实现 Java 原生 `Serializable`。网络层使用 JSON / Protobuf，页面传递使用 `Parcelable`，本地存储使用数据库或 DataStore。
- Android 中 `Serializable` 反射和对象流开销更大，频繁页面跳转或列表数据传递优先考虑 `Parcelable` 或只传关键 id。

<a id="常见坑"></a>
###### 常见坑

- 以为实现 `Serializable` 就能序列化所有字段。实际字段引用的对象也要可序列化，否则可能抛出 `NotSerializableException`。
- 忘记显式声明 `serialVersionUID`，类结构小改动后旧数据无法反序列化。
- 把密码、token、运行期上下文等敏感或临时字段也序列化出去，应该使用 `transient` 或框架对应忽略机制。
- 把 Java 原生序列化当成网络协议或长期存储格式，后续版本兼容和跨语言解析都会很麻烦。
- 在 Android 中通过 Intent 传递大对象，可能造成卡顿、内存压力或 Binder 事务失败。
- 反序列化不可信数据，可能带来安全风险。
- 以为 `Parcelable` 可以长期持久化。`Parcel` 主要用于 Android 运行时传输，不是稳定文件格式。
