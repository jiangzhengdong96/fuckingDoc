### Java 线程知识点清单

###### 内容概述

本文件记录 Java 线程相关知识点，包括线程基础、创建方式、线程状态、线程安全、synchronized、volatile、线程协作、中断、守护线程、Lock 和并发工具、线程池、网络编程和线程、ThreadLocal、Android 使用场景和常见坑，以及关联面试题。

###### 使用场景

- Android 中网络请求、文件读写、数据库操作、图片处理、日志上传和复杂计算不能阻塞主线程。
- 线程池适合管理后台任务，避免频繁创建线程，并控制并发数量。
- 线程安全知识用于处理共享状态、缓存、单例、任务队列、多回调和多线程读写问题。
- 理解线程状态、锁、等待和中断有助于排查 ANR、死锁、任务卡住、CPU 飙高和内存泄漏问题。

<a id="线程基础"></a>
###### 线程基础

- 进程是操作系统进行资源分配的基本单位，线程是 CPU 调度执行的基本单位。一个进程可以包含多个线程，同一进程内的线程共享进程资源，例如堆内存、文件句柄等。
- 多线程的价值是提高响应性和吞吐能力。比如 Android 主线程负责 UI 响应，耗时任务放到后台线程执行，避免主线程被阻塞导致卡顿或 ANR。
- 一个 Java 程序通常运行在一个 JVM 进程里，`main()` 方法由主线程执行；程序内部还可能启动业务线程，JVM 自身也可能有 GC 等后台工作线程。
- 多进程和多线程解决的是不同层面的并发。多进程隔离性更强，一个进程崩溃通常不直接影响另一个进程，但创建和进程间通信成本更高；多线程共享同一进程资源，通信方便但共享状态更容易出错。
- 并发和并行不是同一个概念。并发强调多个任务在同一时间段内交替推进；并行强调多个任务在同一时刻真正同时执行，通常依赖多核 CPU。
- 同步和异步描述的是调用方是否等待结果；多线程描述的是执行载体。异步不一定等于多线程，单线程事件循环也可以实现异步；多线程也不一定天然异步。
- Java 线程由 `Thread` 表示。调用 `start()` 才会启动新线程，JVM 会创建新的执行路径并在合适时机调用 `run()`；直接调用 `run()` 只是普通方法调用，不会创建新线程。
- 一个 `Thread` 对象只能成功 `start()` 一次。线程结束后不能重新启动同一个 `Thread` 对象，需要创建新的线程对象。
- Java 21 引入并正式支持虚拟线程，适合大量阻塞式 I/O 任务的服务端场景。Android 日常开发主要还是平台线程、线程池、Handler、Executor、协程等模型，虚拟线程暂不作为 Android 常规能力。

<a id="线程创建方式"></a>
###### 线程创建方式

- 继承 `Thread` 可以直接重写 `run()`：

```java
Thread thread = new Thread() {
    @Override
    public void run() {
        // do work
    }
};
thread.start();
```

- 实现 `Runnable` 更常见，因为任务和线程本身解耦，任务可以交给 `Thread`、`Executor` 或线程池执行：

```java
Runnable task = () -> {
    // do work
};
new Thread(task).start();
```

- `Callable<V>` 可以返回结果并抛出受检异常，通常配合 `Future<V>` 或线程池使用：

```java
Callable<Integer> task = () -> 1 + 1;
Future<Integer> future = executor.submit(task);
Integer result = future.get();
```

- `Future.get()` 会阻塞当前线程直到结果返回或抛出异常。Android 中不能在主线程直接等待耗时 `Future.get()`，否则容易卡 UI。
- 实际开发中不建议频繁手动 `new Thread()`。更推荐使用线程池、`Executor`、Android 的 `HandlerThread`、`WorkManager`、协程等更可控的任务调度方式。

<a id="线程状态"></a>
###### 线程状态

- Java 线程状态由 `Thread.State` 枚举表示，常见有：

| 状态 | 含义 | 常见进入原因 |
|---|---|---|
| `NEW` | 新建，尚未启动 | 创建 `Thread` 后还没调用 `start()` |
| `RUNNABLE` | 可运行 | 已启动，正在运行或等待 CPU 调度 |
| `BLOCKED` | 阻塞，等待进入同步代码 | 等待获取 `synchronized` 监视器锁 |
| `WAITING` | 无限期等待 | `Object.wait()`、`Thread.join()`、`LockSupport.park()` |
| `TIMED_WAITING` | 限时等待 | `Thread.sleep()`、带超时的 `wait()` / `join()` |
| `TERMINATED` | 已终止 | `run()` 执行完成或异常退出 |

- Java 层的 `RUNNABLE` 同时包含“正在运行”和“就绪等待 CPU 调度”，不要简单把它等同于操作系统层面的 running。
- `BLOCKED` 主要是等待进入 `synchronized` 临界区；`WAITING` / `TIMED_WAITING` 通常是线程主动等待某个条件、时间或其他线程结束。
- 线程状态适合用来辅助定位问题。比如大量线程 `BLOCKED` 可能说明锁竞争严重；大量线程 `WAITING` 可能在等条件、队列或 `join()`；主线程长时间卡住可能导致 Android ANR。

<a id="线程安全"></a>
###### 线程安全

- 线程安全问题通常出现在多个线程共享同一份可变数据时。只读数据、线程局部数据、不可变对象通常更容易保证安全。
- 线程安全常看三个维度：

| 维度 | 含义 | 典型问题 |
|---|---|---|
| 原子性 | 一个操作不可被中途打断 | `i++` 实际是读、改、写三个步骤 |
| 可见性 | 一个线程修改后，其他线程能及时看到 | 一个线程改了标志位，另一个线程一直读到旧值 |
| 有序性 | 程序执行顺序不被错误重排影响 | 双重检查单例需要 `volatile` |

- 解决线程安全可以从几个方向入手：避免共享可变状态、使用不可变对象、把状态限制在线程内部、使用锁、使用 `volatile`、使用原子类、使用并发集合或更高层的并发工具。
- `AtomicInteger`、`AtomicBoolean`、`AtomicReference` 等原子类适合简单原子更新；`ConcurrentHashMap`、`CopyOnWriteArrayList` 等并发集合适合特定读写模式；复杂不变量通常仍需要锁保护。
- 单次引用赋值、读取等简单操作可能本身具备原子性，但这不等于整个业务逻辑线程安全。比如“先判断再修改”“读取多个字段保持一致”仍然可能需要锁、原子类或并发容器。
- 原子性、可见性、有序性要分开看。某个操作是原子的，不代表其他线程一定能及时看到；`volatile` 能解决可见性和部分有序性问题，但不解决复合操作原子性。
- 线程安全不是“所有方法都加锁”这么简单。锁粒度太粗会影响性能，锁对象不统一会失去互斥效果，多个操作组合起来也可能需要整体保护。

<a id="synchronized"></a>
###### synchronized

- `synchronized` 是 Java 内置锁机制，用来保证临界区的互斥访问，并提供可见性和有序性保证。进入同步块需要获取锁，退出同步块会释放锁。
- `synchronized` 锁的是对象监视器，不是代码文本本身。不同写法对应不同锁对象：

| 写法 | 锁对象 |
|---|---|
| 普通同步方法 | 当前实例 `this` |
| 静态同步方法 | 当前类的 `Class` 对象 |
| 同步代码块 | 括号里指定的对象 |

```java
synchronized (lock) {
    count++;
}
```

- 锁对象必须统一。两个线程如果锁的是不同对象，就不能互斥。比如两个实例的普通同步方法锁的是各自的 `this`，它们不会互相阻塞。
- `synchronized` 是可重入锁。同一个线程已经持有某个对象锁时，可以再次进入同一把锁保护的同步代码，不会把自己锁死。
- `synchronized` 能保证临界区内共享变量修改对后续获取同一把锁的线程可见。不要只把它理解成“排队”，它还涉及 Java 内存模型里的可见性。
- 死锁常见于多个线程按不同顺序申请多把锁。减少死锁的思路包括固定加锁顺序、减少锁嵌套、缩小锁范围、使用超时锁或更高层并发工具。

<a id="volatile"></a>
###### volatile

- `volatile` 用来保证变量的可见性，并禁止与该变量相关的一部分重排序。一个线程写入 `volatile` 变量后，其他线程读取同一个变量能看到最新值。
- `volatile` 不保证复合操作的原子性。`i++` 包含读取、加一、写回三个步骤，即使用 `volatile` 修饰，也可能在多线程下丢失更新。
- 适合使用 `volatile` 的典型场景是状态标志、开关变量、单次发布等。例如：

```java
private volatile boolean running = true;

public void stop() {
    running = false;
}
```

- 双重检查单例中，实例字段需要 `volatile`，因为对象创建和引用赋值可能发生重排序；`volatile` 可以避免其他线程看到“引用不为空但对象还没完全初始化”的状态。
- 如果需要“读-改-写”这种复合原子操作，优先考虑 `AtomicInteger`、`AtomicReference` 或锁，而不是只用 `volatile`。

<a id="线程协作"></a>
###### 线程协作

- `wait()`、`notify()`、`notifyAll()` 是 `Object` 上的方法，作用于对象监视器，必须在持有同一个对象锁的同步代码块或同步方法中调用，否则会抛出 `IllegalMonitorStateException`。
- `wait()` 会让当前线程释放对象锁并进入等待；被 `notify()` / `notifyAll()` 唤醒后，线程不会立刻继续执行，而是要重新竞争同一把锁，拿到锁后才从 `wait()` 后面继续执行。
- 等待条件应该用 `while` 循环检查，不要用 `if`：

```java
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }
    // consume ready state
}
```

- 使用 `while` 的原因是可能存在虚假唤醒，也可能被唤醒后条件已经被其他线程改变。线程协作的核心是“等待条件成立”，不是“被通知一次就一定可以继续”。
- `notify()` 只唤醒一个等待线程，`notifyAll()` 唤醒所有等待线程。条件复杂或有多类等待者时，`notifyAll()` 更安全但可能带来更多竞争；`notify()` 更高效但更容易唤醒不合适的线程。
- `sleep()` 是 `Thread` 的静态方法，让当前线程暂停一段时间，不释放已经持有的对象锁；`wait()` 是 `Object` 方法，会释放对应对象锁，常用于线程通信。
- `join()` 表示当前线程等待另一个线程结束。主线程调用子线程的 `join()` 会阻塞主线程，所以 Android 主线程中要谨慎。

<a id="中断机制"></a>
###### 中断机制

- Java 线程中断是一种协作式取消机制，不是强制杀死线程。调用 `interrupt()` 会设置目标线程的中断标记，目标线程需要自己检查并决定如何退出。
- 常见中断相关 API：

| API | 作用 |
|---|---|
| `thread.interrupt()` | 请求中断目标线程 |
| `thread.isInterrupted()` | 查看目标线程中断标记，不清除标记 |
| `Thread.interrupted()` | 查看当前线程中断标记，并清除标记 |

- 如果线程正在 `sleep()`、`wait()`、`join()` 等阻塞方法中，被中断时通常会抛出 `InterruptedException`，并清除中断标记。捕获后要么退出任务，要么重新设置中断标记，避免吞掉取消信号。

```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

- 不推荐使用 `Thread.stop()`、`suspend()`、`resume()` 这类强制控制线程的方法，它们已经过时且不安全，可能破坏对象状态或导致死锁。

<a id="守护线程"></a>
###### 守护线程

- 守护线程也叫 daemon thread，常用于后台辅助任务。JVM 中所有非守护线程结束后，即使还有守护线程在运行，JVM 也可以退出。
- 设置守护线程要在 `start()` 之前调用 `setDaemon(true)`，线程启动后再设置会抛出异常。
- 守护线程不适合承载必须可靠完成的任务，例如写文件、提交订单、上传关键日志等，因为 JVM 退出时不会等待守护线程把任务收尾。
- JVM 的 GC 等后台工作可以理解为守护性质的线程。Android 日常业务开发里通常不需要频繁手动创建守护线程，更常见的是使用线程池、HandlerThread、WorkManager 或协程。

<a id="lock-和并发工具"></a>
###### Lock 和并发工具

- `ReentrantLock` 是 `java.util.concurrent.locks` 包里的可重入锁，可以作为 `synchronized` 的替代方案。它支持显式加锁和解锁、可中断等待、公平锁选项、`tryLock()` 尝试获取锁等能力。
- 使用 `ReentrantLock` 时必须在 `finally` 中释放锁，避免异常导致锁无法释放：

```java
lock.lock();
try {
    // access shared state
} finally {
    lock.unlock();
}
```

- `tryLock()` 可以尝试获取锁，拿不到时立即返回或等待指定时间，适合避免长时间死等。它比单纯进入 `synchronized` 更容易实现超时、降级和失败处理。
- `Condition` 可以配合 `ReentrantLock` 实现类似 `wait()` / `notify()` 的条件等待。一个 `Lock` 可以创建多个 `Condition`，适合把不同等待条件拆开管理。
- `ReadWriteLock` 适合读多写少的场景。没有写操作时允许多个线程同时读；写操作需要独占，写入时其他读写线程都要等待。
- `StampedLock` 在读写锁基础上增加了乐观读能力，读的时候可以先不阻塞写，读取后再校验数据是否被写线程改过。它适合读多写少且读操作很短的场景，但 `StampedLock` 不是可重入锁，使用复杂度更高。
- 悲观锁默认认为共享数据容易被别人修改，所以访问前先加锁，例如 `synchronized`、`ReentrantLock`。乐观锁默认冲突较少，更新时再检查是否被别人改过，CAS 和很多原子类属于这种思路。
- `AtomicInteger`、`AtomicLong`、`AtomicReference` 等原子类通常基于 CAS 思路实现无锁更新，适合计数器、状态标记、引用替换等简单场景。复杂多个变量的一致性仍然可能需要锁。
- `ConcurrentHashMap`、`CopyOnWriteArrayList`、`BlockingQueue` 等并发集合能减少手写同步代码。优先使用标准并发工具，不要轻易自己实现复杂同步容器。
- 并发集合的“线程安全”也有边界。单个方法通常是安全的，但多个方法组合的业务逻辑不一定原子，例如“先 containsKey 再 put”应优先考虑 `putIfAbsent()` 等原子方法。

<a id="线程池"></a>
###### 线程池

- 线程池用于复用线程、控制并发数量、管理任务队列和统一处理任务执行。比频繁创建销毁线程更稳定，也更容易治理资源。
- 常见线程池参数：

| 参数 | 含义 |
|---|---|
| `corePoolSize` | 核心线程数 |
| `maximumPoolSize` | 最大线程数 |
| `keepAliveTime` | 非核心线程空闲存活时间 |
| `workQueue` | 任务队列 |
| `threadFactory` | 线程创建工厂 |
| `handler` | 拒绝策略 |

- 线程池大致执行逻辑：核心线程未满时创建核心线程；核心线程满后任务进入队列；队列满且未到最大线程数时创建非核心线程；仍无法接收任务时触发拒绝策略。
- 常见拒绝策略包括抛异常、调用者线程执行、丢弃当前任务、丢弃队列最旧任务。实际项目中要结合业务设计，不要忽略拒绝策略。
- 不建议盲目使用 `Executors.newCachedThreadPool()` 或 `newFixedThreadPool()`。它们隐藏了队列或最大线程数配置，使用不当可能导致线程数过多或任务堆积。更推荐显式创建 `ThreadPoolExecutor` 并设置合理参数。
- 常见快捷线程池可以用于理解不同任务模型，但实际项目仍要关注它们的隐藏参数：

| 类型 | 特点 | 风险 |
|---|---|---|
| `FixedThreadPool` | 固定线程数量 | 无界队列可能堆积任务 |
| `CachedThreadPool` | 线程数可动态增长 | 突发任务可能创建过多线程 |
| `SingleThreadExecutor` | 单线程串行执行 | 任务慢会阻塞后续任务 |
| `ScheduledThreadPool` | 延迟或周期性执行任务 | 周期任务异常、耗时过长会影响调度 |

- `ScheduledThreadPoolExecutor` 适合定时或周期性任务，例如延迟执行、固定频率刷新、超时检查。Android 中长期可靠后台任务更推荐结合 `WorkManager`，不要仅依赖进程内定时线程。
- `Future` 表示异步任务未来的结果，`Callable` 相比 `Runnable` 可以返回结果并抛出异常。调用 `Future.get()` 会阻塞当前线程，所以不要在 Android 主线程直接等待。
- `ForkJoinPool` 面向可拆分的并行计算，核心思想是把大任务拆成小任务并行执行，再合并结果，任务通常继承 `RecursiveTask` 或 `RecursiveAction`。它更适合 CPU 密集型分治计算，不适合普通 Android 网络请求。
- Android 中线程池要根据任务类型区分：I/O 密集型可以适当多线程，CPU 密集型通常接近 CPU 核数；长期任务可以考虑 `WorkManager`；主线程切换可用 `Handler`、`runOnUiThread`、`LiveData`、协程等。

<a id="网络编程和线程"></a>
###### 网络编程和线程

- 网络编程可以放在线程专题里一起理解，因为经典 Java 网络 API 很多都是阻塞式调用。`Socket.connect()`、`ServerSocket.accept()`、输入流 `read()`、输出流 `write()` 都可能阻塞当前线程。
- 阻塞式网络请求不能放在 Android 主线程。主线程负责 UI 绘制和事件分发，如果同步等待网络连接、DNS、读写响应数据，页面会卡住，严重时会触发 ANR。
- Java 基础里常见网络类包括 `Socket`、`ServerSocket`、`DatagramSocket`、`InetAddress`、`URL`、`HttpURLConnection`。Android 实际业务里更常见的是 OkHttp、Retrofit 这类库，但底层仍然离不开线程调度、I/O 等待和结果回调。
- BIO 网络模型可以简单理解成“一个阻塞连接占用一个执行线程”。服务端常见写法是主线程循环 `accept()`，收到连接后交给线程池处理，避免每个连接都无限制 `new Thread()`。
- 网络任务通常属于 I/O 密集型任务。线程池线程数可以比 CPU 核数稍多，但仍然要限制上限、设置队列和拒绝策略，避免弱网、接口慢、重试过多时任务堆积。
- 网络请求必须设置超时。连接超时、读取超时和整体任务超时都很重要，否则线程可能长时间卡在网络 I/O 上，线程池被占满后会影响后续任务。
- 取消网络任务不能只依赖 `interrupt()`。很多阻塞 I/O 不一定会因为线程中断立刻退出，实际项目中通常要配合关闭 `Socket`、取消 `Call`、设置超时或使用库提供的取消 API。
- 网络响应回来后不要直接假设已经在主线程。同步请求在调用线程返回，异步请求的回调线程取决于库和调度器，更新 UI 前要明确切回主线程。
- 网络连接、输入流、输出流都属于外部资源，用完要关闭。推荐使用 `try-with-resources`，或者在任务取消、异常、超时时做好清理。
- 多线程共享网络对象时要确认线程安全边界。比如同一个连接的读写顺序、共享请求状态、回调列表、缓存对象都可能涉及并发问题，需要串行化、加锁或使用线程安全结构。
- NIO、Selector、Netty 这类模型是为了减少阻塞线程数量、提升大量连接场景下的吞吐能力。Android 应用层一般不需要自己实现复杂 NIO 网络框架，理解“阻塞 I/O 会占线程、非阻塞 I/O 用事件通知减少线程占用”即可。
- 这里的网络编程只讲和线程相关的部分。协议细节放到 `computer-network`，OkHttp、Retrofit、缓存、证书、DNS 等 Android 网络实践放到 `network`。

<a id="threadlocal"></a>
###### ThreadLocal

- `ThreadLocal<T>` 用于给每个线程保存独立变量副本。同一个 `ThreadLocal` 在不同线程中取到的是各自线程绑定的值。
- 常见场景包括线程内上下文、日期格式化对象、链路追踪上下文、数据库事务上下文等。
- 在线程池中使用 `ThreadLocal` 要特别注意清理。线程池线程会复用，如果任务结束后不 `remove()`，后续任务可能读到上一个任务残留数据，也可能造成内存泄漏。

```java
try {
    local.set(value);
    // do work
} finally {
    local.remove();
}
```

- Android 中也要谨慎使用 `ThreadLocal`。如果存入 Activity、View、Context 等生命周期对象，在线程长期存活时可能造成泄漏。

<a id="android-使用场景和注意点"></a>
###### Android 使用场景和注意点

- Android 主线程也叫 UI 线程，负责界面绘制和事件分发。耗时操作不能直接放在主线程，否则会导致卡顿甚至 ANR。
- 子线程不能直接更新 UI。更新 UI 需要切回主线程，例如使用 `Handler(Looper.getMainLooper())`、`Activity.runOnUiThread()`、`View.post()`、LiveData、Flow、协程主线程调度等。
- Android 线程模型常见工具：

| 工具 | 适用场景 |
|---|---|
| `Handler` / `Looper` | 线程消息队列、主线程切换 |
| `HandlerThread` | 带 Looper 的后台线程 |
| `Executor` / 线程池 | 普通后台任务 |
| `WorkManager` | 可延迟、需要可靠执行的后台任务 |
| Kotlin 协程 | 结构化并发、异步任务、线程切换 |

- Android 的异步任务要关注生命周期。Activity/Fragment 销毁后，后台线程回调仍持有页面引用，可能导致崩溃或内存泄漏。应结合生命周期取消任务、弱引用、ViewModel、协程作用域等方式处理。
- 排查 ANR 时，线程知识可以帮助理解主线程是否在等锁、等 I/O、等 Binder、等子线程 `join()` 或执行了耗时计算。

<a id="常见坑"></a>
###### 常见坑

- 直接调用 `run()` 不会启动新线程，只有调用 `start()` 才会创建新执行路径。
- 一个 `Thread` 对象不能重复调用 `start()`。
- `volatile` 不能保证 `i++` 这类复合操作的原子性。
- `wait()`、`notify()`、`notifyAll()` 必须在持有同一对象锁的同步代码中使用。
- `wait()` 要放在 `while` 条件循环中，不要只用 `if`。
- `sleep()` 不释放对象锁，`wait()` 会释放对应对象锁。
- 锁对象不同就不能互斥，普通同步方法和静态同步方法锁的对象也不同。
- `ReentrantLock` 使用后必须释放，通常写在 `finally` 中。
- `StampedLock` 不是可重入锁，不要按 `ReentrantLock` 的习惯嵌套获取。
- 并发集合只能保证自身单个操作安全，业务层复合操作仍然要考虑原子性。
- 线程池任务异常如果没有统一处理，可能悄悄丢失或只在线程日志里出现。
- 线程池中使用 `ThreadLocal` 后不清理，可能导致数据串用或内存泄漏。
- 同步网络请求、Socket 读写、DNS 解析等阻塞操作不能放在 Android 主线程。
- 网络请求要设置超时和取消逻辑，否则线程可能长期阻塞，拖垮线程池。
- Android 子线程不能直接更新 UI，主线程也不能等待耗时任务完成。
