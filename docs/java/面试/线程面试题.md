<a id="start-和-run-有什么区别"></a>
###### start 和 run 有什么区别

答案：

- `start()` 会启动一个新线程，让线程进入可运行状态，由 JVM 调度后执行 `run()`。
- 直接调用 `run()` 只是普通方法调用，仍然在当前线程执行，不会创建新的执行路径。
- 一个 `Thread` 对象只能成功调用一次 `start()`，重复启动会抛出 `IllegalThreadStateException`。
- 面试回答时可以强调：`run()` 是任务内容，`start()` 是启动线程的入口。

关联知识点：[线程基础](../知识点梳理/线程.md#线程基础)

<a id="java-线程有哪些状态"></a>
###### Java 线程有哪些状态

答案：

- Java 线程状态由 `Thread.State` 表示，包含 `NEW`、`RUNNABLE`、`BLOCKED`、`WAITING`、`TIMED_WAITING`、`TERMINATED`。
- `NEW`：线程对象已创建，但还没有调用 `start()`。
- `RUNNABLE`：线程已经启动，正在运行或等待 CPU 调度。Java 层的 `RUNNABLE` 同时包含“就绪”和“运行中”。
- `BLOCKED`：等待进入 `synchronized` 临界区，通常是等待对象监视器锁。
- `WAITING`：无限期等待其他线程触发条件，例如无超时的 `wait()`、`join()`。
- `TIMED_WAITING`：限时等待，例如 `sleep()`、带超时的 `wait()` / `join()`。
- `TERMINATED`：`run()` 执行完成或异常退出。

关联知识点：[线程状态](../知识点梳理/线程.md#线程状态)

<a id="sleep-和-wait-有什么区别"></a>
###### sleep 和 wait 有什么区别

答案：

- `sleep()` 是 `Thread` 的静态方法，表示当前线程暂停一段时间；`wait()` 是 `Object` 的方法，用于对象监视器上的线程协作。
- `sleep()` 不会释放当前线程已经持有的对象锁；`wait()` 会释放调用对象对应的锁。
- `sleep()` 可以在普通代码中调用；`wait()` 必须在持有同一对象锁的 `synchronized` 代码中调用，否则会抛出 `IllegalMonitorStateException`。
- `sleep()` 到时间后会重新进入可运行状态；`wait()` 通常需要 `notify()` / `notifyAll()` 唤醒，或者等待超时版本到期。
- 简单记法：`sleep()` 用于暂停执行，`wait()` 用于线程通信。

关联知识点：[线程协作](../知识点梳理/线程.md#线程协作)

<a id="synchronized-锁的是什么"></a>
###### synchronized 锁的是什么

答案：

- `synchronized` 锁的是对象监视器，不是代码文本本身。
- 普通同步方法锁当前实例，也就是 `this`。
- 静态同步方法锁当前类的 `Class` 对象。
- 同步代码块锁括号里指定的对象。
- 锁对象必须一致才有互斥效果。如果两个线程进入的是同一段同步逻辑，但锁对象不同，就不能保证线程安全。
- `synchronized` 还提供可见性和有序性保证：一个线程退出同步块前对共享变量的修改，对后续获取同一把锁的线程可见。

关联知识点：[synchronized](../知识点梳理/线程.md#synchronized)

<a id="volatile-能保证原子性吗"></a>
###### volatile 能保证原子性吗

答案：

- 不能。`volatile` 主要保证可见性，并禁止和该变量相关的一部分指令重排序。
- `i++` 这类复合操作不是原子操作，它包含读取、加一、写回三个步骤。即使用 `volatile` 修饰，多个线程同时执行时也可能丢失更新。
- 如果需要保证复合操作的原子性，可以使用 `synchronized`、`Lock`、`AtomicInteger`、`AtomicReference` 等方式。
- `volatile` 更适合状态标记、开关变量、一次性发布等场景。

关联知识点：[volatile](../知识点梳理/线程.md#volatile)

<a id="wait-为什么要放在-while-循环里"></a>
###### wait 为什么要放在 while 循环里

答案：

- `wait()` 等待的是“条件成立”，不是“被通知一次”。线程被唤醒后必须重新检查条件。
- 使用 `while` 是为了处理虚假唤醒，也为了处理被唤醒后条件又被其他线程改变的情况。
- 如果用 `if`，线程被唤醒后会直接继续执行，可能在条件不满足时消费数据或修改状态，导致并发错误。

```java
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }
    // 条件确认成立后再继续执行
}
```

关联知识点：[线程协作](../知识点梳理/线程.md#线程协作)

<a id="notify-和-notifyall-有什么区别"></a>
###### notify 和 notifyAll 有什么区别

答案：

- `notify()` 只唤醒一个正在该对象监视器上等待的线程，具体唤醒哪个线程不由业务代码直接控制。
- `notifyAll()` 会唤醒所有正在该对象监视器上等待的线程，被唤醒的线程还需要重新竞争锁，并重新判断条件。
- `notify()` 开销较小，但如果存在多类等待条件，可能唤醒不合适的线程，导致某些线程继续等待。
- `notifyAll()` 更稳妥，但会带来更多线程竞争。
- 实际面试中可以这样说：条件简单、等待者单一时 `notify()` 可以使用；条件复杂或不确定时优先考虑 `notifyAll()`，并配合 `while` 检查条件。

关联知识点：[线程协作](../知识点梳理/线程.md#线程协作)

<a id="interrupt-是强制停止线程吗"></a>
###### interrupt 是强制停止线程吗

答案：

- 不是。`interrupt()` 是协作式取消机制，作用是设置目标线程的中断标记。
- 目标线程需要自己检查中断状态，并决定退出、清理资源或继续执行。
- 如果线程正在 `sleep()`、`wait()`、`join()` 等阻塞方法中，被中断时通常会抛出 `InterruptedException`，并清除中断标记。
- 捕获 `InterruptedException` 后不要直接吞掉。常见处理方式是结束任务，或者调用 `Thread.currentThread().interrupt()` 重新设置中断标记。

```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

关联知识点：[中断机制](../知识点梳理/线程.md#中断机制)

<a id="守护线程是什么"></a>
###### 守护线程是什么

答案：

- 守护线程是后台辅助线程。JVM 中所有非守护线程结束后，即使守护线程还没执行完，JVM 也可以退出。
- 守护线程需要在 `start()` 前调用 `setDaemon(true)` 设置，线程启动后不能再改。
- 它适合辅助性后台工作，不适合必须可靠完成的任务，例如保存文件、提交交易、上传关键数据。
- Android 日常业务里通常不需要手动依赖守护线程，更多会使用线程池、HandlerThread、WorkManager 或协程。

关联知识点：[守护线程](../知识点梳理/线程.md#守护线程)

<a id="synchronized-和-volatile-有什么区别"></a>
###### synchronized 和 volatile 有什么区别

答案：

- `synchronized` 是锁机制，能保证临界区互斥访问，也能保证可见性和有序性。
- `volatile` 是变量可见性机制，能让一个线程对变量的写入及时被其他线程看到，并禁止部分重排序，但不能保证复合操作原子性。
- `synchronized` 适合保护共享可变状态和复合逻辑；`volatile` 适合简单状态标记、开关变量、一次性发布。
- 如果一个操作需要“读-改-写”作为整体完成，通常不能只靠 `volatile`。

关联知识点：[线程安全](../知识点梳理/线程.md#线程安全)

<a id="reentrantlock-和-synchronized-有什么区别"></a>
###### ReentrantLock 和 synchronized 有什么区别

答案：

- `synchronized` 是 Java 内置锁，进入同步块自动加锁，退出同步块自动释放锁，写法简单。
- `ReentrantLock` 是显式锁，需要手动 `lock()` 和 `unlock()`，通常必须在 `finally` 里释放。
- `ReentrantLock` 支持 `tryLock()`、可中断等待、公平锁选项、多个 `Condition` 条件队列等能力，适合需要超时、取消、多个等待条件的复杂场景。
- 普通互斥逻辑优先用 `synchronized` 更简单；需要高级控制能力时再考虑 `ReentrantLock`。

关联知识点：[Lock 和并发工具](../知识点梳理/线程.md#lock-和并发工具)

<a id="readwritelock-和-stampedlock-适合什么场景"></a>
###### ReadWriteLock 和 StampedLock 适合什么场景

答案：

- `ReadWriteLock` 适合读多写少。没有写入时，多个读线程可以并发读取；写入时需要独占，其他读写都要等待。
- `StampedLock` 在读写锁基础上增加乐观读，读取时可以先不阻塞写，读完再校验期间是否发生写入。
- `StampedLock` 更复杂，而且不是可重入锁，不能简单替代所有读写锁。
- 如果只是普通互斥，用 `synchronized` 或 `ReentrantLock`；读多写少并且性能瓶颈明确时，再考虑读写锁或 `StampedLock`。

关联知识点：[Lock 和并发工具](../知识点梳理/线程.md#lock-和并发工具)

<a id="atomic-原子类和-cas-解决什么问题"></a>
###### Atomic 原子类和 CAS 解决什么问题

答案：

- `AtomicInteger`、`AtomicLong`、`AtomicReference` 等原子类用于无锁地完成简单原子更新，例如计数、状态切换、引用替换。
- CAS 可以理解为“比较当前值是否还是预期值，如果是就更新，否则失败重试或走其他逻辑”。
- 原子类适合单变量简单更新，不适合天然维护多个变量之间的复杂不变量。
- 原子类能解决部分原子性问题，但不等于所有并发逻辑都不需要锁。

关联知识点：[Lock 和并发工具](../知识点梳理/线程.md#lock-和并发工具)

<a id="线程池的核心参数有哪些"></a>
###### 线程池的核心参数有哪些

答案：

- `corePoolSize`：核心线程数。
- `maximumPoolSize`：最大线程数。
- `keepAliveTime`：非核心线程空闲后的存活时间。
- `workQueue`：任务队列。
- `threadFactory`：线程创建工厂，可以设置线程名、优先级、异常处理等。
- `handler`：拒绝策略，任务无法接收时如何处理。
- 执行流程可以概括为：核心线程没满先建核心线程；核心线程满了任务进队列；队列满了且没到最大线程数则建非核心线程；仍无法接收时触发拒绝策略。

关联知识点：[线程池](../知识点梳理/线程.md#线程池)

<a id="为什么不建议直接使用-executors-创建线程池"></a>
###### 为什么不建议直接使用 Executors 创建线程池

答案：

- `Executors` 的快捷方法会隐藏关键参数，容易让开发者忽略队列容量、最大线程数和拒绝策略。
- `newFixedThreadPool()` 使用无界队列，任务堆积过多时可能导致内存压力。
- `newCachedThreadPool()` 最大线程数非常大，任务暴涨时可能创建过多线程。
- 更推荐显式创建 `ThreadPoolExecutor`，根据任务类型设置线程数、队列大小、线程名和拒绝策略。
- Android 中还要区分 I/O 密集、CPU 密集、长期可靠后台任务等场景，不要所有任务共用一个无限制线程池。

关联知识点：[线程池](../知识点梳理/线程.md#线程池)

<a id="future-和-forkjoin-是什么"></a>
###### Future 和 ForkJoin 是什么

答案：

- `Future` 表示异步任务未来的结果，常和 `Callable`、线程池一起使用。`Future.get()` 会阻塞当前线程直到任务完成或抛出异常。
- `Callable` 相比 `Runnable` 可以返回结果，也可以抛出受检异常。
- `ForkJoinPool` 面向分治任务，把大任务拆成小任务并行执行，最后合并结果，任务通常继承 `RecursiveTask` 或 `RecursiveAction`。
- Android 开发里不要在主线程调用耗时 `Future.get()`；Fork/Join 更适合 CPU 密集型并行计算，不适合普通网络请求。

关联知识点：[线程池](../知识点梳理/线程.md#线程池)

<a id="bio-网络编程为什么要放到子线程或线程池执行"></a>
###### BIO 网络编程为什么要放到子线程或线程池执行

答案：

- BIO 网络编程是阻塞式模型，`connect()`、`accept()`、`read()`、`write()` 都可能让当前线程等待。
- 如果把同步网络请求放在 Android 主线程，会阻塞 UI 绘制和事件分发，导致卡顿甚至 ANR。
- 服务端或普通 Java 程序里，如果每个连接都直接 `new Thread()`，连接数一多会造成线程过多、上下文切换变重、内存压力变大。
- 更合理的做法是把网络任务交给线程池，并设置线程数上限、任务队列、拒绝策略、超时和取消逻辑。
- 大量长连接或高并发连接场景可以进一步了解 NIO、Selector、Netty 等模型，它们的目标是减少阻塞线程数量。

关联知识点：[网络编程和线程](../知识点梳理/线程.md#网络编程和线程)

<a id="网络请求取消为什么不能只靠-interrupt"></a>
###### 网络请求取消为什么不能只靠 interrupt

答案：

- `interrupt()` 是线程中断标记，不是强制停止线程。它对 `sleep()`、`wait()`、`join()` 这类阻塞方法比较明确，但对很多网络 I/O 不一定能让阻塞立即退出。
- 线程可能卡在 Socket 读写、DNS、连接等待或三方库内部调度中，只设置中断标记不一定足够。
- 实际项目里要配合具体网络 API：关闭 `Socket`、调用 OkHttp `Call.cancel()`、设置连接超时和读取超时、给业务任务设置整体超时。
- 捕获异常后还要做资源清理，避免连接、输入流、输出流泄漏。
- Android 中取消网络任务还要结合生命周期，例如页面销毁时取消请求，避免回调持有 Activity 或 Fragment。

关联知识点：[网络编程和线程](../知识点梳理/线程.md#网络编程和线程)

<a id="threadlocal-有什么用有什么风险"></a>
###### ThreadLocal 有什么用有什么风险

答案：

- `ThreadLocal` 用于给每个线程保存独立变量副本。同一个 `ThreadLocal` 在不同线程中读到的是各自线程绑定的数据。
- 常见用途包括线程内上下文、链路追踪信息、事务上下文、日期格式化对象等。
- 风险主要在线程池场景：线程会复用，如果任务结束后不清理，后续任务可能读到上一个任务残留的数据。
- 另一个风险是内存泄漏，尤其是在 `ThreadLocal` 中保存较大对象或 Android 生命周期对象时。
- 使用建议是：`set()` 后在 `finally` 中调用 `remove()`。

```java
try {
    local.set(value);
    // do work
} finally {
    local.remove();
}
```

关联知识点：[ThreadLocal](../知识点梳理/线程.md#threadlocal)

<a id="android-为什么不能在子线程更新-ui"></a>
###### Android 为什么不能在子线程更新 UI

答案：

- Android 的 UI 绘制和事件分发主要由主线程负责，View 层级不是按多线程同时修改来设计的。
- 如果多个线程同时修改 UI 状态，会带来竞态条件、状态不一致和绘制异常。
- 子线程完成耗时任务后，应切回主线程更新 UI，例如使用 `Handler(Looper.getMainLooper())`、`Activity.runOnUiThread()`、`View.post()`、`LiveData`、`Flow`、协程主线程调度等。
- 反过来，主线程也不能执行耗时任务或长时间等待子线程结果，否则容易卡顿或 ANR。

关联知识点：[Android 使用场景和注意点](../知识点梳理/线程.md#android-使用场景和注意点)

<a id="如何排查线程导致的-anr-或死锁"></a>
###### 如何排查线程导致的 ANR 或死锁

答案：

- 先看主线程状态：是否在等待锁、等待 I/O、等待 Binder、等待 `join()`，或者正在执行耗时计算。
- 如果主线程处于 `BLOCKED`，重点找它在等哪把锁，以及哪条线程持有这把锁。
- 如果多条线程互相持有对方需要的锁，就可能是死锁。排查时关注线程堆栈里的锁对象、等待关系和加锁顺序。
- 如果大量线程堆积在 `WAITING` / `TIMED_WAITING`，要看是否在等队列、条件、网络、数据库、线程池任务结果。
- Android 中可以结合 ANR traces、Logcat、Perfetto、线程 dump、`adb shell dumpsys activity anr` 等信息定位。
- 解决思路通常是：减少主线程耗时、避免主线程等锁或等后台任务、统一加锁顺序、缩小锁范围、给任务设置超时和取消机制。
