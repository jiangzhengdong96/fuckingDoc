<a id="取消与等待结束"></a>
###### 取消与等待结束

| 方法 | 作用 | 返回时保证什么 |
|---|---|---|
| `cancel()` | 发出取消信号 | 不保证协程代码或 finally 已执行完 |
| `join()` | 等待目标 Job 完成 | 等到包括 finally 和子任务在内的完成；不把目标失败作为结果重新抛出 |
| `cancelAndJoin()` | 先取消再等待完成 | 正常返回时目标已结束；调用者自身取消可能让等待抛异常 |
| `Deferred.await()` | 等待结果 | 返回成功结果或抛出失败 / 取消异常 |

```kotlin
suspend fun stopWorker(worker: Job) {
    worker.cancelAndJoin()
    // 正常返回后才能认定 worker 的清理已结束。
}
```

cancelAndJoin 仍依赖目标响应取消；不可取消的死循环或阻塞 API 会使等待迟迟不结束。不要在目标协程内部 join 自己。

<a id="协作式取消与阻塞"></a>
###### 协作式取消与阻塞

```kotlin
suspend fun compute(items: List<Item>): Result = withContext(Dispatchers.Default) {
    val output = mutableListOf<Value>()
    for (item in items) {
        ensureActive()
        output += transform(item)
    }
    Result(output)
}
```

- `isActive`：读状态，适合循环条件；退出后的返回语义由代码决定。
- `ensureActive()`：已取消就抛 CancellationException，不主动让出调度机会。
- `yield()`：检查取消并给其他协程执行机会；不保证切换到另一个线程。
- suspend 函数不一定支持取消；能否取消由实现决定，不是函数名或修饰符保证。
- `withContext(IO)` 只负责调度，不会自动让阻塞 Socket / SDK 调用支持取消。
- JVM 上可中断的阻塞调用可考虑 `runInterruptible(Dispatchers.IO) { blockingCall() }`；前提是 API 正确响应线程中断。其他库应使用其 cancel / close / 注销接口。

<a id="超时参数与边界"></a>
###### 超时参数与边界

| API | 到期行为 | 适用场景 |
|---|---|---|
| `withTimeout(timeMillis)` | 取消块并抛 TimeoutCancellationException | 需要区分超时和成功结果 |
| `withTimeoutOrNull(timeMillis)` | 自己这层超时返回 null | 超时允许降级且 null 语义明确 |

TimeoutCancellationException 是 CancellationException 的子类。withTimeoutOrNull 不会把所有异常变成 null；业务异常仍抛出，外部取消和不是自身产生的超时也继续传播。非正超时时间意味着不执行块中的任务。

```kotlin
suspend fun loadWithFallback(): Data {
    val remote = withTimeoutOrNull(2_000) {
        repository.loadRemote()
    }
    return remote ?: repository.loadCache()
}
```

这里示意远端返回非 null 的 Data，避免混淆“超时”和“接口合法返回 null”。超时依赖协作取消，不是强制杀线程的硬截止时间。超时也不代表服务器没完成写入；重试写操作仍需幂等键或结果查询。

<a id="finally与资源释放"></a>
###### finally 与资源释放

取消时 finally 仍会执行；但 finally 中普通可取消挂起调用可能立即抛取消异常。只有确实必须挂起的有限清理才使用 NonCancellable：

```kotlin
try {
    process()
} finally {
    resource.close() // 非挂起清理通常不需要 NonCancellable
    withContext(NonCancellable) {
        withTimeoutOrNull(1_000) { flushPendingCleanup() }
    }
}
```

清理自身失败仍需明确处理策略，避免掩盖原始失败；上例是边界示意，不要求所有场景同时 close 和 flush。NonCancellable 会延迟父级完成，不能包住长时间业务请求，也不要用 launch(NonCancellable) 把任务从原取消链中分离。清理超时同样只能约束协作式挂起操作。

超时可能在资源刚获取、结果尚未交给调用方时发生。优先在同一作用域内获取、使用、关闭资源，例如 `withTimeout { openResource().use { useResource(it) } }`，避免从超时块返回需要调用方关闭的裸资源。回调返回资源时，还要处理恢复与取消竞态下的资源释放。

<a id="取消信号与旧结果"></a>
###### 取消信号与旧结果

```kotlin
try {
    performRequest()
} catch (e: CancellationException) {
    throw e
} catch (e: IOException) {
    showRecoverableError(e)
}
```

runCatching 会捕获 CancellationException，使用前必须明确重新抛出取消的策略。取消不等于撤销：已经提交的数据库写入、导航或网络副作用不会自动回滚。

切换查询时，旧 Job.cancel 只是一层保护。若旧 SDK 不响应取消，或仍通过独立回调更新状态，还需让回调遵守任务归属，并在提交结果处校验请求版本 / 当前查询；校验与更新必须处于一致的同步边界。
