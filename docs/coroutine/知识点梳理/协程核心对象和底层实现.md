### 协程核心对象和底层实现

###### 内容概述

本文件补充 Kotlin 协程更底层的对象模型和源码理解入口，重点说明 `CoroutineScope`、`CoroutineContext`、`Job`、`CoroutineDispatcher`、`Continuation`、启动方法参数、配置项、作用域级别、状态机和异常取消链路。它不是替代 Android 协程使用文档，而是帮助理解“为什么这样用”和“源码里大概怎么串起来”。

###### 使用场景

- 面试中需要从使用层讲到协程底层原理。
- Code Review 时判断作用域、Dispatcher、Job、异常处理是否配置合理。
- 阅读 kotlinx.coroutines、Lifecycle KTX 或协程反编译代码时建立对象关系。
- 自定义长生命周期任务、注入 Dispatcher、封装回调为挂起函数时避免破坏结构化并发。

<a id="核心对象关系"></a>
###### 核心对象关系

先用一句话串起来：

```text
CoroutineScope
  -> 持有 CoroutineContext
      -> Context 里放 Job / Dispatcher / CoroutineName / CoroutineExceptionHandler 等元素
  -> launch / async / withContext 创建或切换协程
      -> suspend 函数通过 Continuation 挂起和恢复
      -> Dispatcher 决定恢复时投递到哪个线程或队列
      -> Job 记录生命周期、父子关系、取消和异常传播
```

核心对象职责：

| 对象 | 主要职责 | Android 中怎么理解 |
|---|---|---|
| `CoroutineScope` | 协程启动入口，规定新协程归属于谁 | `viewModelScope` 表示任务归 ViewModel 管，`lifecycleScope` 表示任务归 Lifecycle 管 |
| `CoroutineContext` | 类似协程配置集合，按 key 保存元素 | `Job + Dispatchers.Main + CoroutineName + CoroutineExceptionHandler` 这类组合 |
| `Job` | 协程生命周期和父子关系 | 页面结束、ViewModel 清理、父任务失败时通过 Job 取消任务树 |
| `CoroutineDispatcher` | 决定协程代码在哪类线程执行或恢复 | `Main` 更新 UI，`IO` 做阻塞 IO，`Default` 做 CPU 计算 |
| `Continuation` | 挂起函数的“恢复点” | suspend 函数挂起后，结果回来时通过 continuation 继续执行下一行 |
| `Deferred<T>` | 带结果的 `Job` | `async` 返回它，`await()` 取结果并暴露异常 |

常见源码实现名可以作为阅读线索，但业务代码不要依赖它们：

| 源码/内部类线索 | 大概对应场景 | 注意 |
|---|---|---|
| `StandaloneCoroutine` | `launch` 默认创建的协程对象 | 内部实现细节，版本可能调整 |
| `DeferredCoroutine` | `async` 创建的带结果协程 | `await()` 会读取结果或重新抛异常 |
| `LazyStandaloneCoroutine` / `LazyDeferredCoroutine` | `CoroutineStart.LAZY` | 调用 `start()`、`join()`、`await()` 才启动 |
| `ScopeCoroutine` / `DispatchedCoroutine` | `coroutineScope`、`withContext` 等挂起边界 | 用于把当前挂起点和子任务完成结果接起来 |
| `JobSupport` | `Job` 状态机的基础实现 | 维护 active、cancelling、completed 等状态 |
| `DispatchedContinuation` | 带调度器的恢复点 | 用于把 resume 投递到目标 Dispatcher |
| `ContinuationImpl` | 编译器生成的 suspend 状态机基类线索 | 反编译 suspend 函数时经常看到 label 状态 |

理解重点：

- `CoroutineScope` 不是线程池，它只是协程归属和默认上下文。
- `CoroutineContext` 不是普通 map，但可以把它理解成按 key 组合的配置集合。
- 协程真正能取消，是因为 `Job` 被放进上下文并形成父子关系。
- 挂起不是阻塞线程，挂起本质是保存恢复点，等结果回来再恢复执行。

<a id="coroutinecontext-配置项"></a>
###### CoroutineContext 配置项

`CoroutineContext` 可以组合多个元素：

```kotlin
val context = SupervisorJob() + Dispatchers.IO + CoroutineName("app-sync")
val scope = CoroutineScope(context)
```

常见元素：

| 配置项 | 类型/写法 | 作用 | 注意 |
|---|---|---|---|
| 空上下文 | `EmptyCoroutineContext` | 没有额外配置 | builder 会从外层 scope 继承默认配置 |
| 组合上下文 | `a + b` | 把多个 context element 合并 | 相同 key 后面的覆盖前面的 |
| 任务生命周期 | `Job()` | 管理取消、完成、父子关系 | 普通 `Job` 子失败通常会影响父 |
| 监督任务 | `SupervisorJob()` | 子任务失败不自动取消兄弟任务 | 仍然要处理失败子任务的异常 |
| 调度器 | `Dispatchers.Main / IO / Default` | 决定执行和恢复线程 | 挂起函数不自动切线程，需要明确配置 |
| 协程名称 | `CoroutineName("load-user")` | 方便日志和调试 | 不影响调度和生命周期 |
| 异常处理器 | `CoroutineExceptionHandler { _, e -> }` | 处理未捕获异常 | 主要对 root `launch` 有意义，不能替代业务 `try/catch` |
| 不可取消上下文 | `NonCancellable` | 在取消后的清理代码中继续执行一小段 | 只适合 `finally` 里释放资源，不要包业务请求 |
| 线程本地元素 | `ThreadContextElement` | 切线程时传递线程本地变量 | Android 业务较少直接写 |

上下文合并要特别小心 `Job`：

```kotlin
viewModelScope.launch(Job()) {
    // 不推荐：显式传入新的 Job，容易让任务脱离 viewModelScope 原本的父子取消链路。
}
```

更常见的是只覆盖 Dispatcher 或名称：

```kotlin
viewModelScope.launch(Dispatchers.IO + CoroutineName("load-user")) {
    repository.refresh()
}
```

但在 Android 分层里，更推荐 Repository 内部或注入的 Dispatcher 决定 IO：

```kotlin
viewModelScope.launch(CoroutineName("load-user")) {
    val user = repository.loadUser() // Repository 内部 withContext(dispatchers.io)
    _uiState.value = UiState.Content(user)
}
```

<a id="作用域级别"></a>
###### 作用域级别

协程作用域的核心问题不是“哪里都能 launch”，而是“这个任务归谁管，什么时候取消”。

| 作用域级别 | 常见写法 | 生命周期 | 适合场景 | 风险 |
|---|---|---|---|---|
| 局部结构化作用域 | `coroutineScope {}` | 当前 suspend 调用结束 | 在一个函数内并发多个子任务并等待结果 | 子失败默认取消兄弟任务 |
| 局部监督作用域 | `supervisorScope {}` | 当前 suspend 调用结束 | 多个子任务互不影响，例如多个卡片独立加载 | 每个子任务异常要单独处理 |
| ViewModel 作用域 | `viewModelScope` | `ViewModel.onCleared()` | 页面数据加载、状态维护、业务编排 | 不适合跨页面长期任务 |
| Fragment View 作用域 | `viewLifecycleOwner.lifecycleScope` | Fragment View 销毁 | 收集 UI 状态、更新 binding | 不要用 Fragment 自身 lifecycle 更新已销毁 View |
| Activity/Fragment 生命周期作用域 | `lifecycleScope` | Lifecycle 销毁 | 页面级短任务、延迟动作 | 和可见性不同，收集 Flow 还要配 `repeatOnLifecycle` |
| Compose 副作用作用域 | `LaunchedEffect` | key 改变或离开组合时取消 | 进入页面自动加载、收集状态 | key 选错会重复启动 |
| Compose 事件作用域 | `rememberCoroutineScope()` | 组合离开时取消 | 点击后启动 Snackbar、滚动等事件任务 | 不适合 ViewModel 业务状态加载 |
| 应用级外部作用域 | `CoroutineScope(SupervisorJob() + dispatchers.io)` | Application / Manager 手动取消 | 跨页面同步、缓存预热、全局连接 | 必须有明确 owner 和取消入口 |
| 全局作用域 | `GlobalScope` | 进程级，几乎不自动取消 | 极少数真正全局任务 | Android 业务中容易泄漏和失控 |

Repository 是否应该持有 Scope：

- 普通 Repository 优先暴露 `suspend fun` 或 `Flow`，让调用方作用域决定生命周期。
- 如果 Repository/Manager 需要长期后台同步，可以注入 `externalScope`，并由 Application、DI 容器或业务 manager 持有和释放。
- 不要因为拿不到 scope 就用 `GlobalScope`，这通常说明任务归属没有设计清楚。

示例：应用级可控外部作用域：

```kotlin
class AppCoroutineScope(
    dispatchers: AppDispatchers
) : Closeable {
    private val job = SupervisorJob()
    val scope = CoroutineScope(job + dispatchers.io + CoroutineName("app-scope"))

    override fun close() {
        job.cancel()
    }
}
```

<a id="启动方法参数"></a>
###### 启动方法参数

`launch` 常见签名可以这样记：

```kotlin
fun CoroutineScope.launch(
    context: CoroutineContext = EmptyCoroutineContext,
    start: CoroutineStart = CoroutineStart.DEFAULT,
    block: suspend CoroutineScope.() -> Unit
): Job
```

参数含义：

| 参数 | 含义 | 常见用法 | 注意 |
|---|---|---|---|
| `context` | 给本次新协程追加或覆盖上下文元素 | `Dispatchers.IO`、`CoroutineName`、`CoroutineExceptionHandler` | 慎传新的 `Job`，可能改变父子关系 |
| `start` | 控制协程启动时机 | 默认 `DEFAULT`，少数场景 `LAZY` | Android 业务很少需要 `ATOMIC` / `UNDISPATCHED` |
| `block` | 协程体，接收 `CoroutineScope` 作为 receiver | `launch { ... }` | block 内启动的子协程默认属于它 |

`CoroutineStart` 几种模式：

| 模式 | 含义 | 使用建议 |
|---|---|---|
| `DEFAULT` | 创建后按调度器正常调度执行 | 业务默认选择 |
| `LAZY` | 延迟启动，调用 `start()`、`join()` 或 `await()` 时才启动 | 需要显式控制启动时机才用 |
| `ATOMIC` | 启动前不响应取消，直到执行到第一个挂起点 | 底层/特殊场景，业务少用 |
| `UNDISPATCHED` | 先在当前线程执行到第一个挂起点，之后按恢复调度器走 | 容易制造线程理解成本，业务少用 |

常用方法对比：

| 方法 | 返回值 | 是否新建协程 | 典型场景 | 参数重点 |
|---|---|---|---|---|
| `launch` | `Job` | 是 | 启动不需要直接返回值的任务 | `context`、`start` |
| `async` | `Deferred<T>` | 是 | 并发获取结果 | 必须 `await()`，否则结果和异常不好管理 |
| `withContext` | `T` | 不算脱离当前流程的新任务 | 切一段上下文并等待结果 | `context` 常用于切 Dispatcher |
| `coroutineScope` | `R` | 创建局部结构化作用域 | suspend 函数内并发子任务 | 子失败默认取消整个 scope |
| `supervisorScope` | `R` | 创建局部监督作用域 | 多个子任务失败互不影响 | 子异常要自己收口 |
| `runBlocking` | `T` | 启动并阻塞当前线程 | main 函数、测试桥接 | 不要在 Android 主线程业务里用 |
| `launchIn(scope)` | `Job` | 在指定 scope 收集 Flow | Flow 末端启动收集 | 生命周期由传入 scope 控制 |

`async` 并发写法：

```kotlin
val result = coroutineScope {
    val user = async { repository.loadUser() }
    val orders = async { repository.loadOrders() }
    HomeData(user.await(), orders.await())
}
```

如果其中一个失败，普通 `coroutineScope` 会取消兄弟任务；如果业务要求卡片之间互不影响，需要改成 `supervisorScope` 并分别处理结果。

<a id="挂起函数和状态机"></a>
###### 挂起函数和状态机

`suspend` 的核心不是“自动开线程”，而是“函数可以挂起，并把后续执行位置保存到 `Continuation`”。

源码：

```kotlin
suspend fun loadUser(): User {
    val token = api.getToken()
    return api.getUser(token)
}
```

概念上可以理解成编译器生成了类似状态机：

```text
loadUser(continuation)
  label = 0 -> 调 api.getToken，把后续位置保存起来，可能返回 COROUTINE_SUSPENDED
  label = 1 -> token 恢复回来，继续调 api.getUser
  label = 2 -> user 恢复回来，返回最终结果
```

关键点：

- suspend 函数在 JVM 层会多一个 `Continuation` 参数，这是恢复执行的回调对象。
- 每个挂起点会记录当前 label 和局部变量，结果回来后从对应 label 继续执行。
- 如果挂起函数立即有结果，可能直接返回；如果需要等待，会返回类似 `COROUTINE_SUSPENDED` 的标记。
- `delay()` 是挂起，不是 `Thread.sleep()`；它不会一直占用当前线程。
- 阻塞 API 如果没有切到 `Dispatchers.IO`，即使用 suspend 包起来也可能阻塞主线程。

把回调包装成可取消挂起函数时，常用 `suspendCancellableCoroutine`：

```kotlin
suspend fun LocationClient.awaitLocation(): Location = suspendCancellableCoroutine { cont ->
    val callback = object : LocationCallback {
        override fun onSuccess(location: Location) {
            cont.resume(location) {}
        }

        override fun onError(error: Throwable) {
            cont.resumeWithException(error)
        }
    }

    requestLocation(callback)

    cont.invokeOnCancellation {
        removeCallback(callback)
    }
}
```

注意：

- 包装回调时必须处理取消，避免页面销毁后底层回调还持有对象。
- 回调可能多次返回时，要防止重复 resume。
- 如果底层 SDK 没有取消接口，至少要在恢复前判断 continuation 状态或做业务兜底。

<a id="调度器与线程切换"></a>
###### 调度器与线程切换

调度器决定“协程执行或恢复时提交到哪里”，但协程本身不是线程。

| Dispatcher | 适合场景 | 底层理解 | Android 注意点 |
|---|---|---|---|
| `Dispatchers.Main` | UI 更新、主线程 API | Android 主线程调度器 | 需要 `kotlinx-coroutines-android` |
| `Dispatchers.Main.immediate` | 已经在主线程时立即执行，不额外排队 | 减少一次主线程投递 | AndroidX scope 内部常见，业务按需使用 |
| `Dispatchers.IO` | 网络、数据库、文件等阻塞 IO | 面向阻塞 IO 的共享线程资源 | 不适合 CPU 密集计算 |
| `Dispatchers.Default` | CPU 密集任务 | 面向 CPU 计算的共享线程资源 | 大量 JSON、排序、加密、图片计算等 |
| `Dispatchers.Unconfined` | 特殊测试或底层场景 | 初始在当前线程，挂起后由恢复方决定 | Android 业务一般不用 |
| `executor.asCoroutineDispatcher()` | 复用已有线程池 | 把 Java Executor 包成 Dispatcher | 需要管理 Executor 生命周期 |
| `limitedParallelism(n)` | 限制某类任务并发数 | 在 Dispatcher 上限制并发视图 | 适合限制同步、上传、解码等并发 |

`withContext` 切换流程可以理解为：

```text
当前协程
  -> withContext(Dispatchers.IO)
  -> 保存当前 Continuation
  -> 把 block 调度到 IO 线程执行
  -> block 完成后恢复原协程
  -> 后续代码继续按外层上下文执行
```

示例：

```kotlin
viewModelScope.launch {
    val config = withContext(dispatchers.io) {
        fileDataSource.readConfig()
    }
    _uiState.value = UiState.Content(config)
}
```

易错点：

- suspend 函数不代表一定在后台线程执行。
- Retrofit 的 suspend 接口自身不阻塞主线程等待网络，但数据库、文件、Bitmap 解码等阻塞代码仍要切 IO 或 Default。
- `flowOn(dispatchers.io)` 只影响它上游的 Flow 操作，不影响下游 `collect` 所在线程。
- 不要用 `Dispatchers.IO` 包所有任务；CPU 密集任务应该用 `Default` 或专门 Dispatcher。

<a id="job-取消和异常传播"></a>
###### Job 取消和异常传播

`Job` 管的是生命周期和父子关系。常见状态可以粗略理解为：

```text
New/Active -> Cancelling -> Completed
                 |             |
             cancel cause   success or failure
```

普通父子关系：

```kotlin
viewModelScope.launch {
    launch { repository.loadA() }
    launch { repository.loadB() }
}
```

- 父协程取消，两个子协程都会取消。
- 子协程未捕获异常，通常会取消父协程，父协程再取消其它子协程。
- 父协程会等待子协程完成后才真正完成。

监督关系：

```kotlin
viewModelScope.launch {
    supervisorScope {
        launch { loadHeader() }
        launch { loadList() }
    }
}
```

- 一个子任务失败，不会自动取消兄弟子任务。
- 失败子任务的异常仍然需要处理，否则会走未捕获异常路径。
- 适合多个独立模块加载，例如首页多个区域分别失败分别展示。

`launch` 和 `async` 异常差异：

| 方法 | 异常暴露时机 | 处理方式 |
|---|---|---|
| `launch` | 未捕获异常会向父协程传播，root launch 可被 `CoroutineExceptionHandler` 兜底 | 协程体内 `try/catch` 或父级统一策略 |
| `async` | 异常保存在 `Deferred` 里，`await()` 时重新抛出 | 在 `await()` 外层处理，不能忘记 await |

`CoroutineExceptionHandler` 的边界：

- 它不是万能 catch。
- 它主要处理没有被其它地方消费的未捕获异常。
- 对 `async`，如果异常被封装到 `Deferred` 并通过 `await()` 暴露，应该在 `await()` 处处理。
- Android 业务错误通常应在 ViewModel 转成 UI 状态，而不是只靠 handler 打日志。

取消异常：

```kotlin
try {
    repository.load()
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    _uiState.value = UiState.Error(e.message ?: "加载失败")
}
```

原因：`CancellationException` 是正常取消信号，吞掉它会破坏父子取消链路。

###### Android 配置模板和排查

Dispatcher 集中配置：

```kotlin
data class AppDispatchers(
    val main: CoroutineDispatcher = Dispatchers.Main,
    val io: CoroutineDispatcher = Dispatchers.IO,
    val default: CoroutineDispatcher = Dispatchers.Default
)
```

ViewModel：

```kotlin
class UserViewModel(
    private val repository: UserRepository,
    private val dispatchers: AppDispatchers
) : ViewModel() {

    fun load() {
        viewModelScope.launch(CoroutineName("load-user")) {
            _uiState.value = UiState.Loading
            try {
                val user = repository.loadUser()
                _uiState.value = UiState.Content(user)
            } catch (e: CancellationException) {
                throw e
            } catch (e: Exception) {
                _uiState.value = UiState.Error(e.message ?: "加载失败")
            }
        }
    }
}
```

Repository：

```kotlin
class UserRepository(
    private val api: UserApi,
    private val dao: UserDao,
    private val dispatchers: AppDispatchers
) {
    suspend fun loadUser(): User = withContext(dispatchers.io) {
        val user = api.getUser()
        dao.insert(user)
        user
    }
}
```

Fragment 收集：

```kotlin
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state ->
            render(state)
        }
    }
}
```

排查清单：

- 看任务 owner：这个协程属于 ViewModel、View、Lifecycle、Application 还是局部函数？
- 看 Job：有没有手动传新 `Job()` 导致脱离父作用域？
- 看 Dispatcher：阻塞 IO 是否切到 IO，CPU 密集是否切到 Default？
- 看异常：业务错误在哪里转 UI 状态？`CancellationException` 有没有被吞？
- 看 Flow：收集是否绑定 `viewLifecycleOwner` 和 `repeatOnLifecycle`？
- 看事件：一次性 Toast、导航是否误放到 `StateFlow`？
- 看测试：Dispatcher 是否可注入，Main 是否可替换？

常见优化建议：

- 主链路用 `viewModelScope.launch`，耗时工作下沉到 Repository 的 suspend 函数。
- Repository 不要默认创建长期 scope，除非任务确实跨页面并有明确 owner。
- 并发任务优先用 `coroutineScope`，互不影响时再用 `supervisorScope`。
- 给关键任务加 `CoroutineName`，方便日志中定位。
- 使用 `limitedParallelism(n)` 控制某类高成本任务并发，例如批量上传、批量解码、同步任务。
