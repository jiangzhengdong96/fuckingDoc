### 协程和传统方案对比

###### 内容概述

本文件记录 Kotlin 协程和 Android 常见传统异步方案的对比，包括 Thread、Handler、Executor、AsyncTask、RxJava、LiveData 和回调写法，重点说明协程解决的问题、适用边界和迁移取舍。

###### 使用场景

- 面试中解释为什么 Android 项目常用协程。
- 老项目从 Handler、Executor、RxJava 或回调迁移到协程时做方案判断。
- 代码评审时判断某段异步逻辑是否应该改成协程。

<a id="和回调对比"></a>
###### 和回调对比

回调写法：

```kotlin
api.getUser(
    id = userId,
    onSuccess = { user ->
        dao.save(
            user,
            onComplete = {
                view.showUser(user)
            },
            onError = { error ->
                view.showError(error)
            }
        )
    },
    onError = { error ->
        view.showError(error)
    }
)
```

协程写法：

```kotlin
viewModelScope.launch {
    try {
        val user = repository.getUser(userId)
        _uiState.value = UserUiState.Success(user)
    } catch (e: Exception) {
        _uiState.value = UserUiState.Error(e.message ?: "加载失败")
    }
}
```

对比：

- 回调容易出现嵌套，成功、失败、取消和生命周期逻辑分散在多个回调里。
- 协程可以把异步流程写成顺序结构，错误处理和状态更新更集中。
- 回调本身不是不能用，底层 SDK 仍可能提供回调；对业务层可以用 `suspendCancellableCoroutine` 包装成挂起函数。

<a id="和-thread-对比"></a>
###### 和 Thread 对比

`Thread` 写法：

```kotlin
Thread {
    val data = loadFromDisk()
    Handler(Looper.getMainLooper()).post {
        render(data)
    }
}.start()
```

协程写法：

```kotlin
viewModelScope.launch {
    val data = withContext(Dispatchers.IO) {
        loadFromDisk()
    }
    _uiState.value = UiState.Success(data)
}
```

对比：

- `Thread` 是系统线程，创建和切换成本更高，生命周期需要自己管理。
- 协程是运行在线程上的轻量级任务，能配合调度器复用线程。
- 手写线程需要自己处理取消、异常、回主线程和页面销毁问题。
- 协程可以跟 `viewModelScope`、`lifecycleScope` 绑定，生命周期更清楚。

注意：

- 协程不是让耗时任务消失，阻塞 IO 仍然要放到 `Dispatchers.IO`。
- CPU 密集任务仍会占用线程，不能因为用了协程就忽略性能。

<a id="和-handler-对比"></a>
###### 和 Handler 对比

`Handler` 常用于线程通信和延迟任务：

```kotlin
handler.postDelayed({
    doSomething()
}, 300)
```

协程写法：

```kotlin
viewModelScope.launch {
    delay(300)
    doSomething()
}
```

对比：

- `Handler` 更底层，适合处理 Looper 消息队列、主线程投递和一些框架级场景。
- 协程更适合业务异步流程，能自然表达延迟、取消、异常和顺序逻辑。
- `handler.postDelayed` 需要手动 `removeCallbacks`，否则页面销毁后任务仍可能执行。
- `delay` 是可取消的，作用域取消后延迟任务也会取消。

适用边界：

- 操作 Android 消息队列、底层消息分发时，`Handler` 仍然有价值。
- 普通业务延迟、网络、数据库、状态编排，优先用协程。

<a id="和-executor-对比"></a>
###### 和 Executor 对比

`Executor` 写法：

```kotlin
executor.execute {
    val data = loadFromDisk()
    mainHandler.post {
        render(data)
    }
}
```

协程写法：

```kotlin
viewModelScope.launch {
    val data = withContext(Dispatchers.IO) {
        loadFromDisk()
    }
    render(data)
}
```

对比：

- `Executor` 负责线程池调度，但不直接提供结构化并发、父子任务、生命周期取消和挂起恢复。
- 协程的 `Dispatcher` 可以理解为更高层的调度入口，同时协程还提供 Job、取消、异常传播和作用域。
- `Executor` 适合已有 Java 并发代码、库内部线程池或需要精细控制线程池参数的场景。
- Android 业务层通常用 `Dispatchers.IO`、`Dispatchers.Default` 或注入的 Dispatcher 更简洁。

<a id="和-asynctask-对比"></a>
###### 和 AsyncTask 对比

`AsyncTask` 曾经用于后台任务和主线程回调，但已经不适合作为新代码方案。

问题：

- 生命周期不清晰，容易持有 Activity 引用导致泄漏。
- 取消和异常处理不直观。
- API 设计老旧，不适合复杂任务组合。
- Android 官方已经废弃，不建议新项目继续使用。

协程替代：

```kotlin
viewModelScope.launch {
    val result = withContext(Dispatchers.IO) {
        doBackgroundWork()
    }
    _uiState.value = UiState.Success(result)
}
```

<a id="和-rxjava-对比"></a>
###### 和 RxJava 对比

RxJava 优点：

- 操作符非常丰富。
- 对复杂事件流、组合流、背压处理有成熟能力。
- 老项目中可能已经大量使用。

RxJava 成本：

- 学习曲线更陡。
- 链式调用过长时调试困难。
- 线程切换、订阅释放和错误处理需要团队规范。

协程 / Flow 优点：

- 挂起函数适合一次性异步结果。
- Flow 适合流式数据。
- 与 Android Lifecycle、ViewModel、Compose、Room、Retrofit 等生态结合更自然。
- 顺序代码可读性更接近同步逻辑。

迁移建议：

- 单次请求优先迁移为 `suspend` 函数。
- 连续状态或数据流迁移为 `Flow`。
- 老项目大规模 RxJava 不要一次性全改，优先从新模块或边界清晰的 Repository 开始。

<a id="和-livedata-对比"></a>
###### 和 LiveData 对比

`LiveData` 定位：

- 生命周期感知的数据持有者。
- 常用于 ViewModel 到 XML View 页面之间的状态观察。

协程 / Flow 定位：

- 协程处理异步任务和并发流程。
- `Flow` 表示异步数据流。
- `StateFlow` 表示状态，`SharedFlow` 表示事件。

对比：

- `LiveData` 更偏 UI 观察，操作符和异步组合能力较弱。
- `Flow` 更通用，可以在 Repository、UseCase、ViewModel 多层传递和组合。
- XML 老项目中 `LiveData` 仍可使用；新 Kotlin 项目更常用 `StateFlow` / `SharedFlow`。

注意：

- `LiveData` 和协程不是完全同类。协程负责异步执行，`LiveData` 负责状态观察。
- 不要为了追新把稳定的 `LiveData` 老代码无意义迁移，优先看维护成本和团队熟悉度。

<a id="选择建议"></a>
###### 选择建议

| 场景 | 建议 |
|---|---|
| 单次网络请求、数据库读写 | `suspend` + `viewModelScope` / `withContext(Dispatchers.IO)` |
| 页面 UI 状态 | `StateFlow` |
| 一次性事件 | `SharedFlow` |
| 生命周期感知收集 | `repeatOnLifecycle` |
| 底层消息队列操作 | `Handler` |
| 需要精细线程池控制 | `Executor` 或自定义 Dispatcher |
| 老项目复杂 RxJava 链 | 保留或分模块渐进迁移 |
| 新项目异步数据流 | `Flow` |

总结：

- 协程不是为了替代所有并发工具，而是让业务异步流程更清晰。
- Android 业务层优先选择协程和 Flow。
- 底层线程、消息队列、老项目兼容场景仍可能保留传统方案。
