<a id="section-内容概述"></a>
###### 内容概述

从“任务属于谁、怎么启动、是否等待、返回什么”理解常用 API。正式名称是 async、runBlocking，而不是 asyn、runBlock。以下 main 示例使用 kotlinx-coroutines-core，通常导入 `kotlinx.coroutines.*`；Android、Compose 作用域还需要对应框架依赖。

<a id="section-使用场景"></a>
###### 使用场景

学习代码执行顺序、页面请求、并行加载多个接口、线程切换、生命周期收集和跨页面任务管理。带 repository、api 等变量的片段是业务结构示意，不是独立可运行程序。

<a id="概念与方法总览"></a>
###### 概念与方法总览

| 名称 | 是什么 | 返回值 / 等待行为 |
|---|---|---|
| `CoroutineScope` | 持有 CoroutineContext 的作用域，作为启动任务的入口 | 本身不是线程，也不会因为创建了 scope 就执行任务 |
| `viewModelScope` / `lifecycleScope` | 框架管理的 scope 实例 | 生命周期结束时取消所属任务 |
| `GlobalScope` | 上下文为空的全局启动入口，没有父 Job | 不随调用方结束而取消，也不会让调用方自动等待 |
| `launch` | CoroutineScope 的扩展函数，启动子协程 | 返回 Job，不自动等待完成，不直接返回业务结果 |
| `async` | CoroutineScope 的扩展函数，启动带结果的子协程 | 返回 Deferred<T>，用 await 获取结果 |
| `withContext` | 挂起函数，在指定上下文中执行代码块 | 等待代码块及其子任务完成，返回 T |
| `coroutineScope` | 挂起函数，建立局部结构化作用域 | 等待代码块及其子任务完成，返回 T |
| `supervisorScope` | 挂起函数，建立局部监督作用域 | 同样等待，但隔离直接子任务失败 |
| `runBlocking` | 普通函数，建立协程作用域并阻塞调用线程 | 等待代码块及其子任务完成，返回 T |

withContext、coroutineScope、supervisorScope 不是长期持有的页面 scope。它们在当前挂起调用中组织一段工作；runBlocking 则用于普通阻塞入口与挂起代码之间的桥接。suspend 只表示函数允许挂起，不负责自动开线程或创建任务。

<a id="入门核心对象"></a>
###### 入门：Scope、Context、Job 和 Dispatcher 各管什么

先看一条常见配置，不需要一次记住所有名词：

```kotlin
val parentJob = SupervisorJob()
val scope = CoroutineScope(parentJob + Dispatchers.Default)
val task = scope.launch { delay(100) }
```

| 名称                          | 初学时怎么理解                        | 不是什么                                |
| --------------------------- | ------------------------------ | ----------------------------------- |
| `CoroutineScope`            | 启动任务的入口，持有一组上下文配置              | 不是线程池，不是调用后立即执行的任务                  |
| `CoroutineContext`          | 一组按 key 存放的协程配置                | 不等于 Android 的 Context，不需要传 Activity |
| `Job`                       | 任务的生命周期与父子关系控制对象               | 不是业务返回值，也不决定线程                      |
| `SupervisorJob`             | 特殊的 Job，隔离直接子任务失败向父级的传播        | 不会自动捕获异常、重试或保证任务成功                  |
| `CoroutineDispatcher`       | 决定代码在哪个执行环境运行或恢复               | 不负责决定任务属于哪个页面                       |
| `CoroutineName`             | 给协程加调试名称                       | 不影响线程或取消规则                          |
| `CoroutineExceptionHandler` | 对可交给它处理的未捕获异常做最后处理             | 不能恢复已失败的任务，也不是所有异常都能接到              |
| `Deferred<T>`               | 带结果的 Job，async 返回它，可 await 取结果 | await 不是重新执行请求                      |

上面先创建了父 Job 和 scope，还没有执行业务；launch 才创建并启动子任务，返回的 task 是这个子任务的 Job。任务通过父子关系归属 parentJob。

```text
scope 的上下文：parentJob + Default
                  │
                  └── launch 创建的 task Job
```

`+` 表示组合上下文元素，不是启动两个任务。相同 key 的元素右侧覆盖左侧，例如 `Dispatchers.IO + Dispatchers.Default` 最后使用 Default。随意在 launch 中传入新的 Job 会替换父 Job 配置，可能使任务脱离原作用域的取消链。

<a id="job控制任务生命周期"></a>
###### Job：管理任务生命周期

```kotlin
fun main() = runBlocking {
    val job = launch {
        try {
            println("开始")
            delay(1_000)
            println("正常结束")
        } finally {
            println("执行清理")
        }
    }
    yield() // 让子协程先开始并执行到 delay
    job.cancelAndJoin()
    println("任务已结束：${job.isCompleted}")
}
```

该例会打印“开始”“执行清理”“任务已结束：true”，不会打印“正常结束”。delay 支持取消，取消时会抛出 CancellationException，使任务进入清理流程。

- `isActive`：仍处于活动状态；等待 delay 时也可以是 active，不代表正在占用 CPU。
- `isCancelled`：已进入取消或因失败导致的取消状态。
- `isCompleted`：包括清理和子任务在内已经结束；既可能成功，也可能失败或取消。
- `cancel()`：请求取消，不等待结束；`cancelAndJoin()`：请求取消并等待。
- 父任务取消会向下取消子任务。普通子任务以 CancellationException 取消，通常不会因此让父级失败；非取消异常才涉及下面的失败传播。

`Job()` 本身只创建生命周期控制对象，没有代码块，也不会自己执行工作。作为长期 scope 的父 Job 时，即使某个子任务已完成，这个父 Job 通常仍保持活动；owner 结束时需要取消它。已取消的父 Job 不能通过再次 launch 复活，后续新任务通常会立即被取消。

<a id="supervisorjob失败隔离"></a>
###### SupervisorJob：一个子任务失败，不自动拖垮兄弟任务

假设首页同时加载头像和推荐列表：头像失败是否必须让推荐列表也失败？这取决于业务。两块允许独立展示时，监督关系可能更合适。

| 情况 | 普通 Job | SupervisorJob |
|---|---|---|
| 直接子任务抛未捕获的非取消异常 | 父级失败并取消其他子任务 | 不因此使监督父级或其他直接子任务失败 |
| 主动取消父 Job | 所有子任务一起取消 | 所有子任务也一起取消 |
| 某个子任务主动取消 | 通常不影响父级和兄弟任务 | 通常也不影响其他任务 |
| 失败子任务是否自动恢复 | 不会 | 也不会 |

下面是可独立运行的 JVM main 示例。handler 仅用于演示异常输出；实际 UI 的错误状态应在业务调用边界处理。

```kotlin
import kotlinx.coroutines.*

fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, error ->
        println("捕获未处理异常：${error.message}")
    }
    val parent = SupervisorJob()
    val scope = CoroutineScope(parent + Dispatchers.Default + handler)

    try {
        val avatar = scope.launch {
            throw IllegalStateException("头像加载失败")
        }
        val recommendations = scope.launch {
            delay(100)
            println("推荐列表加载成功")
        }
        joinAll(avatar, recommendations)
        println("监督父级仍活动：${parent.isActive}") // true
    } finally {
        parent.cancelAndJoin() // 自建 scope，显式清理
    }
}
```

两个任务可以独立完成，异常打印与推荐打印的先后不应作为业务保证。若换成普通 Job，未处理失败会取消父级，兄弟任务若尚未结束也会被取消；不要以为已经执行完的副作用能被撤销。

**监督只作用于直接子任务之间，不会让整个后代树都自动失败隔离：**

```text
SupervisorJob
  ├── launch A（普通协程 Job）
  │     ├── async X 失败
  │     └── async Y 可能随 A 被取消
  └── launch B 不因 A 失败而被取消
```

X、Y 的直接父级是 A，A 仍按普通失败规则工作。若 X、Y 要相互隔离，可在 A 内使用 supervisorScope，并分别处理结果。

<a id="监督与异常处理区别"></a>
###### 监督、异常处理和业务错误态不是同一件事

```kotlin
viewModelScope.launch {
    try {
        repository.refresh()
    } catch (e: CancellationException) {
        throw e
    } catch (e: java.io.IOException) {
        // 更新错误状态，让页面能提示或重试。
    }
}
```

默认 AndroidX viewModelScope 使用监督关系，适合多项页面任务，但这不等于网络异常不用处理。未处理异常仍可能交给最终异常处理机制，在 Android 中可能造成崩溃。

- Job / SupervisorJob：决定失败如何影响父子和兄弟任务。
- try/catch：在能够处理失败的地方转换结果、降级或更新 UI；不要吞取消异常。
- CoroutineExceptionHandler：处理到达对应边界的未捕获异常，任务已经失败，不能从抛异常的下一行继续运行。
- async：异常保存在 Deferred 中并可由 await 抛出；普通父级下失败仍会向上传播，监督下也需要观察并处理 await 的结果。

`try { scope.launch { fail() } } catch (...) { ... }` 通常接不住之后协程体里的异常：launch 已经返回。要处理任务内部失败，把 try/catch 放进协程体，或在结构化调用外捕获 coroutineScope / await 传播的失败。

<a id="supervisorjob与supervisorscope"></a>
###### SupervisorJob 和 supervisorScope 怎么选

| API                       | 用途                                          | 谁等待、谁清理                 |
| ------------------------- | ------------------------------------------- | ----------------------- |
| `SupervisorJob()`         | 创建监督父 Job，可组合成长生命周期 scope（创建一个可以反复启动任务的作用域） | owner 管理并取消，不自动等待业务代码   |
| `supervisorScope { ... }` | 在当前挂起调用内临时组织独立子任务（一次函数调用内，临时组织多个任务）         | 函数等待所有子任务结束，保留与调用方的取消关系 |

页面里只需要临时并发加载几个互不影响的模块，通常用 supervisorScope；应用或账号级组件需要持续接收新任务时，可注入或持有明确管理的监督 scope。不是为了隔离一次请求失败，就每次新建一个永久 scope。

可选的 `SupervisorJob(parentJob)` 会挂到指定父级：上级取消仍向下传播；监督层的直接子任务失败被隔离。多个没有传 parent 的独立 Job，不会因为定义在同一个函数里就自动成为父子。

<a id="作用域怎么选"></a>
###### 作用域怎么选

| 作用域 / 入口                            | 归属与取消时机                            | 常见用法与边界                                                                                    |
| ----------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| `viewModelScope`                    | ViewModel 清理时取消                    | 页面加载、业务编排；旋转或留在返回栈中不一定清理                                                                   |
| `Activity.lifecycleScope`           | Activity Lifecycle 到 DESTROYED 时取消 | Activity UI 工作；STOPPED 不会自动取消所有任务                                                          |
| `Fragment.lifecycleScope`           | Fragment 本身销毁时取消                   | 不等于 Fragment View 的生命周期                                                                    |
| `viewLifecycleOwner.lifecycleScope` | Fragment View 销毁时取消                | 收集状态并访问 binding，通常更合适                                                                      |
| `rememberCoroutineScope()`          | 对应组合位置离开 Composition 时取消           | 在点击回调中 launch；不是每次重组都取消重建                                                                  |
| `LaunchedEffect(key)`               | 离开组合或 key 改变时取消，key 改变会启动新任务       | Compose 管理副作用的 API，并非可随处获取的 scope 变量                                                       |
| `CoroutineScope(context)`           | owner 自己管理                         | 注入的应用级 / 账号级 / 组件级任务；通常提供 Job、Dispatcher 和取消入口                                             |
| `MainScope()`                       | 调用方自己管理                            | 创建 SupervisorJob + Main 的作用域，不自动绑定页面                                                       |
| `GlobalScope`                       | 没有调用方父 Job                         | 独立任务，不能依赖调用方取消；JVM 退出或进程死亡也不会保证它完成 （和CoroutineScope区别就是不能通过scope 批量取消子协程，只能调用对应子协程引用一个个取消） |

Repository 是单例，不意味着内部必须创建 scope。单例可以保存共享数据，而 suspend 方法沿用 ViewModel 发起任务的生命周期；任务确需跨页面运行时，再注入明确管理的外部 scope。

```kotlin
class SyncOwner(private val dispatcher: CoroutineDispatcher) {
    private val scope = CoroutineScope(SupervisorJob() + dispatcher)

    fun sync(): Job = scope.launch {
        // 执行业务；预期失败应在合适边界处理，监督不会自动吞异常。
    }

    fun close() {
        scope.cancel() // owner 结束时调用；cancel 不等于已经等待清理完成
    }
}
```

GlobalScope 并非绝对不能用于学习演示，但它会把任务从当前结构化关系中分离。普通入口返回后，不能期待运行器自动等它；需要显式保存 Job 并等待。给 GlobalScope.launch 的内部末尾加 delay，并不能阻止外层入口提前结束。

<a id="launch启动不返回业务结果"></a>
###### launch：启动任务，返回 Job

常见形式：`scope.launch(context = ..., start = ..., block = { ... })`。

- context：追加或覆盖上下文，例如 Dispatcher、CoroutineName；不传时继承 scope 的相关配置。
- start：启动策略，默认 DEFAULT；不等于所有情况下都“立刻在另一个线程执行”。
- block：协程体，接收者是 CoroutineScope，可以继续启动子协程。
- 返回 Job：用于 start、cancel、join、cancelAndJoin，以及观察 isActive / isCompleted / isCancelled。

```kotlin
fun main() = runBlocking {
    println("1 外层开始")
    val job = launch {
        println("3 子协程开始")
        delay(10)
        println("4 子协程结束")
    }
    println("2 launch 已返回")
    job.join()
    println("5 等待完成")
}
```

这个特定例子继承 runBlocking 默认事件循环，输出按 1、2、3、4、5 排列。换成 Default / IO、UNDISPATCHED 或立即执行型调度器后，不能照搬这个顺序；并发线程上的两个独立打印通常没有固定先后保证。

launch 默认会启动，不需要额外 start。它返回 Job 时任务可能尚未执行，也可能已经执行了一部分；join 只等待，不返回业务结果，也不把目标失败直接作为结果重新抛出。不过父子失败传播仍可能取消等待者。

<a id="async并发获取结果"></a>
###### async：启动带结果的任务，用 await 等待

async 的 context、start、block 参数与 launch 类似，返回 Deferred<T>。Deferred 也是 Job，除取消和等待结束外，还能通过 await 取得 T 或抛出任务失败。

```kotlin
fun main() = runBlocking {
    val a = async { delay(100); 10 }
    val b = async { delay(100); 20 }
    println(a.await() + b.await()) // 30
}
```

先启动两个任务再 await，等待时间可以重叠；并发不等于一定在两个线程上并行执行，delay 期间线程可以执行其他工作。

```kotlin
// 这样写则是先等 A 完成，才启动 B。
val a = async { loadA() }.await()
val b = async { loadB() }.await()
```

`awaitAll()` 等多个 Deferred，任一个失败时可及时抛异常；它本身不是启动器。默认结构化并发下 async 失败也会取消普通父级，不是等 await 才传播；并发任务的整体失败通常在外层 try/catch 包住 coroutineScope 处理。

<a id="withcontext切换并等待"></a>
###### withContext：切换上下文并等待结果

常见形式：`withContext(context) { ... }`，它是 suspend 函数，返回代码块的结果，不返回可独立操作的 Job。

```kotlin
suspend fun readConfig(file: java.io.File): String =
    withContext(Dispatchers.IO) {
        file.readText() // 阻塞 IO 放到合适调度器
    }

// ViewModel 中
viewModelScope.launch {
    val text = readConfig(file) // 暂停当前流程，等待读取结果
    updateUi(text)             // 恢复到调用方上下文后继续
}
```

调用方协程等待不等于调用线程阻塞。withContext 块通常属于当前取消链，不能因为切到 IO 就跨越 ViewModel 清理继续运行。IO 与 Default 可能共享底层线程，不保证每次都是物理线程切换；传入相同调度器也可能直接执行。

两个连续 withContext 调用默认先后完成，不会自动并发；需要独立并发结果时先 async，再 await。Retrofit / Room 等已经提供主线程安全的挂起 API 时，不必机械为每次调用再包 IO。不要为普通切线程传入新的 Job，破坏原本父子关系。

<a id="局部作用域与失败隔离"></a>
###### coroutineScope 与 supervisorScope：组织子任务

```kotlin
suspend fun loadPage(): Page = coroutineScope {
    val user = async { api.loadUser() }
    val favorites = async { api.loadFavorites() }
    Page(user.await(), favorites.await())
}
```

coroutineScope 不创建独立线程，默认沿用调用方上下文；只要一个普通子任务失败，其他任务通常一起取消，适合“整体成功或整体失败”。作用域会等子任务结束，不会留下任务再直接返回。

```kotlin
suspend fun loadIndependentPanels(): Pair<String, String> = supervisorScope {
    val left = async { loadLeft() }
    val right = async { loadRight() }

    suspend fun valueOrFallback(task: Deferred<String>): String = try {
        task.await()
    } catch (e: CancellationException) {
        throw e
    } catch (e: java.io.IOException) {
        "加载失败"
    }

    valueOrFallback(left) to valueOrFallback(right)
}
```

supervisorScope 隔离直接子任务失败，但不吞异常。上例明确处理每个 await 的预期失败；若 await 的异常逃出 scope 代码块，整个 scope 仍会失败并取消剩余子任务。父级取消仍会向所有子任务传播。

<a id="runblocking演示入口"></a>
###### runBlocking：普通入口等待协程运行完

runBlocking 的 context 默认 EmptyCoroutineContext，block 是挂起代码块。它阻塞调用线程，同时默认通过该线程上的事件循环推进协程，直到代码块和子任务完成；不是“阻塞后什么都不能执行”。

```kotlin
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() = runBlocking {
    val job = launch {
        withContext(Dispatchers.IO) {
            listOf("480p", "720p", "1080p")
                .asFlow()
                .collect { println(it) }
        }
        println("start")
        delay(1)
        println("end")
    }
    job.join()
    println("全部完成")
}
```

输出为 480p、720p、1080p、start、end、全部完成，逐行打印。这里显式 join 让“全部完成”位于子任务结束后；即使不写 join，runBlocking 自身也会等子任务完成，但外层那句打印可能提前执行。

- 只是学习顺序：main + runBlocking 很方便；普通运行入口也可写成 `fun demo() = runBlocking { ... }`，不强制写成单元测试。
- 真正协程单元测试：通常使用 kotlinx-coroutines-test 的 runTest，以控制调度和虚拟时间。
- Android UI：不要在主线程用 runBlocking 等耗时工作，可能卡顿甚至死锁；在已有协程中也通常不需要嵌套 runBlocking。
- `runBlocking(Dispatchers.IO)` 仍阻塞调用线程，只是块由 IO 调度，不是避免 UI 阻塞的方案。

若专门演示 GlobalScope，下面的 join 是必要的显式等待；实际业务通常选有 owner 的 scope：

```kotlin
@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
    val job = GlobalScope.launch {
        delay(10)
        println("独立任务完成")
    }
    job.join() // 这个任务不是 runBlocking 的子任务，不能靠自动等待
}
```

<a id="启动等待取消速查"></a>
###### 启动、等待与取消速查

| 操作 / 配置 | 怎么用 | 关键细节 |
|---|---|---|
| `CoroutineStart.DEFAULT` | launch / async 默认策略 | 按调度器安排执行，真正开始前可被取消 |
| `CoroutineStart.LAZY` | 先创建，start / join / await 时启动 | 多个惰性任务要并发，可先全部 start 再 await；未启动也未取消的子任务可能让父级一直等 |
| `CoroutineStart.UNDISPATCHED` | 立即在调用线程执行到首次实际挂起 | 后续恢复遵循调度器；首次执行可能越过较长代码，不等于整个任务都不调度 |
| `CoroutineStart.ATOMIC` | 启动阶段不被提前取消阻止执行 | 不保证整个任务不可取消；第一个可取消挂起点仍可响应取消，实验状态按库版本确认 |
| `job.start()` | 显式启动惰性任务 | 不等待完成，不是重启已经完成的 Job |
| `job.join()` | 挂起等待完成 | 不读取业务结果 |
| `deferred.await()` | 挂起等待结果 | 成功返回值，失败抛异常；可多次 await 同一结果，不是重复请求 |
| `job.cancel()` | 请求取消 | 不等待 finally 清理完成 |
| `job.cancelAndJoin()` | 请求取消并等待结束 | 依赖协作取消，正常返回后才确认目标完成 |
| `delay(ms)` | 挂起等待时间，支持取消 | 不阻塞线程；放在独立任务内部不会让外层方法等待 |
| `yield()` / `ensureActive()` | 让出执行机会并检查取消 / 只检查取消 | CPU 循环需主动配合，不保证一定切换线程 |

选择口诀：只启动用 launch，要并发结果用 async，局部换上下文用 withContext，组合子任务用 coroutineScope，隔离子任务失败用 supervisorScope，普通阻塞入口演示用 runBlocking；任务归属另由合适的 scope 决定。
