<a id="section-内容概述"></a>
###### 内容概述

区分线程安全、逻辑竞态、互斥与限流，明确 limitedParallelism、Mutex、Semaphore 和 Channel 的边界。

<a id="section-使用场景"></a>
###### 使用场景

批量上传、限量解码、跨挂起点维护共享数据、多消费者处理任务、避免重复提交。

<a id="单线程也有逻辑竞态"></a>
###### 单线程也有逻辑竞态

同一线程只能在一个时刻执行一段代码，但协程挂起后其他协程可以运行。先读旧值、挂起、再写回的流程，可能覆盖期间其他协程的更新：

```kotlin
val old = counter
loadSomething() // 挂起，其他协程可能已经修改 counter
counter = old + 1
```

普通无挂起的主线程代码与这种交错不同；不要笼统声称“单线程都不安全”。需要保护的往往是完整的业务操作，而不只是单次字段读写。

<a id="mutex互斥"></a>
###### Mutex 互斥

Mutex 保证遵守同一把锁的协程一次只有一个进入临界区，等待锁时挂起而非阻塞线程。

```kotlin
private val mutex = Mutex()
private var cached: Token? = null

suspend fun getToken(): Token = mutex.withLock {
    cached?.takeIf { it.isValid() } ?: fetchToken().also { cached = it }
}
```

示例把检查、刷新、保存串成一个临界区；所有访问 cached 的路径也必须遵守同一同步规则。网络很慢时持锁会延迟其他调用，可以进一步设计共享中的刷新任务，但要明确失败和取消由谁负责。

- Mutex 不可重入：同一协程再次获取同一把锁可能一直等待；传入相同非空 owner token 的错误重入可抛异常，不是重入支持。
- withLock 正常返回或抛异常都会释放锁；业务副作用不会因为释放锁自动回滚。
- `tryLock()` 立即返回是否拿到锁；成功后必须在 finally 释放。`isLocked` 只是瞬时观察，不能代替获取锁。
- 不要使用 synchronized 把挂起业务跨越的整个过程当作已保护；阻塞锁和挂起式互斥不是同一机制。

<a id="semaphore限制在途任务"></a>
###### Semaphore 限制在途任务

Semaphore(n) 发放 n 个许可，withPermit 在整个代码块结束之前持有许可，包括挂起等待网络的时间，适合限制同时进行中的业务操作。

```kotlin
private val uploadPermits = Semaphore(4)

suspend fun uploadOne(file: File): UploadResult = uploadPermits.withPermit {
    api.upload(file) // 挂起时仍持有许可，最多 4 个通过此入口的上传在途
}
```

异常或取消会通过 withPermit 释放许可。Semaphore 应由同一管理者共享，若每次 uploadOne 都 new Semaphore(4)，调用之间就没有共同限制。不要在持有许可时重复申请同一个只有一个许可的信号量。

许可数只限制并发中的操作，不限制每秒请求数；按时间配额限流还需令牌桶等策略。对百万条任务先 launch 百万个再等许可仍有内存成本，应分批或用有限 worker 消费队列。

<a id="limitedparallelism边界"></a>
###### limitedParallelism 的边界

| 工具                                 | 限制什么             | 挂起后是否继续占用限制名额         |
| ---------------------------------- | ---------------- | --------------------- |
| `dispatcher.limitedParallelism(n)` | 此调度器视图同时执行代码的并行度 | 不按整个业务任务占位，挂起可让其他协程执行 |
| `Semaphore(n).withPermit`          | 进入受控区且尚未结束的操作数量  | 是，直到离开 withPermit     |
| `Mutex.withLock`                   | 共享状态的互斥临界区       | 是，直到释放锁               |

```kotlin
val decodeDispatcher = Dispatchers.Default.limitedParallelism(2)
withContext(decodeDispatcher) { decodeImageBlocking(bytes) }
```

这能限制通过同一个视图执行的同步解码代码的并行度；不保证固定线程身份。`limitedParallelism(1)` 也不是可跨挂起点互斥的锁，两个任务可在挂起点交错。

对于挂起式 upload，网络等待时并未占用调度器执行槽，因此 limitedParallelism(4) 不保证只有 4 个上传在途；应使用共享 Semaphore。每次新建不同视图也不形成共同的 n 额度，需复用视图；IO 的弹性视图还可能超出 IO 默认并行度，不应理解为全应用的统一线程上限。

<a id="channel与广播"></a>
###### Channel 与广播

| 工具                            | 多个消费者时的语义            | 注意事项                  |
| ----------------------------- | -------------------- | --------------------- |
| `Channel` / `receiveAsFlow()` | 一个元素交给其中一个接收者        | 适合工作分配，不是所有 UI 都收到    |
| `SharedFlow`                  | 广播给各订阅者，受缓冲 / 丢弃配置影响 | replay 历史不是一次消费后删除的队列 |
| `StateFlow`                   | 广播当前状态及相等合并后的变化      | 不保证记录全部中间状态           |

Channel 常见容量：RENDEZVOUS（默认 0，发送与接收会合）、BUFFERED（使用默认缓冲策略，不应依赖固定数字）、CONFLATED（保留最新）、UNLIMITED（可能无限占内存）。显式正整数可限制缓冲元素数量。

send 可挂起，trySend 返回 ChannelResult，需要检查失败；成功不等于业务已完成。close 拒绝后续发送，已缓冲元素通常可继续接收；cancel 丢弃待处理内容并取消等待。持有资源的元素需考虑 onUndeliveredElement；该回调不是业务重试入口，也不表示消费确认。

接收与取消可能竞争：元素离开队列后，消费者可能在业务处理前取消。因此 Channel 不天然保证支付、导航等动作恰好执行一次；可靠任务仍需业务确认、幂等和必要的持久化。

<a id="并发工具选择"></a>
###### 选择建议

- 单个数字计数：可用 AtomicInteger 等原子类型；原子变量不能自动保护多个字段之间的不变量。
- UI 状态纯转换：MutableStateFlow.update。
- 多字段共享状态或跨挂起临界区：Mutex，并明确所有读写都遵守锁。
- 在途请求 / 上传数：共享 Semaphore，包住完整业务操作。
- 同步 CPU 任务并行度：复用 Dispatcher 的 limitedParallelism 视图。
- 固定数量 worker 分配任务：有界 Channel，明确停止和取消时如何处置未完成任务。
