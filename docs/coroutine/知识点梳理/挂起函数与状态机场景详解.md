<a id="基本背景"></a>
###### 先记住这几个背景

本文只用两个例子说明：**一个函数连续挂起两次，以及一个挂起函数调用另一个挂起函数。** “顺序”指没有额外嵌套的业务挂起函数，底层 delay 本身当然也是挂起调用。

| 名称 | 在流程中的作用 |
|---|---|
| Continuation（续体） | 保存“以后怎样继续”，通过 resumeWith 接收成功或失败 |
| label | 本层函数下次从哪个位置继续 |
| result | 本次恢复带回的结果，不一定是本层函数最终返回值 |
| completion | 本层完成后，把结果交给哪个调用方续体 |
| COROUTINE_SUSPENDED | 暂时没有业务结果，本次调用先返回 |

需要跨挂起点保存进度时，编译器通常生成状态机续体；直接返回、尾调用等情况可能省去独立续体。这里的 completion 是调用关系，不是 Job 的父子关系。

业务示例保留 Kotlin；状态机使用贴近 JVM 反编译展示的 Java switch/case。它们仍是**教学伪代码**：用英文标识符表达逻辑，省略调度、并发竞争和实际生成类的细节，不能直接当作 kotlinx.coroutines 实现运行。两条主流程先假设 delay 确实挂起、任务成功且未取消。只看 label、result 和 completion 如何变化。

<a id="runblocking外层"></a>
###### 两个例子共同的最外层：runBlocking

先区分两个对象：**B 是 runBlocking 花括号内代码的执行续体；R 是 runBlocking 创建、接收代码块完成结果的 BlockingCoroutine。** B 有业务恢复位置 label；R 管理协程完成，不能简单把它当成另一个有业务 label 的状态机。

下面是两个例子共同使用的入口伪代码。RunBlockingBlock 是代码块续体的示意类型；startBlock、createBlockingCoroutine、joinBlocking 仅表示对应职责，省略真实签名和调度实现。

```kotlin
fun runBlockingExample(createBlock: (BlockingCoroutine<Unit>) -> RunBlockingBlock) {
    val root = createBlockingCoroutine<Unit>() // R
    val block = createBlock(root)              // B, B.completion = R
    startBlock(block)                          // 启动 B 的 label = 0
    root.joinBlocking()                       // 等整体完成后才返回
}
```

startBlock 表示运行库启动代码块：若代码块挂起就等待后续恢复；若直接返回或抛异常则向 R 交付结果。joinBlocking 在本例默认事件循环下会处理可执行任务，没有可执行任务时等待；它不是让调用线程忙循环，也不是挂起函数。真实实现还会等待子任务完成，本页例子没有额外 launch 子任务。

```text
main 调用 runBlocking
  -> 创建 R，再启动 B（B.completion = R）
  -> B 可能挂起，控制权回到运行库
  -> runBlocking 仍在等待整体完成，并处理默认事件循环中的任务
  -> B 最终返回 Unit，运行库通知 R 完成
  -> joinBlocking 结束，runBlocking 返回 Unit，main 结束
```

<a id="顺序挂起例子"></a>
###### 例子一：同一个函数顺序挂起两次

**业务代码：**

```kotlin
suspend fun sequential(): String {
    val prefix = "user"       // ①
    delay(100)                // ② 第一个挂起点
    val text = "$prefix-7"    // ③
    delay(100)                // ④ 第二个挂起点
    return "$text-done"       // ⑤
}

fun main() = runBlocking {
    val result = sequential()
    println(result)           // ⑥ 预期：user-7-done
}
```

sequential 只需要记住三个入口：label = 0 是首次进入，1 是第一次 delay 后，2 是第二次 delay 后。两次挂起复用同一个 sequential 状态机对象。

**对应伪代码：**

```java
// Java-style pseudocode; constructors and continuation inheritance are omitted.
class SequentialState {
    Continuation completion;
    int label = 0;
    String savedPrefix;
    String savedText;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                savedPrefix = "user";                    // ①
                label = 1;
                result = delay(100, this);                // ②
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                // No break: immediate completion falls through to case 1.
            case 1:
                throwOnFailure(result);
                savedText = savedPrefix + "-7";           // ③
                label = 2;
                result = delay(100, this);                // ④
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                // No break: immediate completion falls through to case 2.
            case 2:
                throwOnFailure(result);
                return savedText + "-done";               // ⑤
            default:
                throw new IllegalStateException("Invalid label");
        }
    }
}
```

`delay(100, this)` 示意 JVM 层传入 Continuation 的调用形式；业务 Kotlin 仍写 delay(100)。throwOnFailure 示意检查内部 Result 的失败表示，result 是编译后的 Object 通道，不是要求业务手动拆包装。

**这里没有 while 循环。** switch 进入时读取一次 label：

- 等待真的挂起：立即 return，整个方法退出。以后恢复时重新进入方法，再由 switch 读取已经保存的 label。
- 等待立即完成：没有 return，也没有 break，就贯穿到下一个 case。不是修改 label 后自动重新匹配 switch。
- 两层代码共用结尾时（下面的 Block、InnerState、OuterState），case 里用 break 跳出 switch，然后执行共同结尾。

这是 Java 传统 switch 的贯穿语义；Kotlin when 不会自动贯穿。之前用 while + when 模拟这一点虽然能表达控制流，但不像本例常见的生成结构，因此已改掉。实际 JVM 使用跳转字节码，反编译器也可能显示 if/goto 等形式，不能断言所有挂起函数都是相同 switch 文本。

**把外层 runBlocking 代码块也展开：**

```java
class SequentialBlock {
    BlockingCoroutine completion; // R
    int label = 0;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                label = 1;
                SequentialState state = new SequentialState(this);
                result = state.invokeSuspend(Unit.INSTANCE);
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                break; // Immediate result is ready; continue after switch.
            case 1:
                throwOnFailure(result);
                break; // Resumed result is ready; continue after switch.
            default:
                throw new IllegalStateException("Invalid label");
        }
        System.out.println((String) result); // ⑥
        return Unit.INSTANCE;
    }
}

void main() {
    runBlockingExample(root -> new SequentialBlock(root));
}
```

这里的 Block 简化省略 Continuation 的继承及 resumeWith 桥接；它接收业务函数返回的 String，自己完成后向 R 返回 Unit。代码用于看清关系，不是完整可编译实现。

<a id="顺序挂起流程"></a>
###### 例子一流程：三个入口，两次退出，一次完成

```text
main -> runBlockingExample 创建 R 和 SequentialBlock B
  -> B.invokeSuspend，B.label = 0
  -> 设置 B.label = 1，创建 S，S.completion = B
  -> 第一次进入 S.invokeSuspend，label = 0
     -> ① 保存 prefix = "user"
     -> ② 设置 label = 1，调用第一次 delay
        -> 登记延时恢复 S
        -> 返回 COROUTINE_SUSPENDED
        -> sequential 和外层等待代码逐层退出本次执行

第一次 delay 到期
  -> 运行库恢复 S，传入 Result.success(Unit)
  -> 第二次进入 S.invokeSuspend，label = 1
     -> ③ 读取保存的 prefix，得到 text = "user-7"
     -> ④ 设置 label = 2，调用第二次 delay
        -> 再次返回 COROUTINE_SUSPENDED
        -> 本次恢复结束，外层仍没有 sequential 的最终结果

第二次 delay 到期
  -> 运行库再次恢复同一个 S，传入 Result.success(Unit)
  -> 第三次进入 S.invokeSuspend，label = 2
     -> ⑤ 返回 "user-7-done"
     -> 运行库把这个字符串交给 S.completion
     -> B.invokeSuspend，B.label = 1
     -> ⑥ 打印字符串，B 返回 Unit
     -> 运行库向 B.completion（R）交付 Unit
     -> R 完成，joinBlocking 结束，runBlocking 返回，main 结束
```

| 进入次数 | label | 收到的结果 | 本次执行到哪里结束 |
|---|---|---|---|
| 首次 | 0 | 启动信号 | 第一次 delay 挂起 |
| 第一次恢复 | 1 | 第一次 delay 完成的 Unit | 第二次 delay 再次挂起 |
| 第二次恢复 | 2 | 第二次 delay 完成的 Unit | 返回最终字符串 |

**本例总结：** 同一个函数的多个挂起点，通过同一个状态机对象的不同 label 区分。每次 delay 有自己的等待记录，但不是为 sequential 每次恢复重建状态机。再次挂起就继续等，最终完成才通知 B；B 打印并返回 Unit 后，R 完成，runBlocking 才返回。

<a id="嵌套挂起例子"></a>
###### 例子二：outer 调用 inner，inner 内部挂起

**业务代码：**

```kotlin
suspend fun inner(): String {
    delay(100)                    // ②
    return "done"                 // ③
}

suspend fun outer(): String {
    val value = inner()           // ①
    return "outer: $value"        // ④
}

fun main() = runBlocking {
    val result = outer()
    println(result)               // ⑤ 预期：outer: done
}
```

inner 在 delay 后还要返回字符串；outer 在 inner 后还要拼接字符串。两层都需要记住自己的恢复位置。

**续体关系：**

```text
InnerState I
  -> I.completion = OuterState O
     -> O.completion = NestedBlock B
        -> B.completion = BlockingCoroutine R
```

调用方把自己的续体传进去；被调用函数需要自己的状态机时，创建新续体，并把收到的调用方续体保存为 completion。不是把最外层的同一个对象一直传到底。

**对应伪代码：**

```java
class InnerState {
    Continuation completion; // O
    int label = 0;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                label = 1;
                result = delay(100, this); // ②
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                break;
            case 1:
                throwOnFailure(result);
                break;
            default:
                throw new IllegalStateException("Invalid label");
        }
        return "done";                    // ③
    }
}

class OuterState {
    Continuation completion; // B
    int label = 0;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                label = 1;
                InnerState child = new InnerState(this);
                result = child.invokeSuspend(Unit.INSTANCE); // ①
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                break;
            case 1:
                throwOnFailure(result);
                break;
            default:
                throw new IllegalStateException("Invalid label");
        }
        return "outer: " + (String) result; // ④
    }
}
```

这里把业务状态机统一放进 invokeSuspend，便于读流程。真实普通 suspend 函数的生成代码也可能留在函数体中，由配套续体的 invokeSuspend 重入；不影响这里的完成链关系。

**把外层 runBlocking 代码块也展开：**

```java
class NestedBlock {
    BlockingCoroutine completion; // R
    int label = 0;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                label = 1;
                OuterState state = new OuterState(this);
                result = state.invokeSuspend(Unit.INSTANCE);
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                break; // Immediate result is ready; continue after switch.
            case 1:
                throwOnFailure(result);
                break; // Resumed result is ready; continue after switch.
            default:
                throw new IllegalStateException("Invalid label");
        }
        System.out.println((String) result); // ⑤
        return Unit.INSTANCE;
    }
}

void main() {
    runBlockingExample(root -> new NestedBlock(root));
}
```

这里的 Block 简化省略 Continuation 的继承及 resumeWith 桥接；它接收业务函数返回的 String，自己完成后向 R 返回 Unit。代码用于看清关系，不是完整可编译实现。

<a id="嵌套挂起流程"></a>
###### 例子二流程：调用往里走，完成结果往外传

```text
main -> runBlockingExample 创建 R 和 NestedBlock B
  -> B.invokeSuspend，B.label = 0
  -> 设置 B.label = 1，创建 O，O.completion = B
  -> O.invokeSuspend，label = 0
     -> ① 设置 O.label = 1，开始调用 inner
        -> 创建 I，设置 I.completion = O
        -> I.invokeSuspend，label = 0
           -> ② 设置 I.label = 1，调用 delay
              -> delay 登记恢复 I，返回 COROUTINE_SUSPENDED
           -> inner 返回 COROUTINE_SUSPENDED
        -> outer 返回 COROUTINE_SUSPENDED
     -> 外层调用方也挂起，尚未执行 println

等待完成
  -> 运行库恢复 I，传入 Result.success(Unit)
  -> I.invokeSuspend，label = 1
     -> ③ 返回 "done"
     -> 运行库发现 I 已完成，把 "done" 交给 I.completion，也就是 O
  -> O.invokeSuspend，label = 1，result 的成功值是 "done"
     -> ④ 拼接并返回 "outer: done"
     -> 运行库把字符串交给 O.completion
  -> B.invokeSuspend，B.label = 1
     -> ⑤ 打印 "outer: done"，B 返回 Unit
     -> 运行库向 B.completion（R）交付 Unit
     -> R 完成，joinBlocking 结束，runBlocking 返回，main 结束
```

| 正在恢复谁 | 自己的 label | 收到什么 | 完成后交出什么 |
|---|---|---|---|
| I：inner 的续体 | 1 | delay 完成的 Unit | "done" |
| O：outer 的续体 | 1 | inner 返回的 "done" | "outer: done" |
| 外层代码块 | 其调用 outer 后的恢复位置 | "outer: done" | 打印后完成 |

**本例总结：** 每层用自己的 label 决定从哪里继续，用收到的 result 执行后续计算，完成后把结果交给 completion。inner 若恢复后又挂起，就先退出，不通知 outer 完成。完整完成链为 I → O → B → R；B 打印后返回 Unit，R 完成后 runBlocking 才返回。完成链和 Job 父子取消关系不是同一件事。

<a id="恢复桥接"></a>
###### 谁把内层返回值交给外层

上面流程中“运行库把结果交给 completion”，概念上相当于下面的代码：

```java
// Simplified shape of BaseContinuationImpl.resumeWith.
void resumeWith(Object result) {
    BaseContinuationImpl current = this;
    while (true) {
        Continuation completion = current.completion;
        Object outcome;
        try {
            Object value = current.invokeSuspend(result);
            if (value == COROUTINE_SUSPENDED) return;
            outcome = success(value);
        } catch (Throwable error) {
            outcome = failure(error);
        }
        current.releaseIntercepted();
        if (completion instanceof BaseContinuationImpl) {
            current = (BaseContinuationImpl) completion;
            result = outcome;
        } else {
            completion.resumeWith(outcome);
            return;
        }
    }
}
```

**这一处 while 才是运行库真正采用的恢复循环。** 它推进的是不同层的续体：I 完成后把 current 换成 O，O 完成后换成 B；不是在同一个业务函数里不停检查 label。任意一层返回挂起标记，循环立即退出。最终遇到 R 这样的非 BaseContinuationImpl 完成接收者，调用其 resumeWith 后返回。

伪代码省略了具体 Result 内部表示和部分实现细节，success/failure 表示包装成功或失败。调度安排发生在相关运行库路径上，不由这段循环保证切线程。

label 决定执行位置，result 是送进来的数据，两者不能互相替代。失败结果会在恢复位置进入原有异常处理逻辑；并不是把异常当成正常字符串拼接。

<a id="续体与callback"></a>
###### 续体很像 callback：相似在哪里，区别是什么

**这个理解是对的：它们都能把“完成后接着做什么”交给下层，等结果出来后再通知上层。** Continuation 可以理解成标准化的后续执行接口，但完整的协程机制还包括编译器生成的状态机，以及运行库的调度、Job 和结构化并发。

仍用例子二：等待完成后 inner 得到 "done"，outer 拼接字符串，外层打印。用 callback 表达，可以写成下面的教学代码：

```kotlin
// scheduleLater is a teaching helper: invoke the callback after a delay.
fun innerCallback(callback: (Result<String>) -> Unit) {
    scheduleLater(100) {
        callback(Result.success("done"))
    }
}

fun outerCallback(callback: (Result<String>) -> Unit) {
    innerCallback { result ->
        val mapped = result.map { value -> "outer: $value" }
        callback(mapped)
    }
}

fun startExample() {
    outerCallback { result ->
        println(result.getOrThrow())
    }
}
```

这里 startExample 登记工作后即可返回；它不是前面 runBlocking 的阻塞入口。示意的异步调度环境需要由宿主维持运行，不能直接把它当成保证进程等待结果的 main。

对应的协程业务代码就是前面的：

```kotlin
suspend fun inner(): String {
    delay(100)
    return "done"
}

suspend fun outer(): String {
    val value = inner()
    return "outer: $value"
}

// Inside an existing coroutine:
val result = outer()
println(result)
```

**对照着看流程：**

```text
callback 写法
  -> outer 把后续拼接代码写成 callback，交给 inner
  -> inner 等待完成，调用 callback，传入 "done"
  -> callback 拼接字符串，再调用更外层 callback
  -> 更外层打印

协程写法
  -> outer 把自己的续体 O 交给 inner，I.completion = O
  -> inner 等待完成，I 恢复并返回 "done"
  -> 运行库把结果交给 O，O.invokeSuspend 从 label = 1 继续
  -> 拼接后返回，再沿 completion 交给外层续体
  -> 外层恢复后打印
```

| 对照点 | 普通 callback API | Kotlin 协程 |
|---|---|---|
| 后续代码怎么表达 | 手写回调函数或回调链 | 写顺序代码，编译器拆成状态机 |
| 等待期间保存变量 | 闭包捕获变量，也可以手写状态对象 | 编译器保存跨挂起点需要的变量和 label |
| 结果和失败怎么传 | 由 API 约定；也可以使用 Result | Continuation.resumeWith 用 Result 交付成功或失败 |
| 异常处理 | 异步回调后来抛出的异常，通常不在登记调用的 try/catch 栈内 | 通过挂起调用交付的失败回到恢复位置，可按原 try/catch/finally 处理 |
| 取消和任务关系 | 由 API 或框架提供句柄、注销和协调机制 | 正确挂接作用域时由 Job 管理父子取消；执行仍需配合取消 |
| 后续在哪个线程执行 | 由回调 API 或手动派发决定 | 遵循协程上下文和调度规则，不保证一定换线程 |

**注意几个边界：**

- callback 也可以非阻塞、捕获变量、组织复杂流程，不能说只有协程才能实现这些能力。协程主要把这套流程组织工作交给编译器与运行库。
- `suspend` 关键字本身不自动提供取消或线程切换；这些还取决于使用的 API、Job 和调度器。协程也不必然比 callback 更快。
- 把 callback API 包成挂起函数时，底层仍可能使用 callback；需要正确衔接成功、失败和取消。取消协程不意味着底层网络请求或监听器自动停止，适配层要取消请求或注销监听。
- 一次挂起等待通常只接受一次成功恢复或失败交付；持续触发的监听回调通常用 callbackFlow 等流式适配，不能对同一次等待反复 resume。

**进一步理解：不同 lambda 与不同 label 的对应关系。**

普通 callback 通常把不同的后续步骤写成不同 lambda；编译器生成的状态机则可以把这些步骤放进同一个执行对象，用 label 区分恢复入口。它们都在表达“结果就绪后接着做什么”。

```kotlin
// Callback sketch: each waitAsync call invokes its callback once, later.
waitAsync(100) {
    println("A")
    waitAsync(100) {
        println("B")
    }
}
```

同样的顺序流程用协程表达：

```kotlin
delay(100)
println("A")
delay(100)
println("B")
```

对应的状态机教学伪代码：

```java
class StepsState {
    int label = 0;

    Object invokeSuspend(Object result) {
        switch (label) {
            case 0:
                throwOnFailure(result);
                label = 1;
                result = delay(100, this);
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                // Fall through only if the first wait completed immediately.
            case 1:
                throwOnFailure(result);
                System.out.println("A");
                label = 2;
                result = delay(100, this);
                if (result == COROUTINE_SUSPENDED) {
                    return COROUTINE_SUSPENDED;
                }
                // Fall through only if the second wait completed immediately.
            case 2:
                throwOnFailure(result);
                System.out.println("B");
                return Unit.INSTANCE;
            default:
                throw new IllegalStateException("Invalid label");
        }
    }
}
```

waitAsync 是示意回调 API；状态机中的 delay(100, this) 表示传入续体的 JVM 调用形式。这里省略 completion 和运行库桥接。真正挂起就 return；立即完成则贯穿到下一个 case，不靠 while 再次匹配 label。

| callback 写法 | 状态机写法 |
|---|---|
| 第一个 lambda 的后续步骤 | label = 1：打印 A、发起第二次等待 |
| 第二个 lambda 的后续步骤 | label = 2：打印 B、完成 |
| lambda 捕获后续需要的变量 | 状态机对象保存跨挂起点需要的字段 |
| 调用对应 callback | 恢复续体，进入相应状态分支 |

```text
callback：第一次等待完成 -> 调用第一个 lambda -> 第二次等待完成 -> 调用第二个 lambda
状态机：第一次等待完成 -> 恢复 label = 1 -> 第二次等待完成 -> 恢复 label = 2
```

因此，可以把 invokeSuspend 类比为恢复时执行的回调主体，但不能认为“callback 无法控制执行内部哪部分代码”。callback 用“调用哪个回调”区分步骤，状态机用“进入哪个 label”区分步骤；手写 callback 也能使用带 label 的状态对象。

“将 lambda 换成续体对象”是便于理解的类比，不是严格的一对一替换：lambda 在 JVM 上也可能表现为对象；挂起 lambda 的生成对象还可以同时承担函数对象和续体的职责。不是每个 callback 都是 lambda，也不是每个 suspend 函数都必须生成独立状态机。

**本节总结：** 你看到的 completion 链，确实很像“回调通知上一层”。区别主要是你不必手写每段回调：编译器把后续步骤和跨挂起点变量转换成状态机，替你管理恢复位置；运行库推进恢复，并通过相关协程 API 组织调度、异常和取消。不要把这些能力全部归到 Continuation 一个接口上。

<a id="必要边界"></a>
###### 只补充几个必要边界

- **不一定真正挂起：** delay(0) 或结果已就绪时可能直接返回；伪代码继续后面的分支，不需要等一次恢复。循环中的同一个挂起点也可以复用同一恢复位置，不是每轮新增一个状态。
- **不一定每层都有独立续体：** `suspend fun outer() = inner()` 这样的尾调用可能直接转交调用方续体，不再生成 OuterState。状态机对象也不等于新线程。
- **withContext：** 把例子二的 inner 工作换成 `withContext(Dispatchers.IO) { ... }`，仍是等内部工作完成后继续；它额外负责上下文切换和恢复安排。块内如果执行 File.copyTo，复制仍会阻塞 IO 工作线程。恢复在哪执行由调度规则决定，不保证总在回调线程或原物理线程。
- **runBlocking：** 示例入口会阻塞调用线程直到协程整体完成；不能把内部挂起理解为 main 已经返回。
- **生成代码入口：** 挂起 lambda 常见结构中 create 创建本次执行实例，invoke 是函数对象入口，invokeSuspend 是状态机执行入口；恢复复用原执行实例。Function2 常对应作用域接收者和 Continuation 两个参数。初始代码块对象的 completion 可为 null，启动时再接上真实完成链；不代表执行时没有续体。

更底层的字段编号、原子竞争和调度类不属于本页主线。label 与一次等待内部的挂起/恢复决策状态是两套概念。需要查实现时可参考下方材料，而不用先掌握它们才能理解两个例子。
