###### 使用场景

<a id="伪代码四个关键点"></a>
###### 入门主线：只抓四个关键点

先忽略源码里的原子操作、最高位标记和调度包装。下面依据后文已核对的源码抽出教学伪代码，**不是可以复制运行的 Kotlin，也不是完整的取消与并发实现**。先假设两次延时都确实挂起，且没有取消。

| 先记住的动作 | 真实源码对应 | 暂时怎么理解 |
|---|---|---|
| 保存进度 | 生成续体的 label、L$0、I$0 等字段 | 用一个对象记住下次执行哪段、还需要哪些变量 |
| 暂时返回 | getResult() 与 COROUTINE_SUSPENDED 检查 | 返回“还没完成”的标记，不能执行下一行业务 |
| 到时间再通知 | DelayedResumeTask.run() 与 resume | 定时任务拿着原来的进度对象，请它继续 |
| 继续或交付结果 | invokeSuspend 与 BaseContinuationImpl.resumeWith | 按进度继续；又挂起就先退出，完成才通知调用方 |

同一个例子，用更短的打印代替前文详细日志：

```kotlin
suspend fun greeting(id: Int): String {
    val prefix = "user-$id"
    println("A")
    delay(100)
    val score = id + 10
    println("B")
    delay(100)
    return "$prefix:$score"
}

// 在协程中调用：
val answer = greeting(7)
println(answer) // 最终是 user-7:17
```

人为把它划成三段：0 是第一次 delay 前，1 是两次 delay 之间，2 是第二次 delay 后。**状态编号表示执行位置，不表示这段代码执行了多少次，也不表示线程号。**

<a id="伪代码保存进度"></a>
###### 伪代码一：把函数拆成三段，用对象保存进度

```text
进度对象：
    下一段 = 0
    id = 7
    prefix = 尚未计算
    score = 尚未计算
    调用方 = 等待 greeting 结果的外层续体

执行一段(进度, 本次恢复结果)：
    如果本次恢复结果是异常：按原代码的异常路径处理

    根据 进度.下一段 选择入口：
        0：
            进度.prefix = "user-" + 进度.id
            打印 A
            进度.下一段 = 1
            结果 = 等待100毫秒(进度)
            如果结果是 挂起标记：返回 挂起标记
            否则直接继续第 1 段

        1：
            进度.score = 进度.id + 10
            打印 B
            进度.下一段 = 2
            结果 = 等待100毫秒(进度)
            如果结果是 挂起标记：返回 挂起标记
            否则直接继续第 2 段

        2：
            返回 进度.prefix + ":" + 进度.score
```

注意两处顺序：先保存下一段编号，再进入等待；等待返回挂起标记，就立刻退出本次执行。伪代码中的“直接继续”表示没有挂起时的贯穿执行，不是每个分支结束后都重新启动协程。

变量从普通局部变量变成进度对象中的字段，所以离开当前调用栈后仍能找回。真实编译器决定具体保存哪些字段，上面为教学把 id、prefix、score 都显式放入对象。

<a id="伪代码等待与通知"></a>
###### 伪代码二：等待并不是停在原地，而是约好以后再叫我

真实 delay 的主干是“注册定时恢复 + getResult 判断是否挂起”。本例确定异步完成时，可先简化成：

```text
等待100毫秒(进度)：
    注册定时任务：
        时间到且被调度执行时：
            请求恢复(进度, 成功(Unit))

    返回 挂起标记
```

这不是 `sleep(100)`，不是循环检查时间，也不是在当前函数里等够 100ms 再返回。它先登记后续动作，再立即返回标记。

此时 greeting 的生成代码收到标记，也返回标记；外层调用 greeting 的生成代码同样识别标记并退出，**不会马上执行 println(answer)**。最终这条执行链让出执行权，线程可以做别的事。

定时任务保存着恢复所需的引用，所以系统知道以后要恢复谁。等待期间不是“所有东西都没了”，只是线程上原来这一层层调用已经退出，进度保存在对象里。

真实源码还用原子决策处理“结果先到、取消竞争”等情况；本段只描述注册后确实需要等待的主路径。

<a id="伪代码恢复与返回"></a>
###### 伪代码三：恢复时再次调用入口，但不会从头执行

把源码的 resumeWith、invokeSuspend 和 completion 组合起来看：

```text
请求恢复(进度, 成功或失败)：
    按上下文的调度规则安排以下动作：
        结果 = 执行一段(原来的进度对象, 成功或失败)

        如果执行一段抛出未处理异常：
            把失败交给调用方
        否则如果结果是 挂起标记：
            退出，等下一次恢复
        否则：
            把真正结果交给调用方，让调用方继续
```

“再次调用入口”不等于重跑全部函数：入口先看下一段编号，编号已经是 1，就跳过 0。因此不会重新创建 prefix，也不会再打印 A。

两次 delay 恢复时送回的是 Unit，表示“这次等待完成”。最终字符串则由第 2 段算出，再交给外层。不要把“delay 返回的值”和“greeting 返回的值”混在一起。

调度规则可能要求入队，也可能允许在当前合适的线程直接继续。此处“安排动作”不保证换线程，也不保证每次都多排一次队。

<a id="伪代码三次进入"></a>
###### 跟着例子走：三次进入，两次挂起，一次最终返回

| 时刻 | 从哪段开始 | 做什么 | 这次退出时留下什么 |
|---|---|---|---|
| 第一次调用 greeting(7) | 0 | prefix=user-7，打印 A，登记第一次延时 | 下一段=1，id=7，prefix=user-7，返回挂起标记 |
| 第一次延时恢复 | 1 | 取回 id，算出 score=17，打印 B，登记第二次延时 | 下一段=2，prefix=user-7，score=17，再次返回挂起标记 |
| 第二次延时恢复 | 2 | 拼接 prefix 和 score | 返回真实值 user-7:17，通知外层继续 |

```text
外层：我要 greeting(7) 的结果
  ↓
第 0 段：打印 A，记住“下次进第 1 段”
  ↓ 返回挂起标记；外层也暂停
第一次计时到 → 恢复同一个进度对象
  ↓
第 1 段：打印 B，记住“下次进第 2 段”
  ↓ 再次返回挂起标记；外层仍没有结果
第二次计时到 → 恢复同一个进度对象
  ↓
第 2 段：返回 user-7:17
  ↓
外层：拿到 answer，现在才执行 println(answer)
```

不是三个协程分别执行三个状态，也不是每次恢复都创建新的业务任务。它是同一个挂起调用的不同执行阶段，每次 delay 有各自的一次等待记录。

<a id="伪代码不挂起与异常"></a>
###### 再对比两个分支：不挂起，以及恢复失败

**没有等待：** 把 delay(100) 改成 delay(0)，等待函数直接返回 Unit。第 0 段发现不是挂起标记，就直接走第 1 段，再直接走第 2 段，在同一次调用里返回字符串。代码有状态机，并不意味着每个调用点都必然暂停。

**等待失败或取消：** 恢复信号携带失败结果，状态机在恢复位置按原来的 try/catch/finally 规则处理，而不是把异常作为正常值继续拼接。没有被本层处理的异常才交给外层；取消是否影响其他任务还由 Job 关系决定。

真正需要先理解的机制只有：**对象保存进度，标记表示“尚未完成”，恢复再次进入正确分支，最终结果才让调用方继续。** 后面的真实源码，是在这条主线上增加调度、取消、竞争和优化。

<a id="挂起恢复的四个概念"></a>
###### 挂起恢复的四个概念

| 概念 | 入门解释 |
|---|---|
| suspend 函数 | 允许通过协程机制暂停和恢复的函数；调用时不一定真的暂停 |
| 挂起 | 当前执行链暂时无法继续，把后续位置和需要的状态保留下来，将执行权交回调用链 / 调度器 |
| Continuation（续体） | 表示“接下来怎么执行”，携带 context，通过 resumeWith 接收成功值或异常 |
| 状态机 | 把跨挂起点的执行分成若干段，用状态编号决定恢复时执行哪一段 |

可以把 Continuation 理解为带有“继续执行入口”的进度记录，但它不是把整个线程栈原样复制一份。编译器把跨挂起点需要保留的局部状态存入对象；实际挂起时调用栈逐层返回，结果就绪后再进入相应恢复入口。

```text
执行第一段 → 保存恢复位置和必要变量 → 发起异步等待
         → 真正挂起并让出执行权
结果就绪 → 恢复续体 → 按调度规则执行下一段
```

状态机负责从哪里继续，Dispatcher 负责在哪里运行，Job 负责是否取消。挂起时线程能做其他工作，不等于线程消失，也不保证整个进程没有其他线程或系统服务在处理请求。

<a id="场景一立即返回"></a>
###### 场景一：有 suspend，但没有真正挂起

```kotlin
suspend fun cachedName(): String = "Alice"

fun main() = runBlocking {
    println("1 开始")
    val name = cachedName()
    println("2 收到 $name")
}
```

输出是“1 开始”“2 收到 Alice”。cachedName 没有等待任何异步条件，会直接返回。

同一个挂起 API 也可能按状态走不同路径：await 遇到已成功完成的 Deferred 可以立即取值，delay(0) 不需要真的等待。调用点是“可能挂起的位置”，不是“必然暂停的位置”。

suspend 不会自动创建线程、启动协程或检查所有取消情况。例如 `suspend fun bad() { Thread.sleep(1000) }` 仍会阻塞执行它的线程。没有跨挂起点状态需要保存的简单函数、尾调用等，编译器可能不生成独立完整状态机。

<a id="场景二一个挂起点"></a>
###### 场景二：delay 时别人能执行，恢复后接着走

```kotlin
fun main() = runBlocking {
    launch {
        println("A1")
        delay(100)
        println("A2")
    }
    launch { println("B") }
}
```

在这个默认 runBlocking 事件循环的示例中，顺序为 A1、B、A2：

1. A 输出 A1，执行 delay，注册延时恢复并挂起。
2. 当前线程可以执行 B，不需要等 A 的时间过去。
3. 延时条件满足后，A 变得可以恢复，实际执行仍需调度。
4. A 从 delay 后继续，输出 A2，不会重新输出 A1。

delay 的 100ms 不是“100ms 时刻必然获得 CPU”，调度繁忙时可以更晚。若改成 Thread.sleep，当前线程被阻塞，在本例的同线程执行环境中 B 也要等。

<a id="场景三多个挂起点与局部变量"></a>
###### 场景三：两个挂起点，变量为什么没有丢

```kotlin
suspend fun loadToken(): String {
    delay(100)
    return "token-123"
}

suspend fun loadName(token: String): String {
    delay(100)
    return "Alice($token)"
}

suspend fun buildGreeting(): String {
    val prefix = "你好"
    val token = loadToken()
    val name = loadName(token)
    return "$prefix，$name"
}

fun main() = runBlocking {
    println(buildGreeting())
}
```

buildGreeting 在逻辑上可划分为：

| 状态          | 要做什么                        | 需要保存或接收什么                |
| ----------- | --------------------------- | ------------------------ |
| S0 首次进入     | 建立 prefix，调用 loadToken      | 保存之后还要用的 prefix，登记下一段 S1 |
| S1 得到 token | 接收 token，调用 loadName(token) | prefix 仍需保留，登记下一段 S2     |
| S2 得到 name  | 拼接字符串并返回                    | 读取 prefix 与本次返回的 name    |

编译器只需保存恢复后仍有用的变量，不是所有局部变量都永远存成字段。token 在传给 loadName 后若不再使用，buildGreeting 的后续状态通常无需继续保存它；loadName 需要的参数由它自己的执行状态处理。

**JVM 签名的概念变化：**

```text
源代码：suspend fun buildGreeting(): String
概念上：Object buildGreeting(Continuation<? super String> completion)
```

为什么 JVM 层看起来返回 Object？因为一次调用可能直接返回结果，也可能返回内部挂起标记 COROUTINE_SUSPENDED。业务 Kotlin 代码仍把成功结果看成 String，不需要自己判断该标记。

下面只表达逻辑，不是可编译代码，也不是反编译结果：

```text
step(incomingResult):
    如果是 S0：
        savedPrefix = "你好"
        state = S1                 // 必须在调用前记录恢复位置
        r = loadToken(thisContinuation)
        如果 r 是 SUSPENDED：返回 SUSPENDED
        否则携带 r 直接进入 S1

    如果是 S1：
        检查 incomingResult 是否为失败，若是则按异常路径抛出
        token = 成功值
        state = S2
        r = loadName(token, thisContinuation)
        如果 r 是 SUSPENDED：返回 SUSPENDED
        否则携带 r 直接进入 S2

    如果是 S2：
        检查 incomingResult 是否为失败
        name = 成功值
        返回 savedPrefix + "，" + name
```

立即返回时可以在同一次调用中连续执行多个状态，不必真的退栈再恢复。真正挂起后，结果通过 Continuation 恢复入口送回来，状态机读取先前保存的位置；成功最终传给等待 buildGreeting 的调用者。

实际 JVM 产物常见 label、result、用于保存变量的字段以及 invokeSuspend 等结构。字段名、编号和优化依编译器版本变化，不要把此处 S0/S1/S2 当成实际字节码约定。

<a id="场景四分支循环与嵌套调用"></a>
###### 场景四：分支、循环和嵌套调用

```kotlin
suspend fun total(): Int {
    var sum = 0
    for (i in 1..3) {
        delay(10)
        sum += i
    }
    return sum
}
```

每次恢复要知道当前循环进度和 sum，因此编译器需要保留这些仍有用的状态。这个循环的 delay 调用点可以重复使用同一个恢复位置，并不需要为每次循环都生成一个独立状态；循环次数由保存的迭代进度决定。

分支也类似：如果命中缓存直接 return，就不会经过网络等待路径；不同分支有不同挂起调用时，状态机记录实际选择的那条路径。不能机械地按代码行数估算状态数量。

```text
页面协程 → buildGreeting → loadToken → delay
```

挂起可以沿调用链逐层返回。delay 就绪后先继续 loadToken，loadToken 返回 token 再继续 buildGreeting，最后页面协程获得完整结果。它们不是每层都开一条线程，也不是从页面函数第一行重新跑。

<a id="场景五await与上下文切换"></a>
###### 场景五：await 和 withContext 也是可能挂起的调用

```kotlin
fun main() = runBlocking {
    val result = async(Dispatchers.Default) {
        delay(100)
        42
    }
    println("任务已安排启动")
    println(result.await())
    println("拿到结果后继续")
}
```

默认 async 已经安排执行，await 在结果未就绪时保存调用方的后续状态并挂起；如果结果已经成功就绪，可以直接返回。不是 await 重新调用 async 代码块。

withContext 换调度器执行一段代码时，调用方也可能挂起等待，代码块结束后按调用方上下文恢复。恢复到原上下文不一定回到原来的工作线程：Default / IO 通常是线程池；Main 则对应主线程。相同调度器等优化路径也可能避免额外调度。

状态机能力让“等待异步结果后继续”可以写成顺序代码；并行执行能力仍取决于任务组织、调度器和内部代码是否阻塞，不能把二者混成同一件事。

<a id="场景六回调如何恢复续体"></a>
###### 场景六：回调通过 Continuation 恢复等待者

下面用纯 Kotlin/JVM 的 suspendCoroutine 演示恢复原理；它不是支持完整取消的生产封装：

```kotlin
import kotlinx.coroutines.*
import kotlin.coroutines.resume
import kotlin.coroutines.suspendCoroutine
import kotlin.concurrent.thread

suspend fun readFromCallback(): String = suspendCoroutine { cont ->
    thread(name = "callback-demo") {
        Thread.sleep(100) // 特意模拟底层工作线程中的阻塞任务
        cont.resume("结果")
    }
}

fun main() = runBlocking {
    println("等待结果")
    val value = readFromCallback()
    println("拿到$value")
}
```

流程是注册异步工作 → 函数等待 → 工作线程调用 resume → 等待者恢复。这里人为创建的线程用于模拟回调来源，suspendCoroutine 本身不会自动创建线程。恢复后代码按协程上下文调度，不保证直接在调用 resume 的线程执行。

如果在 suspendCoroutine 的代码块中同步执行 `cont.resume("缓存")`，结果可能在真正挂起前就准备好了，调用方可直接继续。不能仅凭使用了 suspendCoroutine 就断言一定发生挂起。

生产中的单次回调通常用 suspendCancellableCoroutine，并把取消与底层 cancel / 注销监听连接起来。还要处理：

- 成功与失败回调只能选择一个终态；普通 continuation 重复 resume 属于错误。
- `if (cont.isActive) cont.resume(value)` 不是原子的防重方案，检查后仍可能发生并发回调或取消；需依据库版本使用相应原子恢复 API，或设计明确的回调仲裁协议。
- CancellableContinuation 支持取消与恢复的竞争；即使已经提交恢复，调度执行前的取消仍可能阻止成功值交付，需要按及时取消保证处理资源归属。
- 取消不能靠忽略回调代替底层释放；返回文件、连接等资源时还需处理未交付资源的关闭。

<a id="场景七异常取消和finally"></a>
###### 场景七：恢复时收到异常或取消

续体接收的不只有成功值，也可以是失败。Continuation 的基础入口是 `resumeWith(Result<T>)`；resume 和 resumeWithException 可以理解为提交成功和失败的便捷入口。

```kotlin
suspend fun failingRequest(): String {
    delay(10)
    throw java.io.IOException("网络失败")
}

fun main() = runBlocking {
    try {
        val result = failingRequest()
        println(result) // 失败时不会到这里
    } catch (e: CancellationException) {
        throw e
    } catch (e: java.io.IOException) {
        println("显示错误态")
    } finally {
        println("释放资源")
    }
}
```

恢复调用链时，失败会在相应挂起调用处表现为抛异常，因此原代码的 try/catch/finally 跨挂起仍有效。编译器需要保留正确的控制流，不是恢复后跳过异常处理直接执行下一行。

取消并非“删掉状态机对象就结束”：Job 发出取消信号，可取消的挂起 API 让等待者以 CancellationException 退出，随后执行 finally。CPU 死循环或不配合取消的阻塞调用仍可能继续；finally 中的挂起清理还需考虑 NonCancellable，见 [取消与超时](./协程取消与超时.md#finally与资源释放)。

状态机解释了执行如何继续，不会改变 Job 的父子失败传播规则。async 子任务的异常与 await 处捕获的关系仍需结合 coroutineScope / supervisorScope 分析。

###### 源码逐步分析：从同一个例子走完整条链路

用同一个含两次 delay 的函数，沿“进入 → 保存 → 挂起 → 恢复 → 返回调用方”逐段读关键源码。每一步都回答：谁调用谁、对象里保存了什么、返回的到底是业务结果还是挂起标记。

<a id="section-一个例子贯穿全过程"></a>
###### 一个例子贯穿全过程

```kotlin
import kotlinx.coroutines.*

suspend fun greeting(id: Int, waitMillis: Long): String {
    val prefix = "user-$id"
    println("A before first delay: $prefix")
    delay(waitMillis)
    val score = id + 10
    println("B after first delay: $prefix, score=$score")
    delay(waitMillis)
    val answer = "$prefix:$score"
    println("C after second delay: $answer")
    return answer
}

fun main(args: Array<String>) = runBlocking {
    val waitMillis = args.firstOrNull()?.toLong() ?: 100L
    launch { println("OTHER child ran") }
    println("CALL greeting")
    val answer = greeting(7, waitMillis)
    println("RETURN $answer")
}
```

waitMillis 为 100 时，示例输出：

```text
CALL greeting
A before first delay: user-7
OTHER child ran
B after first delay: user-7, score=17
C after second delay: user-7:17
RETURN user-7:17
```

下面不跳步骤，解释 A 后为什么能执行 OTHER、B 如何找回 prefix，以及 C 的结果如何回到 main。该示例未指定其他 Dispatcher，使用 runBlocking 的事件循环；不能把这里的定时恢复路径直接套给所有 Android Main / IO 调度器。

<a id="生成对象与参数"></a>
###### 第一步：编译器给函数添加了什么

源代码看起来只接收 id 和 waitMillis。JVM 实际方法签名是：

```java
Object greeting(int id, long waitMillis,
                Continuation<? super String> completion)
```

completion 是“greeting 最终完成后，通知谁继续”的入口。这里指向 runBlocking 代码块的续体，而不是某个用户手写回调。

编译器还生成 `StateMachineDemoKt$greeting$1`，继承标准库的 ContinuationImpl。为方便阅读，下面把它命名为 GreetingContinuation，字段名保留实际产物：

```java
// 生成类的等价还原；省略注解、类型强转。
class GreetingContinuation extends ContinuationImpl {
    int I$0;       // 此版本用来保存 id
    int I$1;       // 保存 score
    long J$0;     // 保存 waitMillis
    Object L$0;   // 保存 prefix
    Object result;// 本次恢复带来的成功值或内部失败表示
    int label;    // 下一次恢复应进入哪个分支

    GreetingContinuation(Continuation completion) {
        super(completion); // 保存“本函数结束后交给谁”
    }

    Object invokeSuspend(Object incoming) {
        result = incoming;
        label |= Integer.MIN_VALUE;
        return greeting(0, 0L, this);
    }
}
```

第一次进入 greeting 时，创建这个对象，label 默认是 0。恢复时使用的是同一个对象，而不是清空状态后重新建一个。

这里 result 不是始终表示 greeting 的最终字符串。等待 delay 时，它接收的是 delay 完成的 Unit；只有 greeting 最终结束后，调用方才收到字符串。一个调用栈层次对应的结果，不要混到另一个层次上。

<a id="label零保存现场"></a>
###### 第二步：label 为 0，先保存现场再调用 delay

先把首次进入时的生成逻辑单独抽出来：

```java
// 生成函数 label == 0 分支的等价还原。
ResultKt.throwOnFailure(c.result);
String prefix = "user-" + id;
println("A before first delay: " + prefix);

c.L$0 = prefix;       // "user-7"
c.I$0 = id;           // 7
c.J$0 = waitMillis;   // 100
c.label = 1;         // 下一次恢复应到第一次 delay 后

Object r = DelayKt.delay(waitMillis, c);
if (r == COROUTINE_SUSPENDED) {
    return COROUTINE_SUSPENDED;
}
// 没有真正挂起，则直接继续第一次 delay 后的代码。
```

注意保存顺序：**先把 label 改为 1，再调用可能挂起的函数**。这样底层产生恢复信号时，续体已经知道下一步去哪。

此时现场是：

```text
c.label = 1
c.L$0   = "user-7"
c.I$0   = 7
c.J$0   = 100
c.completion = 外层 main 的挂起代码块
```

label 不是线程编号、Job 状态或循环次数；它只是当前函数控制流的恢复位置。保存到对象中的字段属于堆上的对象状态，原来的线程栈随后可以退出。

本次字节码在第二个挂起点还保留了后续业务不再需要的 id、waitMillis。应理解为“编译器保存其生成策略要求的变量”，不能断言每个版本都只保留理论上的最小变量集。

<a id="delay注册等待"></a>
###### 第三步：delay 源码没有 sleep，而是注册一个恢复动作

**库源码：kotlinx-coroutines 1.10.2，Delay.kt 第 121–128 行。**

```kotlin
public suspend fun delay(timeMillis: Long) {
    if (timeMillis <= 0) return
    return suspendCancellableCoroutine sc@ { cont: CancellableContinuation<Unit> ->
        if (timeMillis < Long.MAX_VALUE) {
            cont.context.delay.scheduleResumeAfterDelay(timeMillis, cont)
        }
    }
}
```

一行一行看：

1. 时间不大于 0：直接返回 Unit，不进入等待流程。这是“suspend 不一定挂起”的具体分支。
2. 正数时间：进入 suspendCancellableCoroutine，得到一个支持取消的续体包装对象 cont。
3. scheduleResumeAfterDelay：把“到时间后恢复 cont”注册给定时设施，不是在这一行睡够时间。
4. Long.MAX_VALUE 是特殊等待场景，不安排这个定时任务；本例使用 100，不走该分支。

同文件第 149 行说明定时能力从哪里来：

```kotlin
internal val CoroutineContext.delay: Delay
    get() = get(ContinuationInterceptor) as? Delay ?: DefaultDelay
```

优先使用上下文中的拦截器所提供的 Delay 能力，否则用默认实现。本例 runBlocking 的事件循环提供了它；Android Main 等环境可能走不同具体实现。

<a id="续体包装与挂起判断"></a>
###### 第四步：谁真正决定返回挂起标记

**库源码：CancellableContinuation.kt 第 423–435 行，省略原注释。**

```kotlin
public suspend inline fun <T> suspendCancellableCoroutine(
    crossinline block: (CancellableContinuation<T>) -> Unit
): T = suspendCoroutineUninterceptedOrReturn { uCont ->
    val cancellable = CancellableContinuationImpl(
        uCont.intercepted(), resumeMode = MODE_CANCELLABLE
    )
    cancellable.initCancellability()
    block(cancellable)
    cancellable.getResult()
}
```

这里有三层对象，不是三个业务任务：

```text
CancellableContinuationImpl（本次 delay 的等待、取消与结果）
  → DispatchedContinuation（按上下文恢复的包装）
    → GreetingContinuation c（greeting 的 label 和变量）
      → completion：main 代码块的续体
```

- uCont：本次挂起调用收到的原始续体，本例对应 greeting 的恢复位置。
- intercepted()：通过 ContinuationInterceptor 为恢复过程加上调度能力，常得到 DispatchedContinuation。
- initCancellability()：接入上下文 Job 的取消通知，不是创建一个 launch 子任务。
- block(cancellable)：执行上一步 delay 传入的“注册定时任务”逻辑。
- getResult()：查看等待是否已经完成；还没完成才返回 COROUTINE_SUSPENDED。

**库源码：CancellableContinuationImpl.kt 第 269–285 行。**

```kotlin
private fun trySuspend(): Boolean {
    _decisionAndIndex.loop { cur ->
        when (cur.decision) {
            UNDECIDED -> if (this._decisionAndIndex.compareAndSet(
                cur, decisionAndIndex(SUSPENDED, cur.index)
            )) return true
            RESUMED -> return false
            else -> error("Already suspended")
        }
    }
}

private fun tryResume(): Boolean {
    _decisionAndIndex.loop { cur ->
        when (cur.decision) {
            UNDECIDED -> if (this._decisionAndIndex.compareAndSet(
                cur, decisionAndIndex(RESUMED, cur.index)
            )) return true
            SUSPENDED -> return false
            else -> error("Already resumed")
        }
    }
}
```

这是一套**“挂起和结果就绪谁先发生”的原子决策状态**，不要与业务函数的 label=0/1/2 混淆。CAS（compareAndSet）表示只有当前状态仍是预期值时才更新，解决两个线程竞争的问题。

getResult 的主要分支如下；这是库源码节选，省略可复用续体和父取消句柄安装的细节：

```kotlin
internal fun getResult(): Any? {
    val isReusable = isReusable()
    if (trySuspend()) {
        // 原实现还安装 / 维护取消句柄和可复用续体。
        return COROUTINE_SUSPENDED
    }
    // 原实现还处理可复用续体。
    val state = this.state
    if (state is CompletedExceptionally)
        throw recoverStackTrace(state.cause, this)
    // 原实现在可取消模式检查 context[Job]，已取消则抛取消异常。
    return getSuccessfulResult(state)
}
```

本例在 100ms 尚未到期时执行 getResult，trySuspend 把 UNDECIDED 改为 SUSPENDED，返回挂起标记。至此不是“线程被挂起”，而是这次函数调用返回了一个特殊对象，告诉上层“结果稍后给你”。

<a id="标记逐层返回"></a>
###### 第五步：挂起标记逐层返回，调用线程才能执行别的任务

greeting 看见 delay 返回的标记，马上原样返回。它的调用者 main 代码块也有编译器生成的状态机：

```java
// main 的生成代码等价节选。
mainContinuation.label = 1;
Object r = greeting(7, waitMillis, mainContinuation);
if (r == COROUTINE_SUSPENDED) {
    return COROUTINE_SUSPENDED;
}
// 只有拿到真实结果才会执行 println("RETURN ...")。
```

因此退出方向是：

```text
getResult 返回标记
  → delay 返回标记
  → greeting 返回标记
  → main 的挂起 lambda 返回标记
  → 这段调用栈结束，返回运行协程的基础设施
```

没有任何一层把标记当成 String 打印；每层生成代码都先检查它。普通线程栈退出后，进度仍由堆上的续体对象保存。

本例 runBlocking 的调用线程仍受 runBlocking 阻塞式等待控制，但它能通过事件循环执行其他协程：

**库源码：Builders.kt 的 joinBlocking 循环节选。**

```kotlin
while (true) {
    val parkNanos = eventLoop?.processNextEvent() ?: Long.MAX_VALUE
    if (isCompleted) break
    parkNanos(this, parkNanos)
    if (Thread.interrupted()) cancelCoroutine(InterruptedException())
}
```

processNextEvent 可以取出之前排队的 OTHER 子协程执行，所以 A 和 B 之间出现 OTHER。没有可执行任务时，runBlocking 的等待线程可能 park；这是阻塞式桥接入口的等待策略，不是每个 delay 都独占一条睡眠线程。

<a id="定时器保存谁"></a>
###### 第六步：等待期间谁持有续体，时间到了谁调用恢复

**库源码：EventLoop.common.kt 第 227–240 行，省略注释。**

```kotlin
override fun scheduleResumeAfterDelay(
    timeMillis: Long, continuation: CancellableContinuation<Unit>
) {
    val timeNanos = delayToNanos(timeMillis)
    if (timeNanos < MAX_DELAY_NS) {
        val now = nanoTime()
        DelayedResumeTask(now + timeNanos, continuation).also { task ->
            schedule(now, task)
            continuation.disposeOnCancellation(task)
        }
    }
}
```

DelayedResumeTask 保存到期时间和 cont。schedule 安排到延时任务队列；disposeOnCancellation 则把取消与移除定时任务关联起来。

**同文件第 255–266 行和第 493–498 行。**

```kotlin
override fun processNextEvent(): Long {
    if (processUnconfinedEvent()) return 0
    enqueueDelayedTasks()
    val task = dequeue()
    if (task != null) {
        platformAutoreleasePool { task.run() }
        return 0
    }
    return nextTime
}

private inner class DelayedResumeTask(
    nanoTime: Long,
    private val cont: CancellableContinuation<Unit>
) : DelayedTask(nanoTime) {
    override fun run() { with(cont) { resumeUndispatched(Unit) } }
    override fun toString(): String = super.toString() + cont.toString()
}
```

enqueueDelayedTasks 把到期的任务送入可执行队列，然后某次 task.run 调用恢复动作。时间到只意味着可以安排执行，不承诺那个瞬间立即获得 CPU。

这里明确能回答“谁还记得我”：**定时任务持有可取消续体，续体的包装链持有 greeting 的状态对象，状态对象持有调用方 completion。** 它不是 JVM 自动猜到应该回到哪一行。

<a id="恢复从运行库到状态机"></a>
###### 第七步：恢复信号怎样走到 invokeSuspend

本例已经在相应事件循环执行到期任务，可以走不重复派发的恢复路径。

**库源码：CancellableContinuationImpl.kt 第 594–597 行。**

```kotlin
override fun CoroutineDispatcher.resumeUndispatched(value: T) {
    val dc = delegate as? DispatchedContinuation
    resumeImpl(value, if (dc?.dispatcher === this) MODE_UNDISPATCHED else resumeMode)
}
```

resumeImpl 通过原子状态更新保存成功结果，并调用 dispatchResume。这里成功结果是 Unit，不是 greeting 的字符串。

**同文件第 467–470 行。**

```kotlin
private fun dispatchResume(mode: Int) {
    if (tryResume()) return // 在 getResult 决定挂起之前就完成，无需另派恢复
    dispatch(mode)
}
```

前面已经是 SUSPENDED，tryResume 返回 false，于是继续恢复。DispatchedTask 的 dispatch / resume 根据 MODE_UNDISPATCHED 等决定是否再次投递；本例最终进入下列源码：

```kotlin
// DispatchedContinuation.kt 第 235–238 行
internal inline fun resumeUndispatchedWith(result: Result<T>) {
    withContinuationContext(continuation, countOrElement) {
        continuation.resumeWith(result)
    }
}
```

这里 continuation 是底层生成的 GreetingContinuation。resumeWith 是它从 BaseContinuationImpl 继承的方法，而不是直接调用某一行业务代码。

其他调度器环境可能需要先 dispatch 到对应线程再执行这个恢复链，所以“调用 resume”不等于“总在回调线程继续”，也不等于“永远重新排队”。

<a id="标准库恢复循环"></a>
###### 第八步：BaseContinuationImpl 如何推进本层和调用方

**标准库真实源码：Kotlin 2.2.0，ContinuationImpl.kt 第 21–51 行，下面仅省略调试探针和注释。**

```kotlin
public final override fun resumeWith(result: Result<Any?>) {
    var current = this
    var param = result
    while (true) {
        with(current) {
            val completion = completion!!
            val outcome: Result<Any?> = try {
                val outcome = invokeSuspend(param)
                if (outcome === COROUTINE_SUSPENDED) return
                Result.success(outcome)
            } catch (exception: Throwable) {
                Result.failure(exception)
            }
            releaseIntercepted()
            if (completion is BaseContinuationImpl) {
                current = completion
                param = outcome
            } else {
                completion.resumeWith(outcome)
                return
            }
        }
    }
}
```

这段是串起整个恢复过程的关键：

1. 先调用当前层的 invokeSuspend，把本次结果交给状态机。
2. 如果当前层又挂起：立即 return，不能提前通知调用者“已经成功”。
3. 如果当前层真正返回业务值：包装成成功结果；如果抛异常：包装成失败结果。
4. 释放当前层的拦截包装，并把结果交给 completion。
5. completion 也是生成续体时，在 while 循环中继续推进，避免简单递归层层 resumeWith。

第一次 delay 恢复后，greeting 会执行到第二次 delay 再次挂起，于是本段第 2 步返回，main 还不能打印 RETURN。第二次 delay 恢复后 greeting 才返回字符串，进入第 3–5 步，让 main 继续。

<a id="恢复label一与二"></a>
###### 第九步：label 为什么不会从 0 开始，变量怎样还原

回到第一步生成的 invokeSuspend：

```java
result = incoming;
label |= Integer.MIN_VALUE;
return greeting(0, 0L, this);
```

第一次恢复时 label 原为 1，按位或最高位后变成带“恢复进入”标记的整数。greeting 入口识别这个对象类型及最高位，去掉标记，复用当前对象，label 又是 1。没有恢复标记的首次调用则创建新对象。

这里传入 0、0L 不是把原参数改成 0：进入恢复分支后，会从 I$0、J$0 等字段恢复原值。位标记是此版本编译器的内部进入协议，不是取消标记。

```java
// 生成函数 label == 1 分支的等价还原。
waitMillis = c.J$0;       // 100
id = c.I$0;               // 7
prefix = (String)c.L$0;   // user-7
ResultKt.throwOnFailure(c.result);

int score = id + 10;     // 17
println("B after first delay: " + prefix + ", score=" + score);
c.L$0 = prefix;
c.I$0 = id;
c.J$0 = waitMillis;
c.I$1 = score;
c.label = 2;
Object r = DelayKt.delay(waitMillis, c);
if (r == COROUTINE_SUSPENDED) return COROUTINE_SUSPENDED;
// 立即返回则直接进入第二次 delay 后的代码。
```

第二次 delay 是新的可取消等待对象，但 greeting 仍用同一个状态机对象 c。挂起期间的新现场是：

```text
label=2, L$0="user-7", I$0=7, J$0=100, I$1=17
```

第二次到期再次 resumeWith → invokeSuspend → greeting，恢复分支为 2：

```java
score = c.I$1;
waitMillis = c.J$0;
id = c.I$0;
prefix = (String)c.L$0;
ResultKt.throwOnFailure(c.result);
String answer = prefix + ":" + score;
println("C after second delay: " + answer);
return answer; // 这次是真实字符串，不是挂起标记
```

BaseContinuationImpl 收到真实字符串，推进 completion，也就是 main 的状态机。main.label 为 1，在 greeting 调用之后取出字符串，打印 RETURN。所谓“恢复执行”，就是这条明确的分支和调用链。

<a id="立即返回与恢复竞争"></a>
###### 第十步：两个容易混淆的“不挂起”场景

**场景 A：delay(0)。** 第三步的 `if (timeMillis <= 0) return` 直接返回 Unit，不创建这次可取消等待对象。生成函数看到不是挂起标记，就沿当前调用栈继续执行 B、C，而不是先退栈再 resume。

示例传 0 时输出：

```text
CALL greeting
A before first delay: user-7
B after first delay: user-7, score=17
C after second delay: user-7:17
RETURN user-7:17
OTHER child ran
```

OTHER 没有在 A、B 之间执行，因为这次 greeting 没有真正让出执行权。main 代码块返回后，runBlocking 还会等待子任务，所以 OTHER 最后仍能执行。

**场景 B：回调在 getResult 之前就返回。** 例如把缓存接口包装成 suspendCancellableCoroutine，注册时就同步回调成功：

```kotlin
suspend fun cached(): String = suspendCancellableCoroutine { cont ->
    cont.resumeWith(Result.success("cached"))
}
```

它经过包装对象，但结果抢先就绪。第四步的决策状态说明了为什么不会重复恢复：

| 谁先到 | 决策路径 | 后续行为 |
|---|---|---|
| getResult 先到 | trySuspend：UNDECIDED → SUSPENDED | 返回挂起标记，后到的恢复负责推进续体 |
| 恢复先到 | tryResume：UNDECIDED → RESUMED | dispatchResume 提前返回；getResult 直接取成功值，不再挂起 |

这不是业务 label 的 0→1→2，而是每次等待的竞争协议。还需区分保存成功 / 异常 / 取消的结果状态，以及 Job 的生命周期状态；几种“状态”各有职责。

<a id="异常取消如何进入"></a>
###### 第十一步：如果恢复带来异常，为什么原来的 catch 仍有效

前面恢复分支都有 `ResultKt.throwOnFailure(c.result)`。成功 Unit 时它继续；收到失败表示时它抛出对应异常，因此恢复不会把失败当成正常值执行后续业务。

```kotlin
try {
    delay(100)
    println("延时正常结束")
} catch (e: CancellationException) {
    println("收到取消")
    throw e
} finally {
    println("清理")
}
```

编译器保留原来的异常控制流，所以在恢复位置抛出的取消仍会进入适当的 catch / finally。上面的主例没有这些块，不能拿它的字节码当成本段 try/finally 示例的反编译证据；此处说明的是异常传递机制。

取消时 CancellableContinuation 与 Job 的连接可以让等待提前以失败结束，并处置定时任务；恢复路径还要按取消模式处理竞争。不能理解成取消只把对象删掉，或每次取消都必须等待计时到期。

BaseContinuationImpl 外层的 try/catch 则把未在本层处理的异常包装后交给 completion。它不负责决定兄弟协程是否取消；那属于 Job 与协程构建器的失败传播规则。
