### Android TV 焦点和遥控器知识点清单

###### 内容概述

本文件记录 Android TV 焦点和遥控器相关知识，包括焦点基础、焦点搜索、默认焦点下发、焦点恢复、遥控器按键、列表焦点、弹窗焦点和常见坑。

###### 使用场景

- TV 页面首次进入、返回页面、列表刷新、弹窗关闭、播放器控制层显示隐藏时，都需要处理焦点。
- 遥控器按键响应、焦点丢失、焦点乱跳、按确认键无效等问题，都需要从本文件的机制入手排查。
- 面试中经常会问 TV 焦点机制、焦点丢失原因、遥控器 KeyEvent 分发和列表焦点处理方案。

<a id="焦点基础"></a>
###### 焦点基础

- TV 端的焦点可以理解为“当前遥控器操作目标”。用户按方向键移动焦点，按确认键触发当前焦点 View。
- 焦点不是选中态。焦点表示当前能接收按键事件的控件；选中态通常表示业务状态，例如当前 Tab、当前清晰度、当前分类。
- 焦点态要有明显 UI 反馈，例如放大、描边、阴影、背景变化、文字颜色变化。
- 一个页面应尽量保证任意时刻都有合理焦点。没有焦点时，用户按方向键或确认键可能无响应。
- 焦点变化通常可以监听 `View.OnFocusChangeListener`。

```java
view.setOnFocusChangeListener((v, hasFocus) -> {
    v.setSelected(hasFocus);
});
```

- 点击事件和焦点事件要分清。`onFocusChange` 只表示焦点变化，不应该直接触发业务跳转；确认键或点击才应该触发进入详情、播放等动作。

<a id="可获得焦点的条件"></a>
###### 可获得焦点的条件

- View 想获得焦点，通常需要满足：可见、可用、可 focus、尺寸有效、在当前窗口内、没有被父容器拦截。
- 常见属性：

| 属性 / 方法 | 作用 |
|---|---|
| `android:focusable="true"` | 允许 View 获得焦点 |
| `android:focusableInTouchMode="true"` | 触摸模式下也允许获得焦点，TV 场景不应滥用 |
| `view.setFocusable(true)` | 代码中设置可获得焦点 |
| `view.requestFocus()` | 主动请求焦点 |
| `view.clearFocus()` | 清除焦点 |
| `view.hasFocus()` | 判断自身或子 View 是否有焦点 |
| `view.isFocused()` | 判断当前 View 自己是否有焦点 |

- `visibility=GONE` 或 `INVISIBLE` 的 View 不能正常获得焦点。
- `enabled=false` 的控件通常不能获得焦点，也不会响应点击。
- 父容器如果设置了不允许子 View 获得焦点，可能导致子控件无法聚焦。
- RecyclerView item 的根布局通常要设置可聚焦，内部按钮是否可聚焦要看交互设计。一个 item 内多个可聚焦控件会增加焦点路径复杂度。

<a id="焦点搜索"></a>
###### 焦点搜索

- 用户按方向键时，系统会从当前焦点出发，根据方向和候选 View 的位置寻找下一个焦点。
- 默认焦点搜索不一定符合业务预期，尤其是网格、横竖嵌套列表、瀑布流、浮层、吸顶导航等复杂布局。
- 可以通过 `nextFocusLeft`、`nextFocusRight`、`nextFocusUp`、`nextFocusDown` 指定某个方向的下一个焦点。

```xml
<TextView
    android:id="@+id/btn_confirm"
    android:focusable="true"
    android:nextFocusRight="@id/btn_cancel" />
```

- `nextFocus` 适合稳定布局。如果目标 View 会动态创建、列表 item 会复用，硬写 id 可能不稳定。
- 自定义容器可以重写 `focusSearch()` 或 `onRequestFocusInDescendants()` 控制焦点搜索和子 View 优先级。
- 对于 RecyclerView，焦点搜索还会受到 LayoutManager、item 是否已布局、滚动状态、复用状态影响。
- 焦点搜索异常时，要先明确当前焦点是谁、方向键是什么、系统找到的候选 View 是谁、候选 View 是否可见可聚焦。

<a id="默认焦点下发"></a>
###### 默认焦点下发

- 默认焦点下发指页面首次进入或某个区域加载完成后，把焦点主动交给一个合理的 View。
- 常见默认焦点目标：页面第一个可操作按钮、当前 Tab、推荐列表第一个卡片、上次停留的 item、播放器控制层的播放暂停按钮。
- 不要在 View 还没布局、数据还没加载、RecyclerView item 还没创建时立即 `requestFocus()`，这通常会失败。
- 常用时机：

| 时机 | 适用场景 |
|---|---|
| `view.post { requestFocus() }` | 等待当前 View 完成一次布局后请求焦点 |
| 数据提交完成回调 | 列表数据刷新后请求第一个 item 焦点 |
| `RecyclerView.OnChildAttachStateChangeListener` | item 真正 attach 后下发焦点 |
| `doOnPreDraw` / 布局完成回调 | 需要等布局尺寸和位置稳定后再下发 |
| 页面恢复回调 | 返回页面时恢复上次焦点 |

- 焦点下发前要判断目标是否可聚焦、可见、已 attach、没有被遮挡、父容器没有拦截。
- 默认焦点只能兜底，不应该反复抢焦点。频繁 `requestFocus()` 会让用户手动移动焦点后又被拉回去。
- 如果页面有弹窗或加载态，默认焦点要等弹窗关闭、加载态结束后再下发到真正内容区。

普通 View 的默认焦点可以封装成只执行一次的下发逻辑：

```kotlin
class TvDefaultFocusDelegate {
    private var hasDispatched = false

    fun requestOnce(target: View?) {
        if (hasDispatched || target == null) return

        target.post {
            if (target.canTakeFocus()) {
                hasDispatched = target.requestFocus()
            }
        }
    }

    fun reset() {
        hasDispatched = false
    }
}
```

页面里使用：

```kotlin
private val defaultFocus = TvDefaultFocusDelegate()

override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    retryButton.setOnClickListener { viewModel.reload() }

    viewLifecycleOwner.lifecycleScope.launch {
        repeatOnLifecycle(Lifecycle.State.STARTED) {
            viewModel.uiState.collect { state ->
                render(state)

                if (state is UiState.Success) {
                    defaultFocus.requestOnce(firstCardView)
                } else if (state is UiState.Error) {
                    defaultFocus.requestOnce(retryButton)
                }
            }
        }
    }
}
```

RecyclerView 的默认焦点不要直接找 position 后马上 `requestFocus()`，更稳的方式是等目标 child 真正出现：

```kotlin
fun RecyclerView.requestFocusWhenChildAttached(
    adapterPosition: Int,
    childFocusTarget: (View) -> View = { it }
) {
    if (adapterPosition == RecyclerView.NO_POSITION) return

    fun tryRequest(): Boolean {
        val holder = findViewHolderForAdapterPosition(adapterPosition) ?: return false
        val target = childFocusTarget(holder.itemView)
        return target.canTakeFocus() && target.requestFocus()
    }

    if (tryRequest()) return

    addOnChildAttachStateChangeListener(object : RecyclerView.OnChildAttachStateChangeListener {
        override fun onChildViewAttachedToWindow(view: View) {
            val holder = getChildViewHolder(view)
            if (holder.bindingAdapterPosition == adapterPosition && tryRequest()) {
                removeOnChildAttachStateChangeListener(this)
            }
        }

        override fun onChildViewDetachedFromWindow(view: View) = Unit
    })

    scrollToPosition(adapterPosition)
}
```

<a id="焦点恢复"></a>
###### 焦点恢复

- 焦点恢复指从详情页返回列表页、弹窗关闭、播放器控制层隐藏后，把焦点恢复到用户之前操作的位置。
- 列表焦点恢复通常要保存业务 id 或 adapter position。更推荐保存稳定业务 id，因为 position 可能因为插入、删除、排序变化而改变。
- 返回后要先恢复数据和滚动位置，再请求焦点。否则 item 还没显示出来，焦点恢复会失败。
- RecyclerView 场景可以先 `scrollToPosition()`，等目标 item attach 后再 `requestFocus()`。
- 如果列表刷新后原 item 不存在，要有降级策略，例如聚焦同位置 item、前一个 item、当前行第一个 item 或页面默认焦点。
- 弹窗关闭后，应该恢复到打开弹窗前的焦点 View。如果这个 View 已经不可见或被销毁，则降级到页面默认焦点。
- 播放器控制层隐藏后，焦点要么回到视频区域的根容器，要么保留在控制层逻辑里等待下一次显示，具体取决于交互设计。

保存焦点时优先保存业务 id，同时可以保存弱引用 View 作为弹窗短期恢复使用：

```kotlin
class TvFocusStore {
    var lastContentId: String? = null
        private set

    private var lastView: WeakReference<View>? = null

    fun saveContentFocus(contentId: String, view: View) {
        lastContentId = contentId
        lastView = WeakReference(view)
    }

    fun restoreViewOr(defaultTarget: View) {
        val target = lastView?.get()
        when {
            target.canTakeFocus() -> target?.requestFocus()
            defaultTarget.canTakeFocus() -> defaultTarget.requestFocus()
        }
    }
}
```

弹窗关闭后恢复焦点：

```kotlin
private var focusBeforeDialog: View? = null

fun showDeleteDialog() {
    focusBeforeDialog = requireActivity().window.decorView.findFocus()

    ConfirmDialog()
        .apply {
            onDismissCallback = {
                val oldFocus = focusBeforeDialog
                if (oldFocus.canTakeFocus()) {
                    oldFocus?.requestFocus()
                } else {
                    defaultButton.requestFocus()
                }
            }
        }
        .show(parentFragmentManager, "confirm")
}
```

<a id="遥控器按键"></a>
###### 遥控器按键

- 遥控器按键事件通常经过 Activity、Window、ViewGroup、View 分发，可以在 `dispatchKeyEvent()`、`onKeyDown()`、`onKeyUp()` 或具体 View 的按键监听中处理。
- 常见按键：

| KeyCode | 含义 |
|---|---|
| `KEYCODE_DPAD_UP` | 方向上 |
| `KEYCODE_DPAD_DOWN` | 方向下 |
| `KEYCODE_DPAD_LEFT` | 方向左 |
| `KEYCODE_DPAD_RIGHT` | 方向右 |
| `KEYCODE_DPAD_CENTER` | 确认 |
| `KEYCODE_ENTER` | 确认，部分设备会使用 |
| `KEYCODE_BACK` | 返回 |
| `KEYCODE_MENU` | 菜单 |
| `KEYCODE_MEDIA_PLAY_PAUSE` | 播放 / 暂停 |
| `KEYCODE_MEDIA_FAST_FORWARD` | 快进 |
| `KEYCODE_MEDIA_REWIND` | 快退 |

- 处理确认键时，建议同时考虑 `DPAD_CENTER` 和 `ENTER`。
- 不要在高层无条件消费方向键，否则系统焦点搜索会失效。
- 拦截按键时要明确返回值：返回 `true` 表示消费事件，返回 `false` 表示继续分发。
- 长按会产生重复 key event，要根据 `event.getRepeatCount()` 区分是否重复触发。
- 业务只需要响应按下或抬起之一时，要避免 `ACTION_DOWN` 和 `ACTION_UP` 都执行一次。

Activity 层适合做日志、播放器全局键、返回优先级处理，不适合无条件吞掉方向键：

```kotlin
override fun dispatchKeyEvent(event: KeyEvent): Boolean {
    if (event.action == KeyEvent.ACTION_DOWN) {
        Log.d(
            "TvKey",
            "key=${event.keyCode}, repeat=${event.repeatCount}, focus=${window.decorView.findFocus()}"
        )
    }

    if (playerController.handleGlobalKey(event)) {
        return true
    }

    return super.dispatchKeyEvent(event)
}
```

确认键可以放在可聚焦 View 自己处理，也可以直接依赖 `setOnClickListener`。如果要自己处理，建议只在 `ACTION_UP` 触发业务：

```kotlin
fun View.setTvConfirmAction(action: () -> Unit) {
    setOnKeyListener { _, keyCode, event ->
        val isConfirm = keyCode == KeyEvent.KEYCODE_DPAD_CENTER ||
                keyCode == KeyEvent.KEYCODE_ENTER

        if (isConfirm && event.action == KeyEvent.ACTION_UP) {
            action()
            true
        } else {
            false
        }
    }
}
```

返回键一般按“最上层优先”处理：

```kotlin
override fun onBackPressed() {
    when {
        qualityPanel.isShowing -> qualityPanel.dismiss()
        playerControls.isShowing -> playerControls.hide()
        navController.popBackStack() -> Unit
        else -> finish()
    }
}
```

<a id="焦点工具方法"></a>
###### 焦点工具方法

焦点判断建议集中封装，避免每个页面都漏条件：

```kotlin
fun View?.canTakeFocus(): Boolean {
    return this != null &&
            isShown &&
            isEnabled &&
            isFocusable &&
            isAttachedToWindow
}
```

打印当前焦点路径可以帮助定位焦点落到了哪个层级：

```kotlin
fun Activity.logCurrentFocus(tag: String = "TvFocus") {
    val focus = window.decorView.findFocus()
    Log.d(tag, "current=$focus, id=${focus?.resources?.getResourceEntryName(focus.id)}")
}
```

给一组按钮建立左右循环焦点：

```kotlin
fun linkHorizontalFocus(vararg views: View) {
    views.forEachIndexed { index, view ->
        val left = views[(index - 1 + views.size) % views.size]
        val right = views[(index + 1) % views.size]
        view.nextFocusLeftId = left.id
        view.nextFocusRightId = right.id
    }
}
```

如果某个容器只是展示文案或装饰，不应该参与焦点：

```kotlin
fun View.disableFocusTree() {
    isFocusable = false
    isFocusableInTouchMode = false

    if (this is ViewGroup) {
        descendantFocusability = ViewGroup.FOCUS_BLOCK_DESCENDANTS
        for (index in 0 until childCount) {
            getChildAt(index).disableFocusTree()
        }
    }
}
```

注意：`FOCUS_BLOCK_DESCENDANTS` 会阻止子 View 聚焦，只适合 loading、遮罩、纯展示区域；不要随便加到列表或卡片容器上。

<a id="列表焦点"></a>
###### 列表焦点

- TV 首页常见结构是竖向 RecyclerView 嵌套横向 RecyclerView，每一行是一个频道或栏目，每个 item 是内容卡片。
- 列表焦点问题高发原因：item 复用、数据刷新、滚动过程、动画、图片加载、item 尺寸变化、嵌套列表焦点竞争。
- item 根布局通常要有稳定尺寸，避免焦点放大后改变布局，导致周围 item 被挤动。
- 焦点放大建议用 `scaleX/scaleY` 或外层不参与测量的视觉效果，避免触发布局重新测量。
- 列表刷新时要尽量使用 DiffUtil、稳定 id、局部刷新，减少焦点 View 被重建。
- 如果使用 `notifyDataSetChanged()`，整个列表刷新可能导致当前焦点 View 被 detach，从而焦点丢失。
- 横向列表到下一行的焦点移动要设计清楚：按下时去下一行同列、下一行第一个、还是业务推荐位置。
- 列表滚动时不要让焦点移动到屏幕外不可见 item。必要时要配合滚动到可见区域。
- 对于嵌套 RecyclerView，要避免父列表和子列表同时抢焦点。通常当前行内部 item 获得焦点，父行只负责承载和滚动。

<a id="弹窗和浮层焦点"></a>
###### 弹窗和浮层焦点

- Dialog、PopupWindow、播放控制层、侧边菜单、筛选面板都属于常见浮层焦点场景。
- 弹窗显示后应该把焦点交给弹窗内第一个合理控件，例如确认按钮、关闭按钮或默认选项。
- 弹窗内方向键应尽量在弹窗范围内循环或限制，不要让焦点跑到底层页面。
- 弹窗关闭后要恢复到打开弹窗前的焦点。
- 如果浮层不需要抢焦点，要明确设置不可聚焦或不拦截按键，避免底层页面失去控制。
- 播放器控制层显示时，焦点通常进入控制层；控制层隐藏时，方向键或确认键可能需要重新显示控制层，而不是让焦点丢失。

<a id="常见坑"></a>
###### 常见坑

- 页面没有默认焦点，首次进入后遥控器确认键无效。
- 目标 View 还没 attach 就调用 `requestFocus()`，导致焦点下发失败。
- 加载态或空 View 抢走焦点，内容加载完成后没有转移焦点。
- item 内多个子控件都可聚焦，方向键路径变得不可控。
- 父容器拦截按键后没有继续分发，导致系统焦点搜索失效。
- `notifyDataSetChanged()` 后当前焦点 View 被重建，焦点丢失。
- 焦点放大导致 item 尺寸变化，引起列表抖动和焦点错乱。
- 弹窗关闭后没有恢复焦点，焦点落到底层不可见 View 或直接丢失。
- 页面返回时只恢复 position，没有等 item attach，导致恢复失败。
- 不同遥控器确认键码不同，只处理了 `DPAD_CENTER`，漏掉 `ENTER`。
