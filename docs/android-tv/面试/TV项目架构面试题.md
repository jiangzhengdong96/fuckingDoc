<a id="tv-项目架构和手机项目有什么不同"></a>
###### TV 项目架构和手机项目有什么不同

答案：

**简答：** TV 项目架构要把焦点、遥控器、横屏大屏、播放、列表性能和设备兼容作为核心能力沉淀，而手机项目通常更关注触摸交互、页面栈和多屏尺寸适配。

**展开回答：** TV 端用户所有操作都依赖遥控器和焦点，因此焦点路径、默认焦点、返回恢复、弹窗焦点、播放页控制层都应成为架构关注点。视频类 TV 项目还要把播放器、推荐流、搜索、详情、历史记录、收藏、账号和升级发布拆清楚，避免所有逻辑堆在 Activity 或 Fragment 里。

**易错点：** TV 项目不能只把手机项目横屏化，焦点和播放体验必须被架构显式承载。

**关联知识点：** [TV 和手机端差异](../知识点梳理/TV开发基础.md#tv-和手机端差异)

<a id="tv-项目模块应该怎么拆分"></a>
###### TV 项目模块应该怎么拆分

答案：

**简答：** 可以按基础能力、业务页面和可复用组件拆分，例如 core、network、data、player、common-ui、focus、home、detail、search、profile、settings 等。

**展开回答：** 拆分原则是高复用能力下沉，业务页面保持清晰边界。播放器、焦点工具、遥控器事件、图片加载、网络、数据缓存、日志埋点等可以做成基础模块或公共组件；首页、详情、搜索、播放、设置等业务页面保持各自 ViewModel 和状态。模块拆分不一定越多越好，要看团队规模、构建成本和业务复杂度。

**易错点：** 不要为了“架构好看”过度拆模块，小项目可以先用包结构隔离，等边界稳定后再模块化。

**关联知识点：** [TV 开发基础](../知识点梳理/TV开发基础.md)

<a id="tv-首页架构怎么设计"></a>
###### TV 首页架构怎么设计

答案：

**简答：** TV 首页通常以推荐栏目流为核心，架构上要拆清数据加载、栏目渲染、横竖嵌套列表、焦点保存恢复、分页和错误态。

**展开回答：** 首页可以由 ViewModel 管理整体 UI State，包括 loading、content、error、empty、当前焦点锚点和分页状态。Repository 负责频道、栏目、推荐内容和缓存。UI 层只负责渲染外层栏目和内层卡片，并把焦点变化和点击事件上抛。焦点恢复应基于业务 id，而不是只记 position。

**易错点：** 首页不要让 Adapter 直接请求网络或修改业务状态，Adapter 只负责绑定和事件回调。

**关联知识点：** [TV 列表和焦点性能 - 嵌套列表代码结构](../知识点梳理/TV列表和焦点性能.md#嵌套列表代码结构)

<a id="焦点管理应该放在哪一层"></a>
###### 焦点管理应该放在哪一层

答案：

**简答：** 焦点管理应分层：View 层负责实际 `requestFocus()` 和焦点态，ViewModel 或页面状态保存业务焦点锚点，公共 focus 工具沉淀可复用策略。

**展开回答：** 焦点是 UI 行为，但焦点恢复往往依赖业务 id。比较稳的做法是：ViewHolder 把获得焦点的业务 id 回调给页面；ViewModel 保存 `rowId/contentId/position` 等锚点；数据刷新后 UI 根据锚点找到目标 View 并请求焦点。公共逻辑如默认焦点、弹窗关闭恢复、列表刷新恢复可以沉淀为 focus helper。

**易错点：** 不建议把所有焦点逻辑都写在 Adapter 里，否则页面状态、数据刷新和返回恢复会很难维护。

**关联知识点：** [焦点和遥控器](../知识点梳理/焦点和遥控器.md)

<a id="tv-播放模块怎么设计"></a>
###### TV 播放模块怎么设计

答案：

**简答：** 播放模块要拆分播放器内核、播放状态、控制层 UI、清晰度/字幕/选集、遥控器控制、播放记录和错误恢复。

**展开回答：** 播放器内核可以封装 Media3/ExoPlayer 的初始化、资源释放、播放源切换和事件监听。ViewModel 管理播放状态、选集、清晰度、错误态和控制层显示策略。UI 层负责焦点、遥控器按键和控制层渲染。播放记录、历史进度、收藏和推荐可以通过 Repository 管理。

**易错点：** 播放页不要把播放器事件、UI 控制、数据请求和遥控器按键全写在 Activity 里，否则后续扩展清晰度、字幕、投屏、试看、广告会非常难维护。

**关联知识点：** [TV 媒体播放](../知识点梳理/TV媒体播放.md)

<a id="tv-数据层和缓存怎么设计"></a>
###### TV 数据层和缓存怎么设计

答案：

**简答：** 数据层要区分远端接口、本地缓存、内存状态和 UI 状态，首页推荐、详情、播放记录、收藏、搜索历史等可以按业务建立 Repository。

**展开回答：** TV 首页通常需要快速展示内容，可以先展示本地缓存，再异步刷新远端数据。详情页要处理内容下架、播放源变化、选集更新。播放记录和收藏通常需要本地持久化并同步服务端。数据层不应直接关心焦点和 View，只提供稳定的数据模型和错误结果。

**易错点：** 不要把接口 DTO 直接传到 UI 全链路使用，推荐做领域模型或 UI 模型转换，减少接口变化对页面的影响。

**关联知识点：** [TV 列表和焦点性能 - 预加载和缓存](../知识点梳理/TV列表和焦点性能.md#预加载和缓存)

<a id="遥控器按键事件怎么做架构收敛"></a>
###### 遥控器按键事件怎么做架构收敛

答案：

**简答：** 遥控器事件要有统一分发和页面级处理策略，避免每个 View 随意拦截按键。公共按键、播放页按键、弹窗按键要分清优先级。

**展开回答：** TV 项目常见按键包括方向键、确认、返回、菜单、播放暂停、快进快退。可以在 Activity 或基础 Fragment 中做基础分发，页面根据当前状态处理业务按键。播放页通常有更高优先级，因为方向键和确认键可能同时控制进度条、清晰度弹窗和选集列表。弹窗显示时，要明确是否消费返回键和方向键。

**易错点：** 随意在多个层级重写 `dispatchKeyEvent()` 容易导致按键被重复消费或丢失，要有日志和优先级约定。

**关联知识点：** [焦点和遥控器 - 遥控器按键](../知识点梳理/焦点和遥控器.md#遥控器按键)

<a id="tv-项目如何保证可维护性"></a>
###### TV 项目如何保证可维护性

答案：

**简答：** 通过清晰模块边界、统一 UI 状态、公共焦点工具、播放器封装、稳定数据模型、日志埋点和问题复盘来保证可维护性。

**展开回答：** TV 项目问题通常集中在焦点、播放、列表和兼容性。可维护的架构应该把这些高频问题沉淀成公共能力，而不是每个页面复制一套。比如统一焦点恢复策略、统一播放器事件模型、统一错误态、统一图片加载配置、统一按键日志。每次真实问题修复后，要把复现路径、原因和处理方案回填到问题集。

**易错点：** 架构不是只看分了多少层，而是看高频变化点和高频问题有没有被稳定承载。

**关联知识点：** [Android TV 问题集](../问题集/Android-TV问题集.md)
