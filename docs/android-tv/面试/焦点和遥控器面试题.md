<a id="android-tv-焦点机制怎么理解"></a>
###### Android TV 焦点机制怎么理解

答案：

**简答：** TV 焦点就是遥控器当前操作目标，方向键负责移动焦点，确认键负责触发当前焦点控件。

**展开回答：** 系统会根据当前焦点 View 和方向键做焦点搜索，寻找下一个可聚焦 View。开发时要保证页面有默认焦点、控件可聚焦、焦点态明显、焦点移动路径可预期。复杂布局可以通过 `nextFocus`、自定义焦点搜索、列表焦点恢复等方式控制。

**易错点：** 焦点不是业务选中态，不能只用 selected 替代 focus。

**关联知识点：** [焦点基础](../知识点梳理/焦点和遥控器.md#焦点基础)

<a id="tv-焦点下发源码流程是什么"></a>
###### TV 焦点下发源码流程是什么

答案：

**简答：** TV 焦点流程可以拆成两条线：主动 `requestFocus()` 下发焦点，方向键通过 `focusSearch()` / `FocusFinder` 找下一个焦点；目标成功获得焦点后，父容器通过 `requestChildFocus()` 记录焦点路径。

**展开回答：** 页面默认焦点或焦点恢复时，业务代码通常直接调用目标 View 的 `requestFocus()`，系统会检查目标是否可见、可用、可聚焦、父容器是否允许子 View 聚焦。用户按方向键时，系统会从当前 focused view 出发调用 `focusSearch(direction)`，再通过 `FocusFinder.findNextFocus()` 收集候选并按几何位置选择目标。候选 View 来自 `addFocusables()`。目标 View 成功拿到焦点后，会触发 `onFocusChanged(true)`，并通过 `requestChildFocus()` 沿父链通知各级 `ViewGroup` 更新当前 focused child。

**易错点：** 不要把 `requestFocus()`、`focusSearch()`、`addFocusables()`、`requestChildFocus()` 当成同一类方法。它们分别对应请求焦点、搜索目标、收集候选和父链记录。

**关联知识点：** [TV 焦点下发源码流程](../知识点梳理/TV焦点下发源码流程.md#一次完整方向键流程)

<a id="tv-焦点下发是从哪里开始的"></a>
###### TV 焦点下发是从哪里开始的

答案：

**简答：** 焦点下发通常从业务 `requestFocus()`、方向键默认焦点导航、返回/刷新后的恢复逻辑、Window 或根布局兜底这几个入口开始，不是从 `onRequestFocusInDescendants()` 或 `FocusFinder` 直接开始。

**展开回答：** 页面首次进入时，一般是 Activity / Fragment 等页面代码在 View attach、布局完成或列表数据提交完成后调用 `target.requestFocus()`。返回页、弹窗关闭、列表刷新后，通常也是业务根据上次保存的 View 或业务 id 找到目标，再调用 `requestFocus()`。用户按方向键时，入口是 `KeyEvent` 分发，如果 Activity、父容器、当前 focused View、`OnKeyListener` 都没有消费，系统才进入默认焦点导航，调用 `focusSearch()`，再优先看 `nextFocus*`，最后可能走 `FocusFinder` 几何查找。Window 重新获得焦点或当前焦点失效时，系统也可能从 DecorView / 根 View 做兜底焦点查找，但 TV 列表不要依赖这个兜底。

**易错点：** `onRequestFocusInDescendants()` 是焦点进入某个 `ViewGroup` 后，容器选择内部 child 的扩展点；`FocusFinder` 是方向键搜索候选的算法。它们都不是所有焦点下发的最初入口。

**关联知识点：** [焦点下发从哪里开始](../知识点梳理/TV焦点下发源码流程.md#焦点下发从哪里开始)

<a id="首次进入-activity-时焦点是哪来的"></a>
###### 首次进入 Activity 时焦点是哪来的

答案：

**简答：** 首次进入 Activity 时要区分 Window 焦点和 View 焦点。Window 焦点来自系统窗口管理；真正用于遥控器操作的 View 焦点，是 `DecorView` 下面的 View 树在 attach、Window 获得焦点、首次布局过程中找出来的，或者被业务代码 `requestFocus()` 主动指定。

**展开回答：** Activity 启动后，`setContentView()` 会把布局挂到 `PhoneWindow` 的 `DecorView` 下。Activity resume 后，Window 被加入 `WindowManager`，系统为这棵 View 树创建 `ViewRootImpl`。当 Window 获得焦点并开始首次 measure / layout / draw 时，根 View 才有机会在自己的 View 树中找一个默认可聚焦目标。这个目标可能来自 XML 中第一个可聚焦控件、根布局默认搜索、`ViewGroup` 的 `descendantFocusability` / `onRequestFocusInDescendants()`，也可能在稍后被页面代码 `view.post { target.requestFocus() }` 覆盖。可以用 `window.decorView.findFocus()` 看最终落到哪个 View。

**易错点：** Activity 自己不是遥控器操作的 focused view。不要以为 Activity resume 后业务目标 item 就已经有焦点；RecyclerView item 可能还没创建，TV 页面仍然要等数据和 attach 后主动下发或恢复焦点。

**关联知识点：** [焦点下发从哪里开始](../知识点梳理/TV焦点下发源码流程.md#焦点下发从哪里开始)

<a id="onrequestfocusindescendants-什么时候会调用"></a>
###### onRequestFocusInDescendants 什么时候会调用

答案：

**简答：** 当焦点要进入某个 `ViewGroup`，并且容器准备把焦点交给内部子 View 时，会走 `onRequestFocusInDescendants()`。

**展开回答：** 它常见于父容器被调用 `requestFocus()`、`descendantFocusability=afterDescendants`、页面某个区域重新获得焦点、弹窗或控制层显示后需要默认聚焦内部按钮等场景。默认逻辑通常是遍历可见 child，调用 child 的 `requestFocus()`，谁先成功就返回 true。TV 里可以 override 它，让频道页优先聚焦当前 Tab，让首页行容器优先聚焦上次卡片，让播放器控制层优先聚焦播放按钮。

**易错点：** 它不是方向键搜索的主入口。已有焦点后用户按方向键找下一个目标，重点看 `focusSearch()` 和 `FocusFinder`。

**关联知识点：** [onRequestFocusInDescendants](../知识点梳理/TV焦点下发源码流程.md#onrequestfocusindescendants)

<a id="focussearch-和-focusfinder-分别负责什么"></a>
###### focusSearch 和 FocusFinder 分别负责什么

答案：

**简答：** `focusSearch()` 是 View / ViewGroup 暴露的“找下一个焦点”入口，`FocusFinder` 是系统默认按方向和几何位置挑选候选 View 的算法实现。

**展开回答：** 用户按方向键时，当前 focused view 会参与 `focusSearch(direction)`，搜索请求通常向父容器或根容器传递。默认情况下，根容器会调用 `FocusFinder.findNextFocus()`，先通过 `addFocusables()` 收集候选，再根据当前焦点矩形、方向、候选矩形的相对位置和距离选出目标。开发者 override `focusSearch()` 可以定制特殊路径，但应该只处理明确场景，其余交给 `super`。

**易错点：** 不要在 `focusSearch()` 里无条件返回当前 View 或固定 View，否则焦点会被锁死或乱跳。

**关联知识点：** [方向键移动 focusSearch 流程](../知识点梳理/TV焦点下发源码流程.md#方向键移动-focussearch-流程)

<a id="nextfocus-和-onkeylistener-在焦点流程里是什么时机"></a>
###### nextFocus 和 OnKeyListener 在焦点流程里是什么时机

答案：

**简答：** `OnKeyListener` 比默认焦点搜索更早，当前 focused View 的 listener 返回 true 后，`nextFocusLeft/Right/Up/Down` 和 `FocusFinder` 都不会执行；`nextFocus*` 是进入默认焦点搜索后、几何查找前优先使用的显式方向目标。

**展开回答：** 遥控器方向键只要进入当前 Activity 的 Window，通常每次都会先走 `Activity.dispatchKeyEvent()`，包括 `ACTION_DOWN`、`ACTION_UP`，长按时还会有 repeat 的 `ACTION_DOWN`。但这只是按键分发入口，不代表 Activity 每次都负责决定焦点去哪；Activity 调用 `super.dispatchKeyEvent(event)` 或返回 false 后，事件才继续进入 Window / DecorView、`ViewGroup.dispatchKeyEvent()`，最后到当前 focused View 的 `dispatchKeyEvent()`。在 View 内部会先给 `OnKeyListener` 机会，如果 listener 返回 true，按键被消费，本次方向移动结束；如果返回 false，才继续走 View 自己的 `onKeyDown()` / `onKeyUp()`。这些都没有消费时，系统才进入默认焦点导航，调用 `focusSearch(direction)`。在默认搜索里，系统会先看当前方向有没有配置 `android:nextFocusLeft/Right/Up/Down` 或对应的 `nextFocusXxxId`，目标可见、可聚焦、在当前 root 内时优先使用；目标不可用时再降级到 `FocusFinder` 的候选收集和几何查找。

**易错点：** 给非当前焦点 View 设置 `OnKeyListener` 不等于页面级拦截；返回 true 会挡住默认焦点移动。`nextFocus*` 只影响方向键焦点搜索，不影响手动 `requestFocus()`、`onRequestFocusInDescendants()` 或确认键点击。

**关联知识点：** [KeyEvent nextFocus 和 OnKeyListener 时机](../知识点梳理/TV焦点下发源码流程.md#keyevent-nextfocus-和-onkeylistener-时机)

<a id="addfocusables-如何影响最终焦点"></a>
###### addFocusables 如何影响最终焦点

答案：

**简答：** `addFocusables()` 决定哪些 View 能进入候选集合；没有被加入候选集合的 View，`FocusFinder` 不可能选中它。

**展开回答：** 焦点搜索不是直接遍历所有 View，而是先收集可聚焦候选。`addFocusables()` 会受 visibility、focusable、enabled、focusableInTouchMode、父容器 `descendantFocusability`、当前方向和容器状态影响。TV 弹窗、播放器控制层、侧边栏、禁用区域都可以通过控制候选集合限制焦点范围。比如弹窗打开时只让弹窗内部控件进入候选，避免方向键把焦点移动到底层页面。

**易错点：** 空实现或错误过滤会让整块区域没有候选焦点；把不可见 View 加进去又会导致焦点落到用户看不到的位置。

**关联知识点：** [addFocusables 候选收集](../知识点梳理/TV焦点下发源码流程.md#addfocusables-候选收集)

<a id="requestchildfocus-是请求焦点吗为什么重要"></a>
###### requestChildFocus 是请求焦点吗为什么重要

答案：

**简答：** 不是。`requestChildFocus()` 是 child 已经获得焦点后，父容器收到的通知，用来记录当前焦点在哪个子树里。

**展开回答：** 当某个子 View `requestFocus()` 成功后，父容器会收到 `requestChildFocus(child, focused)`，记录自己的 focused child，并继续向更上层父容器传递。这样根 View 才能沿父子链找到真正的 focused view。TV 自定义容器可以在这里记录最后一次内部焦点，用于菜单、首页行、播放器控制层、弹窗等区域的焦点恢复。

**易错点：** 长期恢复 RecyclerView item 不要只保存 `View` 引用，因为 item 可能被回收。列表场景要保存业务 id 或 stable id。

**关联知识点：** [requestChildFocus 父链记录](../知识点梳理/TV焦点下发源码流程.md#requestchildfocus-父链记录)

<a id="afterdescendants-为什么不能解决-recyclerview-刷新后焦点丢失"></a>
###### afterDescendants 为什么不能解决 RecyclerView 刷新后焦点丢失

答案：

**简答：** `afterDescendants` 只决定父容器和子 View 谁优先拿焦点，不会保存列表 item 身份，也不会在刷新后自动找回原来的业务 item。

**展开回答：** RecyclerView 刷新后，原来获得焦点的 item View 可能被 rebind、detach、回收或替换。此时问题已经不是“父容器还是子 View 优先”的问题，而是“原来的 focused View 是否还存在，以及应该按业务身份恢复到哪个新 View”。`afterDescendants` 可以让子 View 优先获得焦点，但不能等待 `submitList` 完成、不能滚动到目标 item、不能监听 item attach、也不能按业务 id 定位内容。

**易错点：** XML 加了 `android:descendantFocusability="afterDescendants"` 后仍然会丢焦点是正常的，它不是焦点恢复方案。

**关联知识点：** [ViewGroup requestFocus 和 descendantFocusability](../知识点梳理/TV焦点下发源码流程.md#viewgroup-requestfocus-和-descendantfocusability)

<a id="recyclerview-刷新后应该如何恢复-tv-焦点"></a>
###### RecyclerView 刷新后应该如何恢复 TV 焦点

答案：

**简答：** 刷新前保存当前焦点的业务 id，刷新使用 `ListAdapter + DiffUtil` 和稳定 id，`submitList` 完成后按 id 找到目标 position，滚动到目标 item，等 item attach 后再 `requestFocus()`。

**展开回答：** TV 列表恢复焦点的关键是恢复“同一个业务内容”，不是恢复旧 View。可以保存 `contentId`、`rowId`、旧 position 作为降级。数据回来后先提交到 Adapter，再在提交完成回调中查找业务 id 对应的新 position。如果目标存在，先 `scrollToPosition()`，再通过 `findViewHolderForAdapterPosition()` 或 `OnChildAttachStateChangeListener` 等目标 item 真正 attach，最后对 item 内真正可聚焦的子 View 调用 `requestFocus()`。如果目标内容不存在，就降级到同位置、邻近 item、当前行第一个 item 或页面默认焦点。

**易错点：** 不要在 `onBindViewHolder()` 里无条件 `requestFocus()`，否则每次复用和刷新都会抢焦点，用户手动移动焦点也会被打断。

**关联知识点：** [RecyclerView 下的特殊流程](../知识点梳理/TV焦点下发源码流程.md#recyclerview-下的特殊流程)

<a id="页面首次进入如何下发默认焦点"></a>
###### 页面首次进入如何下发默认焦点

答案：

**简答：** 等目标 View 可见、可聚焦并完成布局后，再调用 `requestFocus()`。

**展开回答：** 页面首次进入时，View 可能还没 attach（通常会比布局和绘制早一点）、列表数据还没提交、RecyclerView item 还没创建，如果立即请求焦点可能失败。常见做法是 `view.post { requestFocus() }`、列表数据提交完成后请求焦点、监听目标 item attach 后请求焦点。请求前要检查目标是否可见、可用、可聚焦。

**易错点：** 不要反复无条件下发默认焦点，否则用户刚移动焦点就会被抢回去。

**关联知识点：** [默认焦点下发](../知识点梳理/焦点和遥控器.md#默认焦点下发)

<a id="焦点丢失怎么排查"></a>
###### 焦点丢失怎么排查

答案：

**简答：** 先找“当前焦点去哪了”，再查 View 是否可聚焦、是否被刷新重建、是否被隐藏、是否有父容器或按键拦截。

**展开回答：** 可以打印 `decorView.findFocus()`，确认焦点是 null、落到错误 View、还是落到不可见区域。然后检查目标 View 的 `focusable`、`visibility`、`enabled`、attach 状态、父容器焦点策略、列表刷新、弹窗层级、按键消费。RecyclerView 场景重点看 item 是否被 `notifyDataSetChanged()` 重建、是否还没 attach 就请求焦点。

**易错点：** 不要只在丢失后直接 `requestFocus()` 兜底，要先定位为什么丢，否则后续还会反复出现。

**关联知识点：** [常见坑](../知识点梳理/焦点和遥控器.md#常见坑)

<a id="recyclerview-列表焦点为什么容易出问题"></a>
###### RecyclerView 列表焦点为什么容易出问题

答案：

**简答：** 因为 RecyclerView 会复用、刷新、滚动和 detach item，焦点 View 可能被重建或移出屏幕。

**展开回答：** TV 列表里 item 是焦点目标。数据刷新、全量 notify、图片加载改变尺寸、焦点放大触发布局、滚动到边缘、嵌套 RecyclerView 抢焦点，都可能导致焦点丢失或错乱。解决方向是稳定 item 尺寸、使用 DiffUtil、保存业务 id、等待 item attach 后恢复焦点、避免在 onBind 中无条件 requestFocus。

**易错点：** “列表焦点丢了就 requestFocus 第一个 item”只是兜底，不是完整方案。返回恢复和数据刷新要恢复用户之前的位置。

**关联知识点：** [列表焦点](../知识点梳理/焦点和遥控器.md#列表焦点)

<a id="tv-嵌套列表怎么做焦点恢复"></a>
###### TV 嵌套列表怎么做焦点恢复

答案：

**简答：** 保存外层栏目和内层 item 的稳定标识，返回时先恢复滚动位置，再等目标 item attach 后请求焦点。

**展开回答：** TV 首页常见外层竖向列表嵌套内层横向列表。焦点恢复要保存外层栏目 id、内层内容 id、外层 position、内层 position。返回后先提交数据，再滚动到目标行和目标列，等 ViewHolder attach 后调用 `requestFocus()`。如果目标内容不存在，就降级到同位置、邻近 item 或默认焦点。

**易错点：** 只保存 position 不够稳定，因为数据插入、删除、排序后 position 可能变化。

**关联知识点：** [横竖嵌套列表](../知识点梳理/TV列表和焦点性能.md#横竖嵌套列表)

<a id="activity-viewpager-多-fragment-怎么做焦点管理"></a>
###### Activity ViewPager 多 Fragment 怎么做焦点管理

答案：

**简答：** Activity 做按键入口、全局兜底和当前 Fragment 转发；Fragment 管本页默认焦点和恢复焦点；ViewGroup / RecyclerView 管区域内焦点移动。不要让 Activity 管每一次方向键应该去哪。

**展开回答：** Fragment 本身不在系统 `KeyEvent` 分发链里，方向键通常先到 `Activity.dispatchKeyEvent()`，再进入 Window / DecorView / ViewGroup / 当前 focused View。如果 Fragment 需要页面级按键处理，要由 Activity 找到当前可见 Fragment 并手动调用类似 `onDispatchKeyEvent()` 的接口。普通区域内焦点移动不需要 Activity 转发，应该交给 `nextFocus*`、`onRequestFocusInDescendants()`、`focusSearch()`、`addFocusables()`、RecyclerView / LayoutManager 等局部逻辑。ViewPager 切换时，每个 Fragment 保存自己的最后焦点；View 还在可以短期保存 View，View 被销毁或列表刷新要保存业务 id。

**易错点：** 在 Activity 里无条件消费方向键，会让所有 Fragment 和 ViewGroup 的默认焦点搜索失效。Activity 转发给 Fragment 时，Fragment 也只应该在真正处理了按键时返回 true。

**关联知识点：** [Activity Fragment 和 ViewGroup 的焦点边界](../知识点梳理/TV焦点下发源码流程.md#activity-fragment-和-viewgroup-的焦点边界)

<a id="打开新页面再返回时焦点怎么恢复"></a>
###### 打开新页面再返回时焦点怎么恢复

答案：

**简答：** 如果旧页面 View 树还在，系统通常能保留原 focused View；如果旧 View 被销毁、RecyclerView 刷新或 item 回收，就要业务保存焦点锚点，返回后按业务 id 找回目标并 `requestFocus()`。

**展开回答：** A 页面打开 B 页面后，A Window 会失去焦点。B 关闭时，如果 A 的 View 树还在，之前的 focused child 链路和目标 View 仍可用，A Window 重新获得焦点后通常能回到原 View。若 A Fragment View 被销毁、列表重新提交、item 被回收，旧 View 引用已经失效，系统只能兜底找一个可聚焦 View，不知道业务上应该回到哪个 item。TV 列表推荐离开前保存业务 id 和 position，返回后等数据恢复、`submitList` 完成、目标 item attach，再对 item 内真正可聚焦的 View 调用 `requestFocus()`。

**易错点：** 不要跨页面长期保存 RecyclerView item 的 View 引用。短期弹窗可以保存 View，跨页面和列表刷新要保存业务 id。

**关联知识点：** [页面返回后的焦点恢复](../知识点梳理/TV焦点下发源码流程.md#页面返回后的焦点恢复)

<a id="遥控器按键事件怎么处理"></a>
###### 遥控器按键事件怎么处理

答案：

**简答：** 根据业务在合适层级处理 KeyEvent，方向键不要无条件消费，确认键要兼容 `DPAD_CENTER` 和 `ENTER`。

**展开回答：** Activity、ViewGroup、View 都可能处理按键。方向键每次进入当前 Activity Window 时都会先到 `Activity.dispatchKeyEvent()`，但正常情况下 Activity 应该调用 `super` 继续分发，让当前 focused View 和系统焦点搜索处理移动。只有在需要特殊路径、播放器控制、弹窗限制时才拦截。返回 `true` 表示消费事件，返回 `false` 或调用 `super` 表示继续分发。长按和连续按键要看 `repeatCount`，避免重复触发业务。

**易错点：** 在 Activity 高层直接消费所有方向键，会导致页面焦点完全不动。

**关联知识点：** [遥控器按键](../知识点梳理/焦点和遥控器.md#遥控器按键)

<a id="弹窗关闭后焦点怎么恢复"></a>
###### 弹窗关闭后焦点怎么恢复

答案：

**简答：** 弹窗打开前保存当前焦点，关闭后如果原焦点仍可用就恢复，否则降级到页面默认焦点。

**展开回答：** 弹窗显示后焦点应进入弹窗内部，避免焦点跑到底层页面。关闭时检查打开前的 View 是否还 attach、可见、可聚焦，如果可用就 `requestFocus()`；如果页面刷新或原 View 不存在，就恢复到默认按钮、当前列表 item 或第一个可操作控件。

**易错点：** 弹窗关闭后不恢复焦点，用户会感觉遥控器突然失效。

**关联知识点：** [弹窗和浮层焦点](../知识点梳理/焦点和遥控器.md#弹窗和浮层焦点)
