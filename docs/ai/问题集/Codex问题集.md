### Codex 问题集

###### 内容概述

本文件记录 Codex 使用过程中的自测问题、待验证问题和常见误区，用于复盘提示词、上下文、文件改动、验证和人工 Review。

###### 使用场景

- 使用 Codex 前，用来自查任务描述是否清楚。
- 使用 Codex 后，用来检查改动是否经过验证。
- 复盘失败任务时，用来记录问题原因和改进方式。

###### 任务开始前要给 Codex 哪些上下文

问题：

- 当前任务目标是什么？
- 目标仓库和模块在哪里？
- 有没有项目规则、README、模板或已有同类文件？
- 哪些文件不能改？
- 完成后需要跑什么检查？

处理建议：

- 尽量给出路径、模块名、功能入口和验收标准。
- 如果任务涉及现有结构，先要求 Codex 读取同类模块。
- 如果任务涉及知识库，要求它遵守模板、索引和链接规则。

<a id="codex-改完后要检查什么"></a>
###### Codex 改完后要检查什么

问题：

- diff 是否只集中在目标文件？
- README 导航是否能跳到新文件？
- Markdown 链接和锚点是否正确？
- 代码任务是否跑了构建、测试或 Lint？
- 文档任务是否跑了知识库检查脚本？

处理建议：

- 先看 `git diff`，再看验证命令输出。
- 如果检查失败，优先修当前任务造成的问题。
- 对无关既有失败要明确记录，不要顺手大改。

<a id="哪些情况不能直接相信-codex-的结论"></a>
###### 哪些情况不能直接相信 Codex 的结论

问题：

- 版本、价格、政策、法规、接口文档是否可能变化？
- 代码是否真的能编译？
- 生成的 API 是否在当前依赖版本里存在？
- 安全、隐私、性能结论有没有证据？

处理建议：

- 易变信息要查官方来源或当前项目依赖。
- 技术结论尽量用源码、日志、测试或官方文档支撑。
- 不确定内容标记为待验证。

<a id="命令或检查失败时应该怎么继续"></a>
###### 命令或检查失败时应该怎么继续

问题：

- 失败是当前改动造成的，还是仓库已有问题？
- 错误信息指向哪个文件或脚本？
- 是否需要缩小命令范围？
- 是否有权限、网络、缓存或环境限制？

处理建议：

- 先读错误信息，不要盲目重复执行。
- 如果是当前改动造成的，修到检查通过。
- 如果是环境问题，说明阻塞点和已完成的验证范围。

<a id="如何把一次-codex-使用沉淀成知识"></a>
###### 如何把一次 Codex 使用沉淀成知识

问题：

- 这次任务的稳定流程是什么？
- 哪些 Prompt 有效，哪些描述容易误解？
- 哪些检查命令最有用？
- 是否有可复用的模板、问题集或面试题？

处理建议：

- 把稳定结论放进知识点。
- 把不确定问题放进问题集。
- 把可被问到的理解点整理到面试题。
