<a id="基本定位"></a>
###### 基本定位

- Codex 更适合当“能读仓库、能改文件、能跑命令的开发协作助手”，不是只回答概念的普通聊天窗口。
- 它的价值不只是生成代码，还包括理解已有结构、按项目规则改动、解释 diff、补测试思路和整理文档。
- Codex 的输出不能默认等于最终事实，仍然需要通过代码审查、测试、日志和实际运行结果验证。
- 对仓库任务来说，最重要的是让它先读项目规则、相关文件和现有模式，再决定怎么改。

<a id="基础工作流"></a>
###### 基础工作流

1. 说清目标：要新增、修改、排查、解释还是复盘。
2. 给出范围：明确仓库路径、模块、文件、功能入口或错误日志。
3. 说明约束：例如不要改无关文件、需要保持现有结构、必须跑检查。
4. 让 Codex 先读上下文：先看 README、规则文件、相关代码和现有样式。
5. 执行改动：通过 diff 观察变更是否集中在目标范围内。
6. 验证结果：优先运行项目已有脚本、单测、构建或文档检查。
7. 复盘沉淀：把稳定结论记录到知识点、问题集或 troubleshooting。

<a id="prompt-写法"></a>
###### Prompt 写法

- 好的 Prompt 通常包含四件事：目标、上下文、约束、验收标准。
- 目标要具体，例如“把 Codex 学习笔记放到 AI/知识点梳理，并补面试题和问题集”，比“整理一下 AI”更可执行。
- 上下文要指向真实文件，例如模块 README、项目规则、已有同类目录。
- 约束要写清边界，例如“不改无关文档”“保留已有链接”“按 Java 模块结构生成”。
- 验收标准要能检查，例如“check-knowledge.ps1 通过”“README 导航能跳转到新文件”。

<a id="风险控制"></a>
###### 风险控制

- 不要把 AI 生成内容当作已验证结论，尤其是接口、版本、法律合规、安全和性能结论。
- 修改前先看工作区状态，避免覆盖用户未提交改动。
- 修改后看 diff，确认是否只改了目标文件。
- 涉及代码时要跑对应测试或构建；涉及文档时要跑链接和结构检查。
- 对不确定内容标记“待验证”，不要伪装成确定事实。

<a id="android-项目实践"></a>
###### Android 项目实践

- 文档整理：生成模块 README、知识点、面试题、问题集和索引。
- 代码阅读：让 Codex 按调用链解释 Activity、Fragment、ViewModel、Repository 或工具类。
- 问题排查：把崩溃日志、构建错误、运行现象和相关文件一起给 Codex，要求输出排查路径。
- 迁移改造：先让 Codex 做范围扫描和影响面说明，再分步骤修改。
- 验证闭环：Android 项目优先跑 Gradle 编译、单测、Lint 或项目已有检查脚本。
